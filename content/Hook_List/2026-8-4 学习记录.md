# AMI BIOS HookList（Hook 机制）

Hook 是 AMI BIOS 预留的一批「扩展点」。BIOS 在特定执行流里留好调用位置，OEM 写个函数注册到对应位置，BIOS 跑到那里就自动调用，无需改动核心代码。

## 一、什么是 Hook

- **Hook = 在程序执行流中插入自定义函数**，不修改原始代码即可扩展功能
- AMI BIOS 预设了 **41 个 Hook 点（HOOKID1～HOOKID41）**，覆盖 TSE（Setup）全生命周期：开机画面、键盘映射、进入 Setup、启动前行为、密码处理等
- 调用模型：BIOS 核心代码只调用 Hook 的**入口函数**（如 `DrawQuietBootLogoHook`），由入口函数调度真正注册的回调

```
BIOS 核心代码
    │  正常执行
    ▼
Hook 插入点 ──▶ 自定义函数
    │              │
    └──────────────┘
    ▼
回到正常流程
```

## 二、AMI HookList 架构

### 核心结构

1. **函数指针数组 `AMITSE_HookList[]`**：全局数组，存所有注册的 Hook 函数，以 `NULL` 结尾
2. **HOOKID 标识**：每个 Hook 点唯一编号（HOOKID1…HOOKID41），通过编号定位对应的一组回调
3. **编译时注册**：靠 **ELINKS** 机制在编译期注册，不是运行时动态添加——零运行时开销，链接器直接展开函数列表

### 内存布局（逻辑视图）

```
[HOOK1 ] [默认函数] [你的函数A] [你的函数B]   <- HOOKID1 的所有回调
[HOOK2 ] [默认函数] [你的函数C]               <- HOOKID2 的所有回调
[HOOK3 ] [默认函数]                           <- HOOKID3（无自定义）
 ...
[HOOK41] [默认函数] [你的函数D]
[NULL ]                                           <- 数组结束符
```

## 三、关键数据结构（HookAnchor.h）

### Hook 函数类型（节选）

```c
typedef VOID    (TSE_HOOK)(VOID);              // 基础：无参无返回值
typedef BOOLEAN (TSE_HOOK_T1)(VOID);           // 返回 BOOLEAN
typedef EFI_STATUS (TSE_HOOK_T4)(BOOT_FLOW *bootFlowPtr);
typedef VOID    (TSE_HOOK_T5)(CHAR16 *Password, UINTN MaxSize); // 带参数
// ...共 10+ 种类型（T1 ~ T10）
```

### HOOKID 宏与全局数组

```c
UINTN gHookBase = TSE_HOOKBASE_VALUE;   // TSE 这条 HookList 的基地址偏移
#define HOOKID0  (gHookBase)
#define HOOKID1  (gHookBase + 1)
// ...
#define HOOKID41 (gHookBase + 41)

TSE_HOOK *AMITSE_HookList[] = {
    HOOK_LIST_FROM_ELINKS,   // 编译期由 ELINKS 展开
    NULL                     // 结束符
};
```

> `gHookBase`（`TSE_HOOKBASE_VALUE`）是 TSE 这条 HookList 的基址。**HOOKID1～HOOKID41** 是真正的 Hook 点，HOOKID0 是基址标记。不同子系统（NVRAM、SMM、PCI）各有自己的数组和 base 偏移，互不干扰——"多张独立 HookList 共存"的设计。

### 部分 HOOKID 与默认函数对照

| HOOKID | 默认函数 | 触发时机 |
| -------- | ------------------------- | ------------- |
| HOOKID1 | `DrawQuietBootLogoHook` | 开机 Logo 显示 |
| HOOKID3 | `ProcessEnterSetupHook` | 进入 BIOS Setup |
| HOOKID7 | `MapControlKeysHook` | 按键映射 |
| HOOKID11 | `BeforeEfiBootLaunchHook` | OS 启动前 |
| HOOKID20 | `PasswordEncodeHook` | 密码处理 |

## 四、工作原理（调度流程）

```c
// GenericHook —— 调度器核心
VOID GenericHook(UINTN HookNum, TSE_HOOK *defaultfn)
{
    UINTN first, last;
    if (SearchHook(HookNum, &first, &last)) {
        for (i = first; i <= last; i++)   // 找到：依次执行所有注册的回调
            AMITSE_HookList[i]();
    } else {
        defaultfn();                       // 没找到：执行默认函数（回退）
    }
}
```

1. BIOS 调用 Hook 入口函数（如 `DrawQuietBootLogoHook`）
2. 入口函数调用 `GenericHook` 调度器
3. `GenericHook` 用 HOOKID 在数组里 `SearchHook`，得到该 Hook 点的 `[first, last]` 索引区间
4. 找到 → 依次执行区间内所有已注册的回调
5. 没找到（无自定义回调）→ 执行默认函数，行为不退化

> `GenericHook` 是整张机制的中枢：按 HOOKID 搜出索引区间，跑区间内全部回调；无自定义注册就回退默认函数。核心代码永远只调入口函数，从不知道有没有 OEM 回调——耦合被彻底解开。

## Hook 入口函数的调用约定

每个 Hook 点暴露一个**公开入口函数 `XxxHook()`**，AMITSE 核心代码只调这些入口；入口再委托给 `GenericHook` / `GenericHookTypeN`。核心代码不感知自定义 Hook 的存在。

```c
// 简单 Hook（无参无返回）
VOID DrawQuietBootLogoHook(VOID) {
    GenericHook(HOOKID1, DrawQuietBootLogo);
}
VOID ProcessEnterSetupHook(VOID) {
    GenericHook(HOOKID3, ProcessEnterSetup);
}
VOID BeforeEfiBootLaunchHook(VOID) {
    GenericHook(HOOKID11, BeforeEfiBootLaunch);
}

// 带参数的 Hook（用对应类型的调度器转发参数）
CONTROL_ACTION MapControlKeysHook(AMI_EFI_KEY_DATA key)
{
    return GenericHookType2(HOOKID7, (TSE_HOOK*)MapControlKeys, key);
}
```

> 为什么有 T1～T10 这么多类型与调度器：C 数组是同质的，一张 `TSE_HOOK*` 数组只能统一存"无参无返回"的函数指针。要传参数/返回值，必须有带类型的包装调度器（`GenericHook` 用于 void/void，`GenericHookType2` 转发一个参数并返回 `CONTROL_ACTION`，以此类推）。这是 C 类型系统在约束 Hook 机制的形状。

## ELINKS —— 如何注册 Hook 自定义函数

ELINKS 是 AMI 的**编译期 Hook 注册系统**：在 `.sdl` 文件里声明函数，构建系统自动展开进函数指针数组。

```
1. 写函数     Your .c file
2. 声明 eLink 在 .sdl 里写 eLink 声明
3. AMISDL 构建  自动展开
4. 进数组     编译进 AMITSE_HookList[]
```

```c
// 你的 .sdl 中声明：
//   eLink TSE_HOOK_LIST =
//       HOOK1, MyCustomBootLogo
//
// 构建后，HOOK_LIST_FROM_ELINKS 展开为：
//   HOOK1, DrawQuietBootLogo, MyCustomBootLogo, HOOK3, ProcessEnterSetup, ..., NULL
```

### 为什么是编译期而不是运行时

- **零运行时开销**：链接期定好，运行时不查表分配
- **Flash ROM 体积受限**：BIOS 对固件镜像大小有硬性预算
- **无动态内存分配**：很多阶段（尤其 PEI / 早期 DXE）根本没有堆
- **执行顺序确定**：ELINKS 展开顺序即回调执行顺序，便于复现问题
- **易于调试**：直接看 `Build/*.h` 生成的展开结果确认注册成功

## 添加自己的 Hook 自定义函数

```c
// Step 1：写 Hook 函数（签名必须匹配对应 TSE_HOOK_Tn 类型）
VOID MyCustomBootLogo(VOID)
{
    DrawMyCompanyLogo();
    ShowVersionInfo();
}
```

```text
// Step 2：在模块的 .sdl 里注册
//   eLink TSE_HOOK_LIST =
//       HOOK1, MyCustomBootLogo

// Step 3：构建后到 Build/AMITSEElinks.h 之类生成文件里确认
//   应该能看到 MyCustomBootLogo 出现在展开后的 HOOK_LIST_FROM_ELINKS 中

// Step 4：烧录并测试
```

四步总结：**写函数（签名对齐 TSE_HOOK_Tn）→ 在 .sdl 注册 → 构建并验证 → 烧录测试**。

## 其他类型的 Hook

TSE 的 HookList 只是其中之一，AMI 还有几张独立的 HookList，机制相同但挂在不同子系统：

### NVRAM Hook（变量访问拦截）

- `SetVariableHookList[]` —— 在 `SetVariable` **写之前**调用
- `GetVariableHookList[]` —— 在 `GetVariable` **读之前**调用
- `AfterSetVariableHookList[]` —— 在 `SetVariable` **写之后**调用
- 用途：Secure Boot、Setup 变量过滤。头文件 `AmiNvramDxePlatformHooks.h`

### SMM Hook（系统管理模式拦截）

- `BeforeAfterSmmDispatchHookFunction[]` —— 在 SMI 派发**前/后**运行
- 运行在 SMM 高特权级，用于南桥 SMI 处理
- 通过 `PLATFORMHOOK` eLink 注册。头文件 `AmiSmmCorePlatformHooks.h`

### PCI Hook（PCI 设备回调）

- `ANY_PCI_DEV_CALLBACK(VID, DID, fn)` —— 按厂商/设备 ID 匹配回调
- `0xFFFF` 匹配所有设备
- 用途：设备初始化、Option ROM、跳过设备
- 多阶段回调：`Program`、`Attributes` 等。头文件 `PciBusDevHooksElink.h`

## 与 EDK II 原生机制的对照

AMI 的 HookList 是 Aptio V 在 EDK II 之上的增值层：

| AMI Aptio V 机制 | EDK II 对应物 | 说明 |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `GenericHook` 调度 + 回调数组 | 事件通知模型（CreateEvent/SignalEvent + notify 链）、RegisterProtocolNotify | 都是"observer/通知链"：登记一组回调，触发时依次跑。差异：AMI 编译期固定，EDK II 运行时动态（需堆） |
| TSE `XxxHook()` 入口 | （EDK II Setup 无内建 HookList） | EDK II 表单浏览器靠 HII/Protocol，没有 AMI 这种预设扩展点 |
| NVRAM `SetVariableHookList` | VariablePolicy 与 VarCheckLib/VarCheckPolicyLib | 都是"SetVariable 执行前拦截/校验/加锁"。EDK II 用策略引擎，运行在 SMM/MM 可信环境 |
| SMM `BeforeAfterSmmDispatchHookFunction` | `SmmCorePlatformHookLib`：PlatformHookBeforeSmmDispatch / After | 几乎一一对应：PI SMM Core 在调用已注册 SMI handler 前后调用这两个平台 Hook |
| 单槽平台 Hook（`PlatformHookSerialPortInitialize`） | `PlatformHookLib`（库类，平台提供实例覆盖） | "接口留空、平台实现覆盖"的 Hook 抽象 |
| PCI `ANY_PCI_DEV_CALLBACK` | `PciPlatformLib` / `PciHostBridgeLib` 平台回调、EFI_PCI_ENUMERATION_COMPLETE_GUID 通知 | 按设备匹配、在枚举各阶段插入平台逻辑 |
| ELINKS 编译期函数表 | INF 的 [Protocols]/[Ppis]/[Guids] 元数据 + PCD FixedAtBuild | EDK II 没有通用"链接期回调表"机制，但 Aptio V 的 BDS 控制流本身就是一张 eLink 函数派发表 |

> Aptio V 的 BDS 阶段控制流，官方文档明确说是一张 **eLink 函数派发表**，允许 OEM 加函数、禁函数、换实现。HookList 不是孤立设计，而是 AMI 整个"eLink 派发表"思想在 TSE 上的体现。

## 设计洞察

- **为什么用编译期而非运行时**：BIOS 固件有硬性 Flash ROM 体积预算，PEI/早期 DXE 往往没有堆，动态注册需要运行时分配和动态链表。编译期把一切钉死最省事也最稳
- **为什么有多张独立 HookList + base 偏移**：TSE、NVRAM、SMM、PCI 各自维护自己的数组和 `g*HookBase`，避免单张大表；`SearchHook` 用 `[first, last]` 索引区间定位某个 HOOKID 的回调
- **类型系统的影子**：C 数组同质才演化出 `TSE_HOOK_T1～T10` 族类型与 `GenericHookTypeN` 包装器，它们把不同签名"桥接"进那张 void 指针数组

## 术语表

| 术语 | 含义 |
| --------------------- | ------------------------------------------------ |
| **Hook** | BIOS 预留的扩展点，运行到该点自动调用 OEM 注册的函数 |
| **TSE** | AMI Setup Engine，41 个 Hook 覆盖其全生命周期 |
| **HOOKID** | 每个 Hook 点的唯一编号（HOOKID1～HOOKID41） |
| **AMITSE_HookList[]** | 全局函数指针数组，存所有注册回调，NULL 结尾 |
| **GenericHook** | 调度器核心，按 HOOKID 搜区间并依次执行回调，无注册回退默认函数 |
| **ELINKS / eLink** | AMI 编译期注册机制，SDL 声明经 AMISDL 展开进数组 |
| **TSE_HOOK_Tn** | Hook 函数类型族（T1～T10），对应不同参数/返回值 |
| **SearchHook** | 按 HOOKID 返回该 Hook 在数组中的 `[first, last]` 索引区间 |
