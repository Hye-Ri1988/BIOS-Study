# Runtime Services

Runtime Services 是 UEFI 固件唯一一组在 `ExitBootServices()` 后还可用的服务。OS 内核跑起来之后，Boot Services 那张表已作废，但 Runtime 表仍驻留在内存里，内核可以随时调用它读写 NVRAM 变量、读硬件时钟、复位平台、投递固件升级包。

所有接口通过全局指针 `gRT`（类型 `EFI_RUNTIME_SERVICES *`）访问，本质是一张函数指针表。

## 1. 定位与生命周期

`gRT` 来自 `EFI_SYSTEM_TABLE` 的 `RuntimeServices` 字段。EDK II 的 `UefiRuntimeServicesTableLib` 在库构造阶段从 `SystemTable->RuntimeServices` 取出并缓存为 `gRT`。

三个阶段的分界：

| 阶段 | Boot Services | Runtime Services |
| --- | --- | --- |
| DXE / BDS | 可用 | 可用（物理地址） |
| `ExitBootServices()` 之后、OS 未启用 MMU | 全部失效 | 可用（物理地址） |
| OS 调用 `SetVirtualAddressMap()` 之后 | 全部失效 | 可用（虚拟地址，指针已重定位） |

`ExitBootServices()` 并不销毁 Runtime 表，只是让承载它的内存从"固件所有"变成"OS 所有但标记为 `EFI_MEMORY_RUNTIME` 不可回收"。Runtime 代码和数据分别位于 `EfiRuntimeServicesCode` / `EfiRuntimeServicesData` 类型的内存区，OS 建页表时必须保留映射。

`EFI_RUNTIME_SERVICES` 表头 `Hdr` 带 CRC32，OS 可校验表是否被破坏。平台若无法在 runtime 提供某些服务，规范建议发布 `EFI_RT_PROPERTIES_TABLE` 配置表，用位图告知 OS 哪些接口真正可用；固件仍必须提供返回 `EFI_UNSUPPORTED` 的桩函数，不能留空指针。

## 2. EFI_RUNTIME_SERVICES 表全貌

结构定义在 `MdePkg/Include/Uefi/UefiSpec.h`：

```c
typedef struct {
  EFI_TABLE_HEADER                Hdr;

  // Time Services
  EFI_GET_TIME                    GetTime;
  EFI_SET_TIME                    SetTime;
  EFI_GET_WAKEUP_TIME             GetWakeupTime;
  EFI_SET_WAKEUP_TIME             SetWakeupTime;

  // Virtual Memory Services
  EFI_SET_VIRTUAL_ADDRESS_MAP     SetVirtualAddressMap;
  EFI_CONVERT_POINTER             ConvertPointer;

  // Variable Services
  EFI_GET_VARIABLE                GetVariable;
  EFI_GET_NEXT_VARIABLE_NAME      GetNextVariableName;
  EFI_SET_VARIABLE                SetVariable;

  // Miscellaneous Services
  EFI_GET_NEXT_HIGH_MONO_COUNT    GetNextHighMonotonicCount;
  EFI_RESET_SYSTEM                ResetSystem;

  // UEFI 2.0 Capsule Services
  EFI_UPDATE_CAPSULE              UpdateCapsule;
  EFI_QUERY_CAPSULE_CAPABILITIES  QueryCapsuleCapabilities;

  // Miscellaneous UEFI 2.0 Service
  EFI_QUERY_VARIABLE_INFO         QueryVariableInfo;
} EFI_RUNTIME_SERVICES;
```

14 个函数指针，按功能分五类：

| 类别 | 接口 | 用途 |
| -------------- | ------------------------------------------------------------------- | ------------- |
| Variable | GetVariable / SetVariable / GetNextVariableName / QueryVariableInfo | NVRAM 变量读写与枚举 |
| Time | GetTime / SetTime / GetWakeupTime / SetWakeupTime | RTC 读写与定时唤醒 |
| Virtual Memory | SetVirtualAddressMap / ConvertPointer | 物理地址到虚拟地址的迁移 |
| Reset | ResetSystem | 冷/热复位、关机 |
| Capsule | UpdateCapsule / QueryCapsuleCapabilities | 固件在线升级投递 |
| Misc | GetNextHighMonotonicCount | 跨掉电单调计数高 32 位 |

> `QueryVariableInfo` 在结构体末尾而不是紧跟其他变量服务——它是 UEFI 2.0 才补进来的，为了不破坏 ABI 只能追加尾部。表结构的这种"历史层积"在 UEFI 里很常见。

## 3. 变量服务 Variable Services

变量服务是 Runtime 中被调用最频繁、出问题也最多的部分。

### 3.1 变量的身份

一个变量由 **(VariableName, VendorGuid)** 二元组唯一标识。同一个 GUID 命名空间下变量名唯一，不同 GUID 下同名变量互不干扰——给每个厂商/子系统分配独立命名空间，避免 OEM 变量和规范变量撞名。

规范定义的全局变量挂在 `EFI_GLOBAL_VARIABLE` GUID（`8BE4DF61-93CA-11D2-AA0D-00E098032B8C`）下：

| 变量名 | 内容 |
| ------------------------------------------ | ------------------------- |
| `Boot####` | 单个启动项（描述、DevicePath、可选数据） |
| `BootOrder` | 启动项顺序，UINT16 数组 |
| `BootCurrent` | 本次启动使用的启动项编号 |
| `BootNext` | 下次启动强制使用的启动项，用后自动删除 |
| `Timeout` | 启动菜单等待秒数 |
| `ConIn` / `ConOut` / `ErrOut` | 控制台设备路径 |
| `PK` / `KEK` / `db` / `dbx` | Secure Boot 密钥与签名数据库 |
| `SecureBoot` / `SetupMode` | Secure Boot 状态（只读） |
| `OsIndications` / `OsIndicationsSupported` | OS 与固件之间的功能协商位图 |

### 3.2 四个接口

```c
// 读
EFI_STATUS GetVariable (
  IN     CHAR16    *VariableName,
  IN     EFI_GUID  *VendorGuid,

// 枚举
EFI_STATUS GetNextVariableName (
  IN OUT UINTN     *VariableNameSize,
  IN OUT CHAR16    *VariableName,

// 写 / 改 / 删
EFI_STATUS SetVariable (
  IN CHAR16    *VariableName,
  IN EFI_GUID  *VendorGuid,
  IN UINT32    Attributes,
  IN UINTN     DataSize,
  IN VOID      *Data);

// 查询存储空间
EFI_STATUS QueryVariableInfo (
  IN  UINT32  Attributes,
  OUT UINT64  *MaximumVariableStorageSize,
  OUT UINT64  *RemainingVariableStorageSize,
  OUT UINT64  *MaximumVariableSize);
```

### 3.3 属性位

```c
#define EFI_VARIABLE_NON_VOLATILE                          0x00000001
#define EFI_VARIABLE_BOOTSERVICE_ACCESS                    0x00000002
#define EFI_VARIABLE_RUNTIME_ACCESS                        0x00000004
#define EFI_VARIABLE_HARDWARE_ERROR_RECORD                 0x00000008
#define EFI_VARIABLE_AUTHENTICATED_WRITE_ACCESS            0x00000010  // 已废弃
#define EFI_VARIABLE_TIME_BASED_AUTHENTICATED_WRITE_ACCESS 0x00000020
#define EFI_VARIABLE_APPEND_WRITE                          0x00000040
#define EFI_VARIABLE_ENHANCED_AUTHENTICATED_ACCESS         0x00000080
```

| 属性 | 含义与约束 |
| --------------------------------------- | -------------------------------------------------------------------------------------------- |
| `NON_VOLATILE` (NV) | 存入非易失介质（SPI Flash 的 NVRAM 区），掉电保留。不设则只存内存，重启即失 |
| `BOOTSERVICE_ACCESS` (BS) | 启动期可访问 |
| `RUNTIME_ACCESS` (RT) | `ExitBootServices()` 后仍可访问。**设置 RT 必须同时设置 BS**，否则返回 `EFI_INVALID_PARAMETER` |
| `HARDWARE_ERROR_RECORD` (HR) | 硬件错误记录，存 NVRAM 单独划出的错误记录配额区 |
| `AUTHENTICATED_WRITE_ACCESS` | 老式认证写，已废弃，平台应返回 `EFI_UNSUPPORTED` |
| `TIME_BASED_AUTHENTICATED_WRITE_ACCESS` | 基于时间戳的认证写，数据前置 `EFI_VARIABLE_AUTHENTICATION_2`。Secure Boot 的 PK/KEK/db/dbx 用它 |
| `APPEND_WRITE` | 追加而非覆盖。给 `dbx` 增量吊销签名时很有用 |
| `ENHANCED_AUTHENTICATED_ACCESS` | 增强认证，负载以 `EFI_VARIABLE_AUTHENTICATION_3` 开头 |

最常用组合 `NV | BS | RT`（掉电保留、全程可读写）。只给 BIOS Setup 内部用的配置常写成 `NV | BS`，不暴露给 OS。

### 3.4 GetVariable 的两次调用范式

`GetVariable` 不会替你分配内存，缓冲不够返回 `EFI_BUFFER_TOO_SMALL` 并把所需大小写回 `DataSize`。标准写法是先探大小再取数据：

```c
EFI_STATUS  Status;
UINTN       DataSize;
UINT32      Attributes;
VOID        *Data;

DataSize = 0;
Status = gRT->GetVariable (
           L"BootOrder",
           &gEfiGlobalVariableGuid,
           &Attributes,
           &DataSize,
           NULL);                 // 第一次：只问大小

if (Status != EFI_BUFFER_TOO_SMALL) {
  return Status;                  // 变量不存在或硬件错误
}

Data = AllocateZeroPool (DataSize);
if (Data == NULL) {
  return EFI_OUT_OF_RESOURCES;
}

Status = gRT->GetVariable (
           L"BootOrder",
           &gEfiGlobalVariableGuid,
           &Attributes,
           &DataSize,
           Data);                 // 第二次：真正取数据
```

> `GetVariable` 返回 `EFI_NOT_FOUND` 是正常业务分支，不是错误。合理做法是 `EFI_NOT_FOUND` 时写入默认值。EDK II 提供 `UefiLib` 的 `GetVariable2()` / `GetEfiGlobalVariable2()` 封装，内部完成两次调用和内存分配，优先使用（但它们是 Boot Services 期间的库函数，runtime 阶段不可用）。

### 3.5 SetVariable 的写入与删除

```c
UINT32 Value = 0x1234;

Status = gRT->SetVariable (
           L"MySetting",
           &gMyVendorGuid,
           EFI_VARIABLE_NON_VOLATILE |
           EFI_VARIABLE_BOOTSERVICE_ACCESS |
           EFI_VARIABLE_RUNTIME_ACCESS,
           sizeof (Value),
           &Value);
```

删除有两种等价写法：`DataSize = 0`（且未设 APPEND_WRITE/两种认证属性），或 `Attributes = 0`。

> 带 `TIME_BASED_AUTHENTICATED_WRITE_ACCESS` 的变量，`DataSize = 0` 会失败返回 `EFI_SECURITY_VIOLATION`；必须构造只含 AuthInfo 描述符、签名合法的删除请求（清除 Secure Boot 的 PK 就是这个流程）。

**运行时的额外限制**：`ExitBootServices()` 之后，只有同时具备 `RUNTIME_ACCESS` 和 `NON_VOLATILE` 的变量才允许写。有 RT 但非 NV 的变量在运行时降级为只读。

删除释放的空间往往到下一次掉电重启才真正可用——NVRAM 基于 Flash，删除只是打作废标记，真正回收要走 reclaim（垃圾回收）流程。

### 3.6 存储空间与 reclaim

`QueryVariableInfo` 返回该属性组合下的总容量、剩余容量、单个变量上限。典型平台的 NVRAM 变量区只有 64KB～256KB，用完就是用完。

变量区写满时 `SetVariable` 返回 `EFI_OUT_OF_RESOURCES`。固件内部会尝试 reclaim：把有效变量搬到备份区、擦掉整块 Flash、再搬回来。涉及整块擦除，中途掉电可能损坏变量区，是 BIOS 领域经典的高风险路径。

> 现实教训：2016 年前后 Linux 上 `rm -rf /` 会连带删掉 `/sys/firmware/efi/efivars/` 下的变量，导致部分机型无法开机。内核后来给这些文件加了 immutable 标志，并保留变量区 50% 空间不允许运行时写入。

### 3.7 EDK II 中的实现

| 模块 | 路径 | 说明 |
| ----------------------- | --------------------------------------------- | ------------------------------------------- |
| `VariableRuntimeDxe` | `MdeModulePkg/Universal/Variable/RuntimeDxe/` | 非 SMM 版本，变量逻辑直接跑在 DXE runtime 环境 |
| `VariableSmm` | 同上目录 | 真正的变量读写逻辑，运行在 SMM 内 |
| `VariableSmmRuntimeDxe` | 同上目录 | Runtime 侧薄壳，把请求打包后触发 SMI 转交给 `VariableSmm` |

量产平台基本都用 SMM 方案。`VariableSmmRuntimeDxe` 入口做三件事：把四个函数指针挂到 `gRT`、安装 `gEfiVariableArchProtocolGuid` 和 `gEfiVariableWriteArchProtocolGuid`（DXE Core 依赖这两个架构协议才认为变量服务就绪）、注册 `EVT_SIGNAL_VIRTUAL_ADDRESS_CHANGE` 回调转换通信缓冲区指针。

把变量逻辑放进 SMM 的意义：SMRAM 对 OS 不可见不可写，即使内核被攻破，攻击者也只能通过受控的 SMI 接口按规则请求变量操作。代价是每次 `SetVariable` 都要进一次 SMI，开销几十微秒量级，运行时高频写变量会明显拖慢系统。

### 3.8 常见返回码

| 返回码 | 触发条件 |
| --- | --- |
| `EFI_SUCCESS` | 成功 |
| `EFI_NOT_FOUND` | 变量不存在（读或删时） |
| `EFI_BUFFER_TOO_SMALL` | 缓冲不足，`DataSize` 已更新为所需大小 |
| `EFI_INVALID_PARAMETER` | 指针为 NULL、变量名为空、属性组合非法 |
| `EFI_OUT_OF_RESOURCES` | NVRAM 空间不足 |
| `EFI_WRITE_PROTECTED` | 变量只读或被 VariableLock 锁定 |
| `EFI_SECURITY_VIOLATION` | 认证变量签名校验失败 |
| `EFI_DEVICE_ERROR` | Flash 硬件错误 |
| `EFI_UNSUPPORTED` | 平台在当前时点不支持该调用 |

## 4. 时间服务 Time Services

```c
EFI_STATUS GetTime (
  OUT EFI_TIME               *Time,
  OUT EFI_TIME_CAPABILITIES  *Capabilities OPTIONAL);

EFI_STATUS SetTime (IN EFI_TIME *Time);

EFI_STATUS GetWakeupTime (
  OUT BOOLEAN   *Enabled,
  OUT BOOLEAN   *Pending,
  OUT EFI_TIME  *Time);

EFI_STATUS SetWakeupTime (
  IN BOOLEAN   Enable,
  IN EFI_TIME  *Time OPTIONAL);
```

```c
typedef struct {
  UINT16  Year;        // 1900 – 9999
  UINT8   Month;       // 1 – 12
  UINT8   Day;         // 1 – 31
  UINT8   Hour;        // 0 – 23
  UINT8   Minute;      // 0 – 59
  UINT8   Second;      // 0 – 59
  UINT8   Pad1;
  UINT32  Nanosecond;  // 0 – 999,999,999
  INT16   TimeZone;    // -1440 ~ 1440，或 EFI_UNSPECIFIED_TIMEZONE (2047)
  UINT8   Daylight;
  UINT8   Pad2;
} EFI_TIME;
```

`Daylight` 是位域：`EFI_TIME_ADJUST_DAYLIGHT`(0x01) 表示该时区遵循夏令时，`EFI_TIME_IN_DAYLIGHT`(0x02) 表示当前处于夏令时。`TimeZone` 为 `EFI_UNSPECIFIED_TIMEZONE` 表示时间以本地时间表示、时区未知——这正是 Windows 与 Linux 双系统时间对不上的根源之一（Windows 默认把 RTC 当本地时间，Linux 默认当 UTC）。

### 底层硬件

x86 平台的 RTC 就是 PCH 里那块兼容 MC146818 的电路，通过 I/O 端口 `0x70`（index）/ `0x71`（data）访问，掉电由纽扣电池维持。这块寄存器区和 CMOS 配置区是同一片存储。

EDK II 参考实现在 `PcAtChipsetPkg/PcatRealTimeClockRuntimeDxe/`，安装 `EFI_REAL_TIME_CLOCK_ARCH_PROTOCOL`，DXE Core 检测到该协议后才把 `GetTime`/`SetTime` 挂进 `gRT`。

> 读 RTC 时必须处理"更新中"标志（寄存器 A 的 UIP 位），否则可能读到跨秒的撕裂值。和 MCU 上读跨字节的自由运行定时器需要双读校验是同一类问题。

`SetWakeupTime` 配置 RTC 闹钟，到点由 RTC 拉起 PCH 的唤醒逻辑，把系统从 S3/S4/S5 唤醒。BIOS Setup 里的 "Wake on RTC / RTC Alarm Power On" 就是它。

> OS 起来之后：Linux 通常在启动早期读一次 EFI 时间，之后切到自己的 RTC 驱动直接操作硬件；Windows 更多依赖固件接口。不能假设 OS 一定调用 GetTime，也不能假设一定不调用。

## 5. 虚拟地址映射 Virtual Address Services

这是 Runtime 里概念门槛最高的一块，也是理解"固件如何活到 OS 里"的关键。

### 5.1 问题从哪来

固件全程运行在恒等映射的物理地址上（虚拟地址 = 物理地址）。OS 启动后会重建页表，把内核搬到高位虚拟地址空间。此时固件的 Runtime 代码物理上还在原地，但 OS 页表里没有对应映射的话，内核一调 `gRT->GetVariable()` 就是访问非法地址。

OS 的处理：从 memory map 挑出所有带 `EFI_MEMORY_RUNTIME` 属性的段，给每段分配虚拟地址，填进 `VirtualStart` 字段，然后调用：

```c
EFI_STATUS SetVirtualAddressMap (
  IN UINTN                  MemoryMapSize,
  IN UINTN                  DescriptorSize,
  IN UINT32                 DescriptorVersion,
  IN EFI_MEMORY_DESCRIPTOR  *VirtualMap);
```

固件收到后做两件事：按 PE/COFF 重定位表把所有 runtime 镜像重新定位到新虚拟地址；signal `EVT_SIGNAL_VIRTUAL_ADDRESS_CHANGE` 事件组，让各 runtime 驱动自己修正内部指针。

这个调用**全局只能成功一次**，第二次返回 `EFI_UNSUPPORTED`，且必须在 `ExitBootServices()` 之后调用。

### 5.2 固件替你做什么，不替你做什么

固件替你做的：镜像代码段、数据段的整体重定位，以及 `gRT` 表内部那 14 个函数指针的修正。

固件**不**替你做的：
- 你用 `AllocatePool(EfiRuntimeServicesData, ...)` 分配的缓冲区里存的指针
- 全局变量里缓存的任何指针（包括缓存的 `gRT` 自身）
- 链表节点里的 `ForwardLink` / `BackLink`
- 嵌套结构体里的成员指针

原因很直白：固件不知道你那块内存里哪几个字节是指针。这活儿只能驱动自己干。

### 5.3 ConvertPointer 与回调

```c
EFI_STATUS ConvertPointer (
  IN     UINTN  DebugDisposition,
  IN OUT VOID   **Address);
```

`DebugDisposition` 传 `EFI_OPTIONAL_PTR`(0x01) 表示允许指针为 NULL。EDK II 的 `UefiRuntimeLib` 提供三个封装：`EfiConvertPointer()`（数据指针）、`EfiConvertFunctionPointer()`（函数指针）、`EfiConvertList()`（遍历双向链表转换所有节点指针）。

标准写法：

```c
#include <Library/UefiRuntimeLib.h>

VOID   *gGlobalPointer;
EFI_EVENT mVirtualAddressChangeEvent = NULL;

VOID
EFIAPI
VirtualAddressChangeCallback (
  IN EFI_EVENT  Event,
  IN VOID       *Context
  )
{
  EfiConvertPointer (EFI_OPTIONAL_PTR, (VOID **)&gGlobalPointer);
  //  如果驱动缓存了 gRT，也要一起转
}

EFI_STATUS
EFIAPI
MyRuntimeDriverEntry (
  IN EFI_HANDLE        ImageHandle,
  IN EFI_SYSTEM_TABLE  *SystemTable
  )
{
  return gBS->CreateEventEx (
                EVT_NOTIFY_SIGNAL,
                TPL_NOTIFY,
                VirtualAddressChangeCallback,
                NULL,
                &gEfiEventVirtualAddressChangeGuid,
                &mVirtualAddressChangeEvent);
}
```

### 5.4 转换顺序的陷阱

回调本身运行在**物理地址模式**下。一旦某个指针被 `ConvertPointer` 转成虚拟地址，它在当前回调里就再也不能解引用了——MMU 还没切过去。

处理嵌套结构必须**先叶子后根**：

```c
// 正确：先转结构体内部成员，再转指向结构体的指针
gRT->ConvertPointer (0, (VOID **)&gRuntimeData->Buffer);
gRT->ConvertPointer (0, (VOID **)&gRuntimeData);

// 错误：先转了 gRuntimeData，后面就再也访问不到 ->Buffer 了
```

链表更麻烦：必须先遍历转完所有节点内部指针，最后才调 `EfiConvertList()` 转链接字段。

> 漏转一个指针的后果：OS 运行到某个时刻调用该服务，内核直接 panic 或 BSOD，且往往看不出和固件的关系。EDK II 官方文档承认这块"没有工具能帮你确认是否转全了"，最佳实践是**从设计上尽量减少需要转换的指针**。

### 5.5 EDK II 的实现位置

`MdeModulePkg/Core/RuntimeDxe/` 产生 `EFI_RUNTIME_ARCH_PROTOCOL`，实现 `RuntimeDriverSetVirtualAddressMap()` 和 `RuntimeDriverConvertPointer()`。它维护两条链表：所有 runtime 镜像（用于重定位）和所有 runtime 事件（用于 signal）。

### 5.6 OS 侧的实际行为

Linux 在 `efi_enter_virtual_mode()` 里完成这个调用，可用 `efi=noruntime` 内核参数彻底禁用 Runtime Services，也可用 `efi=old_map` 回退旧映射策略。x86_64 上还有一个 ABI 差异：UEFI 使用 Microsoft x64 调用约定，Linux 内核用 System V，所以内核调用 runtime service 时必须通过 `efi_call` 做参数寄存器转换。

## 6. 系统复位服务 Reset Services

```c
VOID ResetSystem (
  IN EFI_RESET_TYPE  ResetType,
  IN EFI_STATUS      ResetStatus,
  IN UINTN           DataSize,
  IN VOID            *ResetData OPTIONAL);

typedef enum {
  EfiResetCold,             // 冷复位：等同按下 reset 键，硬件全面复位
  EfiResetWarm,             // 热复位：不重新初始化，保留部分状态
  EfiResetShutdown,         // 关机：进入 S5
  EfiResetPlatformSpecific  // 平台自定义，ResetData 携带 GUID 说明语义
} EFI_RESET_TYPE;
```

这个函数**不返回**。原型返回 `VOID` 就是这个意思：调用后代码不会往下走。如果它真的返回了，说明平台复位失败，通常意味着 `EFI_RESET_ARCH_PROTOCOL` 没装好。

`ResetData` 的用法：当 `ResetStatus` 不是 `EFI_SUCCESS` 时，`ResetData` 应指向以 null 结尾的宽字符串（可附加二进制数据），描述复位原因。固件可记进日志方便定位。

### 冷热复位的实际区别

x86 平台上两者最终都落到 PCH 的 Reset Control 寄存器（I/O 端口 `0xCF9`）：

| 写入值 | 效果 |
| ------ | ------------------------------ |
| `0x06` | 热复位（INIT#，CPU 复位但不断电，内存内容可能保留） |
| `0x0E` | 冷复位（触发 SLP_S3# 拉低，全平台断电重启） |

关机走 ACPI 路径：向 PM1_CNT 寄存器写 SLP_TYP = S5 并置 SLP_EN 位。

热复位更快但状态残留多，冷复位更彻底。做内存训练、微码更新一类需要"确保硬件回到干净状态"的操作必须用冷复位。

### EDK II 中的调用方式

平台代码一般用 `ResetSystemLib` 封装而非直接调 `gRT->ResetSystem()`：

```c
#include <Library/ResetSystemLib.h>

ResetCold ();
ResetWarm ();
ResetShutdown ();
ResetPlatformSpecific (DataSize, ResetData);
```

好处：这套接口在 PEI 阶段也能用（此时 `gRT` 还不存在）。通用实现在 `MdeModulePkg/Universal/ResetSystemRuntimeDxe/`。

## 7. 固件升级服务 Capsule Services

```c
EFI_STATUS UpdateCapsule (
  IN EFI_CAPSULE_HEADER    **CapsuleHeaderArray,
  IN UINTN                 CapsuleCount,
  IN EFI_PHYSICAL_ADDRESS  ScatterGatherList OPTIONAL);

EFI_STATUS QueryCapsuleCapabilities (
  IN  EFI_CAPSULE_HEADER  **CapsuleHeaderArray,
  IN  UINTN               CapsuleCount,
  OUT UINT64              *MaximumCapsuleSize,
  OUT EFI_RESET_TYPE      *ResetType);
```

### Capsule 是什么

Capsule 是自描述数据包：头部 + 载荷。载荷可以是 BIOS 镜像、微码、TPM 固件、NVMe/网卡固件，甚至可执行的更新驱动。

```c
typedef struct {
  EFI_GUID  CapsuleGuid;       // 标识 capsule 的格式
  UINT32    HeaderSize;
  UINT32    Flags;
  UINT32    CapsuleImageSize;
} EFI_CAPSULE_HEADER;
```

关键 Flags：

| Flag | 值 | 含义 |
| ------------------------------------- | ---------- | -------------------------------- |
| `CAPSULE_FLAGS_PERSIST_ACROSS_RESET` | 0x00010000 | 复位后 capsule 内容仍需保留，供固件下次开机处理 |
| `CAPSULE_FLAGS_POPULATE_SYSTEM_TABLE` | 0x00020000 | 复位后把 capsule 挂进系统配置表，需同时设上一位 |
| `CAPSULE_FLAGS_INITIATE_RESET` | 0x00040000 | `UpdateCapsule` 内部自行触发复位，需同时设第一位 |

区分两个 GUID：**Capsule GUID** 标识包格式（如 FMP Capsule），**Resource GUID / ImageTypeId** 标识"要更新的是哪个部件"，后者通过 ESRT 暴露给 OS。

### 两条投递路径

**内存投递**：OS 把 capsule 放内存（可分散多块，用 ScatterGatherList 描述），调用 `UpdateCapsule` 设 `PERSIST_ACROSS_RESET`，固件记录信息并触发复位。下次开机 PEI 阶段扫描到待处理 capsule，在早期环境完成刷写。

**Capsule on Disk**：capsule 文件写到 ESP 的 `\EFI\UpdateCapsule\` 目录，然后通过 `SetVariable` 在 `OsIndications` 里置 `EFI_OS_INDICATIONS_FILE_CAPSULE_DELIVERY_SUPPORTED`(0x04) 位，重启后固件自己去 ESP 读文件。适合大体积 capsule——内存投递受限于固件能保留的内存量，ESP 空间充裕。

`OsIndications` 是 OS 和固件的功能协商通道：

| 位 | 含义 |
| ----------- | -------------------------------------------------------------------- |
| 0x01 | `BOOT_TO_FW_UI` — 下次开机直接进 BIOS Setup（Windows"高级启动 → UEFI 固件设置"写这位） |
| 0x04 | `FILE_CAPSULE_DELIVERY_SUPPORTED` |
| 0x08 | `FMP_CAPSULE_SUPPORTED` |
| 0x10 | `CAPSULE_RESULT_VAR_SUPPORTED` |
| 0x20 / 0x40 | `START_OS_RECOVERY` / `START_PLATFORM_RECOVERY` |

### ESRT

EFI System Resource Table 是 UEFI 配置表，列出平台上所有可升级的固件资源。每条记录含资源 GUID、当前版本、最低可回滚版本、上次更新结果。

OS 侧完整流程（Linux fwupd 为例）：读 ESRT 枚举可升级设备 → 从 LVFS 下载 capsule → 调 `UpdateCapsule()` 或写 ESP → 设相关 UEFI 变量 → 重启，固件早期验证签名并刷写 → 再次开机后把结果写回 ESRT 和 `Capsule####` 结果变量。

Windows 侧等价：固件更新以 INF 驱动包形式分发，Windows Update 下发后调 `UpdateCapsule` 交给固件。微软对 ESRT 是硬性要求——没有 ESRT 条目，Windows 就不会尝试固件更新。

安全上：capsule 签名由 Secure Boot 体系验证，回滚保护依赖 ESRT 的 LowestSupportedVersion，Flash 写保护靠 Boot Guard / BIOS Guard 和 SPI 控制器锁位。整条链任何一环缺失，capsule 更新都会变成攻击面。

EDK II 实现在 `MdeModulePkg/Universal/CapsuleRuntimeDxe/`，配合 `MdeModulePkg/Universal/CapsulePei/` 完成开机后处理。

## 8. 杂项：GetNextHighMonotonicCount

```c
EFI_STATUS GetNextHighMonotonicCount (OUT UINT32 *HighCount);
```

UEFI 维护 64 位单调递增计数器。低 32 位由 Boot Services 的 `GetNextMonotonicCount()` 提供（每次调用加一，重启清零）；高 32 位由这个 runtime 服务提供（每调用一次加一并**写入 NVRAM**，跨掉电仍然单调递增）。

它是唯一能提供"跨重启不重复序号"的固件接口，可用于日志序号、事务 ID。但每次调用都写一次 NVRAM，绝不能高频使用。

## 9. 编写 Runtime 驱动的约束

### 9.1 INF 配置

```ini
[Defines]
  INF_VERSION    = 0x00010005
  BASE_NAME      = MyRuntimeDxe
  FILE_GUID      = ........-....-....-....-............
  MODULE_TYPE    = DXE_RUNTIME_DRIVER
  VERSION_STRING = 1.0
  ENTRY_POINT    = MyRuntimeDriverEntry

[LibraryClasses]
  UefiDriverEntryPoint
  UefiBootServicesTableLib
  UefiRuntimeServicesTableLib
  UefiRuntimeLib              # EfiConvertPointer 等
  DebugLib

[Depex]
  gEfiVariableArchProtocolGuid AND
  gEfiVariableWriteArchProtocolGuid
```

`MODULE_TYPE = DXE_RUNTIME_DRIVER` 决定两件事：PE/COFF 的 subsystem 字段被设成 runtime 类型，`LoadImage()` 据此从 `EfiRuntimeServicesCode` 分配代码内存；构建工具要求该模块**必须有 `[Depex]` 段**。

### 9.2 ExitBootServices 之后不能做的事

| 不可用 | 原因 |
| ---------------------------------- | ------------------------------------------ |
| 任何 `gBS->xxx` | Boot Services 表已失效 |
| `AllocatePool` / `AllocatePages` | 属于 Boot Services |
| 所有 Protocol 相关操作 | Handle 数据库属于 DXE Core，已随之失效 |
| `DEBUG()` 输出 | 多数 DebugLib 实例依赖串口驱动或 gBS，runtime 下不可靠 |
| 其他非 runtime 驱动提供的服务 | 那些模块的内存已被 OS 回收 |

> 推论：**runtime 阶段要用的所有内存，必须在 `ExitBootServices()` 之前就用 `EfiRuntimeServicesData` 分配好。** 和 MCU 上"中断服务程序里不能调 malloc"是同一个道理——在受限上下文里不能依赖完整运行环境。

### 9.3 两个必须处理的事件

| 事件 | GUID / 类型 | 该做什么 |
| ---------------------- | ----------------------------------- | ----------------------------------------------- |
| Exit Boot Services | `gEfiEventExitBootServicesGuid` | 置标志位 `mAtRuntime = TRUE`，后续代码据此避开 Boot Services |
| Virtual Address Change | `gEfiEventVirtualAddressChangeGuid` | 用 `ConvertPointer` 转换所有缓存的指针 |

两个回调里都不能调用 Boot Services。Virtual Address Change 回调更严格，连间接依赖 protocol 的库函数都不能用。

### 9.4 一个完整骨架

```c
#include <Uefi.h>
#include <Library/UefiBootServicesTableLib.h>
#include <Library/UefiRuntimeServicesTableLib.h>
#include <Library/UefiRuntimeLib.h>
#include <Library/MemoryAllocationLib.h>

STATIC EFI_EVENT  mExitBootServicesEvent = NULL;
STATIC EFI_EVENT  mVirtualAddressChangeEvent = NULL;
STATIC BOOLEAN    mAtRuntime = FALSE;
STATIC VOID       *mRuntimeBuffer = NULL;

STATIC
VOID
EFIAPI
OnExitBootServices (
  IN EFI_EVENT  Event,
  IN VOID       *Context
  )
{
  mAtRuntime = TRUE;
}

STATIC
VOID
EFIAPI
OnVirtualAddressChange (
  IN EFI_EVENT  Event,
  IN VOID       *Context
  )
{
  EfiConvertPointer (EFI_OPTIONAL_PTR, (VOID **)&mRuntimeBuffer);
}

EFI_STATUS
EFIAPI
MyRuntimeDriverEntry (
  IN EFI_HANDLE        ImageHandle,
  IN EFI_SYSTEM_TABLE  *SystemTable
  )
{
  EFI_STATUS  Status;

  //  runtime 阶段要用的内存，必须现在分配
  mRuntimeBuffer = AllocateRuntimeZeroPool (SIZE_4KB);
  if (mRuntimeBuffer == NULL) {
    return EFI_OUT_OF_RESOURCES;
  }

  Status = gBS->CreateEventEx (
                  EVT_NOTIFY_SIGNAL,
                  TPL_NOTIFY,
                  OnExitBootServices,
                  NULL,
                  &gEfiEventExitBootServicesGuid,
                  &mExitBootServicesEvent);
  if (EFI_ERROR (Status)) {
    return Status;
  }

  Status = gBS->CreateEventEx (
                  EVT_NOTIFY_SIGNAL,
                  TPL_NOTIFY,
                  OnVirtualAddressChange,
                  NULL,
                  &gEfiEventVirtualAddressChangeGuid,
                  &mVirtualAddressChangeEvent);
  return Status;
}
```

`AllocateRuntimeZeroPool()` 来自 `MemoryAllocationLib`，等价于用 `EfiRuntimeServicesData` 调 `AllocatePool` 再清零。

## 10. 重入规则

规范对 Runtime Services 的并发调用有明确限制（UEFI 2.10 Table 8.1），核心几条：

- 任何 runtime 服务执行中，不得调用 `SetVirtualAddressMap()`
- `SetVariable` / `UpdateCapsule` / `SetTime` / `SetWakeupTime` / `GetNextHighMonotonicCount` / `ResetSystem` 执行中，不得调用 `ConvertPointer()`
- 变量类接口之间互斥：`GetVariable` 执行中不得从另一个 CPU 调 `SetVariable`
- 时间类接口之间互斥

违反后果规范定义为"未定义"。实践上多核系统 OS 必须自己加锁串行化 runtime 调用——Linux 用 `efi_runtime_lock` 信号量。

例外：Machine Check、INIT、NMI 不可屏蔽，OS 的处理程序可无视限制调用 `GetTime` / 变量接口 / `ResetSystem`，但被打断的那次调用结果不再有保证。

## 12. 需要注意的点

- **`ExitBootServices()` 是分界线**。之后 `gBS` 全部失效，只剩 `gRT`。Runtime 驱动的所有资源必须在这之前准备好
- **只有 `NV | RT` 的变量才能在运行时写**。有 RT 无 NV 的变量在运行时只读。设置 RT 时必须同时设 BS
- **`GetVariable` 用两次调用范式**。`EFI_NOT_FOUND` 是正常分支不是错误
- **NVRAM 空间很小且写入有风险**。通常几十到几百 KB。运行时高频 `SetVariable` 因 SMI 开销拖慢系统，还可能触发 reclaim
- **虚拟地址转换漏一个指针就是内核崩溃**。转换顺序从叶子到根，转换后的指针在回调内不可再解引用。设计上尽量减少需要转换的指针
- **`ResetSystem` 不返回**。返回了就说明复位失败。选冷复位还是热复位取决于是否需要硬件回到干净状态
- **不要在 runtime 代码里用 `DEBUG()`**。大部分 DebugLib 实例 runtime 下不可用，调试靠 POST code、专用日志缓冲区或硬件调试器
- **Runtime 驱动的 `[Depex]` 是强制的**。构建工具会检查，缺了报错
- **平台可以不实现某些服务**。通过 `EFI_RT_PROPERTIES_TABLE` 告知 OS，但仍必须提供返回 `EFI_UNSUPPORTED` 的桩函数
