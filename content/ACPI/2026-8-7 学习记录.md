# UEFI 与 ACPI

ACPI（Advanced Configuration and Power Interface，高级配置与电源接口）是固件与操作系统之间描述硬件、协商电源管理的工业标准。它和 UEFI 不是同一层东西：UEFI 负责把机器从加电带到"能交棒给 OS"的状态，ACPI 则是交棒时一起递过去的"硬件操作手册"。


## 一、ACPI 是什么：从 APM 到 OSPM

ACPI 的核心目标是 **OSPM（OS-directed Power Management）**——电源调度的最终决策权在 OS，固件只负责把硬件能力和操作方法如实汇报。它取代了更早、更混乱的几套旧标准：

- **APM（Advanced Power Management）**：BIOS 主导电源管理，OS 几乎没有发言权，且只有粗粒度 S 状态，无法做设备级精细调度
- **MPS（MultiProcessor Specification）**：多处理器枚举，被 ACPI 的 MADT 吸收
- **PnP BIOS**：即插即用，被 ACPI 的资源描述方法取代

> 一句话区分：APM 时代"BIOS 说了算"，ACPI 时代"OS 说了算，固件提供数据和方法"。

ACPI 的定义由两部分组成（整个标准的骨架）：
- **表（Tables）**：静态数据结构，描述"有什么硬件、各在什么地址、能力如何"
- **控制方法（Control Methods）**：AML 字节码，描述"怎么操作这些硬件"。OS 用自带的 AML 解释器执行

## 二、UEFI 固件与 ACPI 的关系

| 角色 | 职责 |
| --- | --- |
| UEFI 固件（实现者） | 在 DXE 阶段根据硬件配置生成 DSDT/SSDT 等表；实现 ACPI 规定的硬件寄存器接口（PM1、GPE、Reset 等）；把表交给 OS |
| ACPI（标准） | 规定"固件怎么描述硬件、OS 怎么解析、方法怎么写"的语法和词汇 |
| OS（消费者） | 解析表枚举硬件，执行 AML 控制方法，主导电源与资源配置 |

### 固件侧：表是怎么交给 OS 的

核心接口是 `InstallConfigurationTable`，展开如下：

1. 固件在内存构建好 RSDT/XSDT、FADT、DSDT、SSDT 等表，校验 Checksum
2. `MdeModulePkg/Universal/Acpi/AcpiTableDxe` 提供 **`EFI_ACPI_TABLE_PROTOCOL`**，其 `InstallAcpiTable()` 把一张表拷贝进内部链表、插到 RSDT/XSDT 末尾、重新计算校验和
3. `AcpiTableDxe` 发布完成后调用 `gBS->InstallConfigurationTable(&gEfiAcpiTableGuid, Rsdp)`，把 **RSDP 的物理地址**挂到 **EFI System Table 的 Configuration Table 数组**
4. OS 加载器（Windows bootmgfw / Linux efi stub）直接读 EFI System Table → Configuration Table → `gEfiAcpiTableGuid` 拿到 RSDP。这与 legacy BIOS 时代从 EBDA 扫描 "RSD PTR " 签名不同

> 开源 EDK II 里各平台有自己的 `AcpiPlatformDxe`（如 OvmfPkg、Silicon/.../AcpiPlatformDxe），负责静态表（编译期 ASL→AML）和动态表（运行时按 CPU 拓扑/内存布局生成 MADT、SRAT、PPTT 等）的安装。AMI Aptio V 思路一致：构建期出 DSDT/SSDT 模板，DXE 期 `InstallAcpiTable` 发布。

ACPI 表的内存类型：
- `EfiACPIReclaimMemory`：OS 引导完成后可回收
- `EfiACPIMemoryNVS`：必须保留，供 S3 唤醒恢复/固件后续使用（如 FACS）

## 三、ACPI 整体架构：五大模块

"表 / 命名空间 / 控制方法 / 电源管理 / 系统配置"的依赖关系：

```
RSDP（入口）
  └─ XSDT/RSDT（目录）
       ├─ FADT（固定寄存器 + DSDT 指针 + FACS 指针）
       ├─ DSDT（主定义块，命名空间骨架 + AML 方法）
       ├─ SSDT（补充定义块，可多个，热插拔/差异化）
       └─ 其他子表（MADT / MCFG / HPET / FACS / BGRT ...）
              ↓ OS 解析这些表
        命名空间（树，_SB/_PR/_TZ/_GPE...）
              ↓ OS 遍历树、调用方法
        控制方法（_STA/_CRS/_INI/_Sx/_PRW...）→ 电源管理 / 资源配置
```

## 四、ACPI 表层次结构

### 表发现链路

| 表 | 签名 | 作用 |
| --- | --- | --- |
| RSDP | `RSD PTR ` | 根指针，固定结构。含 `XsdtAddress`（64 位）与 `RsdtAddress`（32 位兼容）。UEFI 下 OS 从 Configuration Table 取它，不必内存扫描 |
| RSDT | `RSDT` | 32 位指针数组（legacy），指向各子表 |
| XSDT | `XSDT` | 64 位指针数组，现代系统用这个；本质是"索引目录" |
| FADT | `FACP` | **固定 ACPI 描述表**，桥梁：指向 DSDT、FACS，声明全部电源硬件寄存器块地址 |
| DSDT | `DSDT` | 差异化系统描述表，核心定义块，含命名空间骨架与大部分 AML 控制方法 |
| SSDT | `SSDT` | 辅助系统描述表，可多个，用于补设备/热插拔/OEM 差异化 |

> [!warning]
> 常见误区"RSDP → XSDT → DSDT/SSDT"跳过了 FADT。实际顺序是 **RSDP → XSDT → FADT → DSDT**；OS 必须先读 FADT 才能拿到 DSDT 指针和那些 PM 寄存器地址。

### FADT 关键字段

**1. 指向其他表的指针**：`DSDT`/`X_Dsdt`（DSDT 物理地址）、`FirmwareCtrl`/`X_FirmwareCtrl`（FACS 地址，S3 唤醒时固件写唤醒矢量用）

**2. 固定硬件寄存器块地址（GAS）**

| 寄存器块 | 用途 |
| --- | --- |
| `PM1a_EVT_BLK` | PM1a 事件寄存器（状态/使能，SCI 事件源） |
| `PM1a_CNT_BLK` | PM1a 控制寄存器（含 SLP_TYP / SLP_EN，发起睡眠/关机） |
| `PM_TMR_BLK` | ACPI 电源管理定时器 |
| `GPE0_BLK` | 通用事件（GPE）寄存器，GPIO/唤醒事件 |
| `ResetReg` / `ResetValue` | ACPI 2.0+ 硬件复位寄存器（与 Runtime Services 的 ResetSystem 同源） |

还有 `SCI_INT`（SCI 中断号）、`SMI_CMD` + `ACPI_ENABLE`/`ACPI_DISABLE`（切 ACPI 模式用）。

### 其他常见子表

| 表 | 签名 | 作用 |
| --- | --- | --- |
| MADT | `APIC` | 中断控制器拓扑（Local APIC / I/O APIC / x2APIC） |
| MCFG | `MCFG` | PCIe 配置空间 MMIO 基址（ECAM） |
| HPET | `HPET` | 高精度事件定时器 |
| FACS | `FACS` | 固件控制结构，S3 唤醒矢量存放处，必须 NVS |
| BGRT | `BGRT` | 启动画面（OEM Logo）位置 |
| SRAT | `SRAT` | 内存/CPU 的 NUMA 亲和性 |
| DMAR | `DMAR` | VT-d DMA 重映射（IOMMU） |
| BERT | `BERT` | 启动错误记录 |

## 五、ACPI 命名空间

命名空间是由 AML 构建的树状结构，相当于硬件的"目录"。所有 ACPI 对象（设备、方法、变量）都挂在这棵树下。

### 四大根节点

| 根 | 含义 |
| --- | --- |
| `_SB` (System Bus) | 系统总线，绝大多数外设挂在下面 |
| `_PR` (Processor) | 处理器，CPU 拓扑、P/C 状态控制 |
| `_TZ` (Thermal Zone) | 热区，温度传感器、风扇策略、过热保护 |
| `_GPE` (General Purpose Event) | 通用事件，ACPI 唤醒 / GPIO 中断分发 |

### 命名规则

- 对象名固定 **4 个 ASCII 字符**
- 首字符必须是字母（A–Z）或下划线（`_`）
- 下划线开头是 ACPI 规范保留的标准名（`_SB`、`_STA`、`_CRS`），自定义设备不要冲突
- 常用对象名：`_HID`（硬件 ID）、`_UID`（唯一 ID）、`_ADR`（地址）、`_CID`（兼容 ID）

### 设备状态方法 `_STA`

`_STA` 返回设备状态位图，OS 据此决定是否枚举、初始化、显示该设备：

| Bit | 含义 |
| --- | --- |
| 0 | 设备存在（Present） |
| 1 | 已启用且正在译码资源 |
| 2 | 应在 UI 中显示 |
| 3 | 工作正常 |
| 4 | 电池存在（仅控制方法电池设备） |

`Return (0x0F)` 即 bit0–3 全 1 = 存在且完全启用；`0x0B`（1011）= 不译码资源（常见半启用状态）。

## 六、控制方法：ASL 与 AML

两个语言层级：
- **ASL（ACPI Source Language）**：类 C 源语言，固件工程师手写，描述设备枚举、电源切换、资源分配逻辑
- **AML（ACPI Machine Language）**：ASL 编译出的字节码，OS 自带 **AML 解释器**（Linux/Windows 都用 ACPICA）解释执行

> 为什么是字节码而非直接调用固件函数？为了跨 OS 兼容：同一份 AML，Windows 和 Linux 各自的解释器都能跑。ACPI 方法运行在 OS 的 AML 虚拟机里，不是在固件里执行。

### 常用标准方法

| 方法 | 作用 |
| --- | --- |
| `_STA` | 设备状态 |
| `_CRS` | 当前资源（Current Resource Settings） |
| `_PRS` | 可用资源（Possible Resource Settings） |
| `_SRS` | 设置资源（Set Resource Settings） |
| `_INI` | 设备/命名空间初始化 |
| `_HID` / `_UID` / `_CID` / `_ADR` | 设备标识 |
| `_S0`/`_S1`/`_S3`/`_S4`/`_S5` | 系统睡眠状态定义 |
| `_PRW` | 唤醒能力 |
| `_DSM` | 设备特定方法（厂商扩展） |
| `_OSI` | 查询当前 OS（OS 差异化分支） |

## 七、电源管理状态体系

四个层级：

| 状态族 | 作用域 | 典型成员 |
| --- | --- | --- |
| G（Global） | 整机生命周期 | G0 工作 / G1 睡眠 / G2 软关机 / G3 机械断电 |
| S（Sleep） | 系统级休眠 | S0 全速 / S1~S3 睡眠 / S4 休眠（挂起到盘）/ S5 软关机 |
| D（Device） | 单设备功耗 | D0 工作 → D3 断电 |
| C/P/T | CPU 专属 | C 空闲态 / P 性能档 / T 热节流 |

### S3 深度睡眠

仅保留内存供电（Self-Refresh），其余硬件断电，唤醒毫秒级。唤醒矢量由固件在 S3 进入前写入 **FACS**，OS 触发 `PM1a_CNT_BLK` 的 `SLP_TYP=S3` + `SLP_EN`，固件（含 SMM）接管恢复。

### SCI 与 SMI（关键区别）

- **SCI（System Control Interrupt）**：ACPI 模式下由硬件事件（按键、开盖、温度越限）触发的中断，**由 OS 的 ACPI 驱动处理**，是 OS 进入 ACPI 世界的入口
- **SMI（System Management Interrupt）**：进 SMM（固件特权级）的中断，OS 看不见，由固件处理，常见于老式电源/legacy 兼容

固件通过往 `SMI_CMD` 端口写 `ACPI_ENABLE` 值，让硬件把事件从 SMI 模式切到 SCI 模式（置 `SCI_EN`），完成"ACPI 使能"。改 FADT 的 `SCI_INT`/`SMI_CMD` 字段直接影响系统能否正常睡眠唤醒。

## 八、资源分配与即插即用（PnP）

ACPI 的资源分配机制是 PnP 的底层：避免 I/O 端口、MMIO 地址、IRQ 冲突。三步：

1. **资源探测**：OS 调设备的 `_PRS`，拿到可用资源范围列表
2. **冲突仲裁**：OS 全局统筹，算出无冲突分配方案
3. **配置生效与验证**：OS 调 `_SRS` 写回配置，再调 `_CRS` 读回验证

> 资源配置的主动权完全在 OS：固件只提供 `_PRS` 的范围和方法，具体怎么分是 OS 定的。

## 九、ASL 代码实例与编译

LED 设备的 SSDT 示例：

```asl
DefinitionBlock ("", "SSDT", 2, "OEMID", "LED001", 0x00000001) {
  Device (LED0) {                    // 声明名为 LED0 的设备对象，挂到命名空间
    Name (_HID, "ACME0001");         // 硬件唯一标识，OS 据它匹配驱动
    Method (_STA) { Return (0x0F); } // 状态：存在/启用/显示/正常（bit0-3）
    Method (_CRS) {                  // 声明占用的资源（内存映射）
      Name (BUF, ResourceTemplate() {
        Memory32Fixed (ReadWrite, 0xFEDC1000, 0x100)
      })
      Return (BUF);
    }
    OperationRegion (REG, SystemMemory, 0xFEDC1000, 0x100); // 映射硬件寄存器
    Field (REG, ByteAcc, NoLock) { LED_CTRL, 8 }            // 定义寄存器位域：8 位控制字段
  }
}
```

- `DefinitionBlock` 参数：表名、签名（SSDT）、修订、OEMID、OEM Table ID、OEM 修订
- `OperationRegion` + `Field`：把一段物理地址映射成可访问的寄存器/位域——和 MCU 里 `#define REG (*(volatile uint32_t*)0xFEDC1000)` 意图一致，只是声明式写法
- 编译进固件后，OS 解析时把 `LED0` 挂到 `_SB` 下，提供 `_HID`，OS 加载对应驱动即可控制 LED

### 编译工具链

- **iASL**（ACPICA 提供）：`iasl -p led led.asl` 编译出 `led.aml`；`iasl -d table.dat` 反汇编已有表（调试利器）
- 编译出的 AML 作为二进制编进固件 FV（或运行时通过 `InstallAcpiTable` 安装）

## 十、调试工具

| 工具 | 平台 | 用途 |
| --- | --- | --- |
| RWEverything（RW.exe） | Windows | 读 ACPI 表、MMIO、IO、PCI，最直观 |
| HE（Hardware Engineer） | AMI 内部 | 同 RW，可直接看 ACPI Table |
| RU.efi | UEFI Shell | Shell 里的硬件查看器，可看 ACPI 结构 |
| `acpidump` + `iasl -d` | Linux | 导出全部表并反汇编成 ASL 文本 |
| `acpiexec` | ACPICA | AML 解释器模拟执行，单测控制方法 |
| Chipsec | Linux/Win | 安全审计，含 ACPI 表检查 |

## 十一、横向对比：ACPI / SMBIOS / Device Tree

| 机制 | 内容性质 | 谁生成 | OS 怎么用 |
| --- | --- | --- | --- |
| ACPI | 操作接口（表 + 可执行 AML 方法） | 固件（DXE 期） | 解析 + 执行方法，主导电源/资源配置 |
| SMBIOS | 静态描述（型号、序列号、插槽） | 固件 | 只读展示（smbiosview / dmidecode） |
| Device Tree（DT） | 硬件拓扑描述（类 ACPI 表，但无 AML） | 固件/引导器（嵌入式 ARM） | OS 解析后驱动匹配 |

## 术语表

- **ACPI**：高级配置与电源接口，固件↔OS 的硬件描述与电源管理工业标准
- **OSPM**：OS-directed Power Management，OS 主导的电源管理，ACPI 核心理念
- **RSDP**：根系统描述指针，ACPI 表发现的全局入口；UEFI 下经 Configuration Table 暴露
- **FADT（FACP）**：固定 ACPI 描述表，指向 DSDT/FACS，声明全部电源硬件寄存器块地址
- **DSDT / SSDT**：主/辅助系统描述表，含命名空间骨架与 AML 控制方法
- **AML**：ACPI Machine Language，ASL 编译出的字节码，由 OS 的 AML 解释器执行
- **SCI / SMI**：系统控制中断（OS 可见、ACPI 模式）/ 系统管理中断（进 SMM、OS 不可见）
- **GAS**：Generic Address Structure，描述寄存器位置的通用结构
- **FACS**：固件 ACPI 控制结构，S3 唤醒矢量存放处，必须保留在 NVS 内存
- **iASL**：ACPICA 提供的 ASL 编译器/反编译器
- **EfiACPIMemoryNVS**：表分配的内存类型之一，OS 不得释放，供 S3 恢复/固件使用
