# AMI SDL 与 LibraryMapping

## 一、为什么会有 AMI SDL

手写 DSC / FDF 可行，但一个真实 AMI 平台（Aptio V）动辄几千个模块、几百个库映射、上千个 PCD，全靠人手维护 INI 文件容易错也难复用。AMI 的解法是再抽象一层：

- **SDL（Source Definition Language）**：AMI 定义的平台描述语言，声明式描述"这个项目有哪些组件、组件之间怎么映射"
- **AMISDL 工具**：构建时读取所有 `.sdl` 文件，自动生成符合 EDK II 规范的 DSC 和 FDF
- **EDK II Build**：拿生成的 DSC/FDF 走标准 BaseTools 流程，产出 FD 镜像

```
SDL 文件（.sdl）
    │  AMISDL 工具
    ▼
DSC / FDF（自动生成）
    │  EDK II BaseTools
    ▼
FD 固件镜像
```

> 一句话理解：SDL 是"配置的来源"，DSC/FDF 是"构建的输入"。开发者只声明意图，AMISDL 负责翻译成 EDK II 能吃的配置文件。

### AMI SDL 的核心对象（Project Objects）

| SDL 对象 | 作用 | 对应的 EDK II 概念 |
| ---------------- | ------------------------- | ------------------------------------------------ |
| `INFComponent` | 声明一个 INF 模块的存在（名字、路径、所属包） | 就是那个 `.inf` 模块本身 |
| `LibraryMapping` | 库类 → 库实例的映射（本课重点） | DSC 的 `[LibraryClasses]` 段 |
| `PCDMapping` | PCD 配置映射 | DSC 的 `[Pcds*]` 各节 |
| `ELINK` | 依赖关系、构建选项、链接顺序等 | DSC 的 `[BuildOptions]`、`[Components]` 顺序、Depex 等 |

> `ELINK` 很重要：AMI 用它注入像 `PcdLib` 依赖、库构造顺序、特定模块执行顺序等构建编排细节。

## 二、LibraryMapping 核心概念

`LibraryMapping` 干一件事：**把一个 EDK II 库类（Library Class）绑定到某个具体的库实例（Library Instance）**，最终被 AMISDL 翻译成 DSC 的 `[LibraryClasses]` 段。

- **库类 = 接口**：只在 `.h` 里声明函数原型，自己不编译成代码（如 `DebugLib.h` 声明 `DebugPrint()`）
- **库实例 = 实现**：真正写函数的模块，有自己的 `.c` 和 `.inf`
- **同一个库类可以有多个实例**：`DebugLib` 有 `BaseDebugLibNull`（空实现）、`BaseDebugLibSerialPort`（打串口）等
- `LibraryMapping` 就是"选一个"的声明

> [!key] 关键对应关系
> - `LibraryMapping` 的 **Class** 字段 = INF 文件里 `LIBRARY_CLASS` 的值
> - `LibraryMapping` 的 **Instance** 字段 = 某个 `INFComponent` 的 `Name`，以 `PackageName.InfName` 格式引用
> - 这条映射最终生成 DSC `[LibraryClasses]` 段里的一行 `Class|Instance.inf路径`

### 为什么需要它

EDK II 里很多库类都有多种实现，不同执行阶段挂不同实现（PEI 用轻量版，DXE 用完整版）。`LibraryMapping` 统一指定默认实现，又允许按架构/模块类型/特定模块覆盖——即"接口不变、实现可换"的依赖注入思想，只是换成 SDL 语法。

## 三、字段详解

| 字段 | 必需 | 类型 | 说明 | 示例 |
| ------------- | --- | ------ | ----------------------------- | --------------------------------- |
| `Class` | ✓ | String | 库类名称，对应 INF 的 `LIBRARY_CLASS` | `"DebugLib"`、`"BaseLib"`、`"NULL"` |
| `Instance` | ✓ | Ref | 库实例引用：`PackageName.InfName` | `"MdePkg.BaseDebugLibSerialPort"` |
| `Arch` | — | String | 限定架构（空格分隔） | `"IA32 X64"` |
| `Module_Type` | — | String | 限定模块类型（空格分隔） | `"DXE_DRIVER"`、`"DXE_SMM_DRIVER"` |
| `Override` | — | Ref | 仅对特定模块生效的覆盖 | `"MdeModulePkg.CapsuleX64"` |
| `Token` | — | Expr | 条件表达式（可多个，AND 关系） | `"FSP_WRAPPER_ENABLE" "=" "1"` |
| `Flag` | — | Int32 | 位域：Bit3=Active，Bit8=Lock | `Disable = Yes` / `Lock = Yes` |
| `Help` | — | Text | 描述说明 | `"Maps DebugLib to serial port"` |

### 特殊值：`Class = "NULL"`

- NULL 表示"无条件注入"的库实例——它不满足任何库类依赖，而是直接被链接进目标模块
- 常用于注入压缩库、栈检查库、安全桩库等"横切"功能
- 通常配合 `Override` 指定目标模块，或配合 `Module_Type` 指定作用范围

> [!warning] NULL 不是"空实现"
> `Class="NULL"` 是 EDK II 里的一种特殊聚合机制：一个模块可以链接任意多个 NULL 库，而具名库类（如 `DebugLib`）在一个模块里只能选一个实例。NULL 库靠自己的构造函数（CONSTRUCTOR）在模块加载时"挂"上行为。

### Flag 位域

- **Bit3 — Active 标志**：默认置位表示激活。`Disable = Yes` 等价于清掉这一位，禁用该映射
- **Bit8 — Lock 标志**：`Lock = Yes` 锁定映射，子包/后续 SDL 不能修改它
- `Disable` 常见用途：**子包用 `Disable=Yes` 撤销父包已建立的映射**，再建立自己的

## 四、基本用法与示例

### 示例 1：最简单映射

```text
LibraryMapping
    Class    = "BaseLib"
    Instance = "MdePkg.BaseLib"
End
```

### 示例 2：配合 INFComponent 使用

```text
# Step 1: 先声明库的 INF 组件
INFComponent
    Name    = "BaseXApicX2ApicLib"
    File    = "Library/BaseXApicX2ApicLib.inf"
    Package = "UefiCpuPkg"
End

# Step 2: 建立映射关系
LibraryMapping
    Class    = "LocalApicLib"
    Instance = "UefiCpuPkg.BaseXApicX2ApicLib"
End
```

### 映射规则

- `Class` = INF 文件里 `LIBRARY_CLASS` 的值
- `Instance` = `PackageName.InfComponentName`
- 一个 `Class` 可映射多个 `Instance`，靠条件（`Arch`/`Module_Type`/`Override`/`Token`）区分
- 不带任何条件的映射就是全局默认值

> [!tip] 命名一致性是头号坑
> `Instance` 里的 `PackageName` 必须和对应 `INFComponent` 的 `Package` 字段一字不差；`InfComponentName` 必须和 `INFComponent` 的 `Name` 字段一字不差。拼错一个字母，构建就报"找不到实例"。

### 生成的 DSC 输出

- 输出到 `[LibraryClasses]` 段，格式：`Class|Instance.inf路径`
- 只有 **Active 且未被 Disable** 的映射才会输出
- 定义了 `Override` 的映射不进 `[LibraryClasses]`，而是进 `[Components]` 里对应模块的 `<LibraryClasses>` 作用域

## 五、高级用法

### 1. Arch / Module_Type 条件筛选

```text
# 同一个 Class 按模块类型映射不同实例
LibraryMapping
    Class       = "CpuExceptionHandlerLib"
    Instance    = "UefiCpuPkg.DxeCpuExceptionHandlerLib"
    Arch        = "IA32 X64"
    Module_Type = "DXE_CORE DXE_DRIVER UEFI_APPLICATION"
End

LibraryMapping
    Class       = "CpuExceptionHandlerLib"
    Instance    = "UefiCpuPkg.SecPeiCpuExceptionHandlerLib"
    Arch        = "IA32 X64"
    Module_Type = "PEI_CORE PEIM SEC"
End
```

### 2. Override 针对特定模块覆盖

```text
# 仅对 CapsuleX64 这一个模块覆盖 DebugLib
LibraryMapping
    Class    = "DebugLib"
    Instance = "MdePkg.BaseDebugLibSerialPort"
    Override = "MdeModulePkg.CapsuleX64"
End
```

### 3. Class = "NULL" 无条件注入

```text
# 把 LZMA 解压库注入 DxeIpl 模块
LibraryMapping
    Class    = "NULL"
    Instance = "MdeModulePkg.LzmaCustomDecompressLib"
    Override = "MdeModulePkg.DxeIpl"
    Token    = "LZMA_SUPPORT" "=" "1"
End
```

### 4. Token 条件控制

```text
# 仅在 FSP 模式下注入特定平台库
LibraryMapping
    Class    = "NULL"
    Instance = "ClientOneSiliconPkg.PeiReadyToBootLib"
    Override = "UefiCpuPkg.CpuMpPei"
    Token    = "AMI_FSP_BIN_SUPPORT" "=" "1"
End
```

### 筛选优先级与逻辑

- **优先级：`Override` > `Module_Type` > `Arch` > 全局**。越具体的条件越先生效
- **Token 逻辑**：多个 Token 条件是 AND 关系，全部满足才输出这条映射
- **Disable 用法**：子包撤销父包已建立的映射，再建立自己的版本

> 这个优先级精确对应 EDK II 构建规范里"库实例解析优先级"。

## 六、与 INFComponent 的关系

`INFComponent` 和 `LibraryMapping` 是引用关系，不是包含关系：

- **INFComponent（声明）**：`Name` 匹配 INF 文件名；`File` 是相对路径；`Package` 是所属 EDK II 包。一个 `INFComponent` 可被多个 `LibraryMapping` 引用
- **LibraryMapping（引用）**：`Instance` 引用"被链接的库实例"的 `INFComponent`；`Override` 引用"被覆盖的目标模块"的 `INFComponent`。两者都是 `PackageName.InfComponentName` 格式，都必须在同一 SDL 项目里定义

⚠️ 规则重申：`Instance` 和 `Override` 的值必须是 `PackageName.InfComponentName`，Package 对 `INFComponent.Package`，Name 对 `INFComponent.Name`。

## 七、DSC 文件生成流程

### OUTPUTREGISTER：声明输出文件

SDL 不直接知道"DSC 该生成到哪、叫什么名"，靠 `OUTPUTREGISTER` 注册：

```text
OUTPUTREGISTER
    Name = "PLATFORM_DSC"
    Path = "Build"
    File = "MyPlatform.DSC"
END
```

### 生成规则

- Active 且未 Disable 的映射 → 输出到 `[LibraryClasses]`
- 按 `Arch` + `Module_Type` 分组输出到不同段
- 带 `Override` 的映射 → **不进** `[LibraryClasses]`，而是写进 `[Components]` 段里对应模块的 `<LibraryClasses>` 作用域
- `Token` 条件在构建时动态求值，不满足的映射不输出

### DSC 段分组示例

```ini
[LibraryClasses]                      ; 全局默认
[LibraryClasses.common.DXE_DRIVER]   ; 按模块类型
[LibraryClasses.IA32]                ; 按架构
[LibraryClasses.X64.PEIM]            ; 架构 + 模块类型

[Components]
  MdeModulePkg/Universal/Capsule/RuntimeDxe/CapsuleX64.inf {
    <LibraryClasses>                 ; Override 映射落在这里
      DebugLib|MdePkg/Library/BaseDebugLibSerialPort/BaseDebugLibSerialPort.inf
  }
```

## 八、EDK II 底层机制

### 8.1 库实例解析的官方优先级

EDK II 构建规范规定，对每个模块，工具按**从高到低**的优先级为每个具名库类选一个实例（NULL 库类除外，可链多个）：

1. **DSC 中组件级作用域**——`[Components]` 里 `Module.inf { <LibraryClasses> ... }`（对应 SDL `Override`）
2. **`[LibraryClasses.Arch.ModuleType]`**——同时带架构和模块类型（对应 SDL 同时指定 `Arch` + `Module_Type`）
3. **`[LibraryClasses.common.ModuleType]`**——仅带模块类型（对应 SDL 仅 `Module_Type`）
4. **`[LibraryClasses.Arch]`**——仅带架构（对应 SDL 仅 `Arch`）
5. **`[LibraryClasses]`**——common 全局（对应 SDL 无条件全局映射）

> `Override > Module_Type > Arch > 全局` 不是 AMI 方言，就是上面第 1～5 级的翻版。SDL 把"段名"换成"字段"，AMISDL 生成 DSC 时再还原成对应段。

### 8.2 NULL 库类的聚合模式

具名库类在一个模块里只能选一个实现；**NULL 库类是个例外——一个模块可以无条件链接任意多个 NULL 库**：

- DSC 里写 `NULL|MdePkg/Library/BaseStackCheckLib/...inf`，构建工具直接把库链进模块，不管模块 INF 有没有声明消费它
- NULL 库靠自己的 `CONSTRUCTOR` 函数在模块加载时被调用，从而"挂"上功能（栈保护 cookie、安全校验桩等）

edk2 源码例子（`MdeLibs.dsc.inc`）：

```ini
[LibraryClasses.common.PEIM]
  NULL|MdePkg/Library/BaseStackCheckLib/BaseStackCheckLib.inf
```

### 8.3 库构造函数与执行时机

库实例可在 INF 里声明 `CONSTRUCTOR`：

```ini
[Defines]
  LIBRARY_CLASS = UefiBootServicesTableLib|DXE_CORE DXE_DRIVER ...
  CONSTRUCTOR   = UefiBootServicesTableLibConstructor
```

构建时，工具在 `AutoGen.c` 里自动生成 `ProcessLibraryConstructorList()` 函数，按依赖关系排好序，在模块的"标准入口包装函数"里、真正的入口点**之前**依次调用所有构造函数。所以模块第一行代码就能直接用 `gBS`、`gST`。

### 8.4 DSC 段的完整语法小结

| SDL 写法 | 生成的 DSC 段 |
| --- | --- |
| 无条件全局 | `[LibraryClasses]` |
| `Arch = "X64"` | `[LibraryClasses.X64]` |
| `Module_Type = "PEIM"` | `[LibraryClasses.common.PEIM]` |
| `Arch="X64" Module_Type="DXE_DRIVER"` | `[LibraryClasses.X64.DXE_DRIVER]` |
| `Override = "Pkg.Module"` | `[Components]` 内 `Module.inf { <LibraryClasses> }` |

## 九、实战案例分析

### 案例 1：栈溢出检查库注入（全局 NULL）

```text
# MdePkg.sdl — 全局 NULL 注入
LibraryMapping
    Class       = "NULL"
    Instance    = "MdePkg.BaseStackCheckLib"
    Module_Type = "PEI_CORE PEIM DXE_CORE DXE_DRIVER ..."
    Token       = "STACK_OVERFLOW_CHECK" "=" "1"
End
```

场景：为所有模块启用栈溢出检测。`Class=NULL` 无条件注入不改任何模块 INF；`Module_Type` 列出目标阶段；`Token` 控制开关；配合构造函数在每个模块加载时埋入栈 cookie 检查。

### 案例 2：FSP 模式下的多阶段平台库映射

```text
LibraryMapping
    Class    = "FspSecPlatformLib"
    Instance = "ClientOneSiliconPkg.FspMPlatformSecLib"
    Override = "IntelFsp2Pkg.Fsp24SecCoreM"
    Token    = "AMI_FSP_BIN_SUPPORT" "=" "1"
End
```

场景：FSP 的 T/M/S 多阶段使用不同平台库。同一 `Class` 映射不同 `Instance`，`Override` 精确到每个 FSP SecCore 模块，`Token` 确保仅在 FSP 模式激活。

### 常见排错技巧

- 检查 `Instance` 里的 `PackageName` 拼写，必须与 `INFComponent.Package` 完全一致
- 确认 `INFComponent` 的 `Name`/`Package` 与引用一致
- 看 `Build/*.log` 里的 LibraryMapping 报错信息
- 怀疑映射冲突时，用 `Disable=Yes` 临时关掉父包的映射验证

> [!warning]
> 1. **"No library instance found"**：DSC 里某个库类没映射。SDL 侧漏写 `LibraryMapping`，或 `Token` 条件没满足导致映射没输出
> 2. **"多个实例冲突/选错实现"**：按 `Override > Module_Type > Arch > 全局` 逐级排查

## 十、SDL 与手写 DSC 的取舍

| 维度 | 手写 DSC | AMI SDL + AMISDL |
| --- | --- | --- |
| 维护方式 | 直接改 INI 文本 | 改声明式 SDL 对象 |
| 复用性 | 平台间难复用 | 子包继承/覆盖父包映射 |
| 出错概率 | 段名、路径、分隔符易错 | 工具生成，格式统一 |
| 可读性 | 几千行平铺 | 按对象语义组织 |
| 调试 | 直接看 DSC | 需理解"SDL → DSC"翻译 |

> 实际项目里两者并存：AMI 平台用 SDL 管理主配置，但 SDL 最终生成 DSC 给人看、给人 debug。两手都要会：读懂生成的 DSC，也能从 DSC 段名反推 SDL 怎么写。
