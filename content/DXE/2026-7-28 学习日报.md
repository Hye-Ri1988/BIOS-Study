# DXE

## Protocol 和 PPI 的关键差异

| | PPI（PEI 阶段） | Protocol（DXE 阶段） |
|---|---|---|
| 数据库 | PEI PPI 数据库，PEI 结束释放 | Handle 数据库，整个 DXE 期间存活 |
| 安装 | PeiServicesInstallPpi | gBS->InstallMultipleProtocolInterfaces |
| 查找 | PeiServicesLocatePpi | gBS->LocateProtocol |
| Handle | 无 | 有，安装时创建，查找时用不到 |
| INF 段 | [Guids] 或 [Ppis] | [Protocols] |
| .dec 段 | [Guids] 或 [Ppis] | [Protocols] |
| 用到的库 | PeiServicesLib | UefiDriverEntryPoint、直接用 gBS |

核心区别只有两个：操作接口从 PeiServices 换成 BootServices（gBS），多了 Handle 这个概念。其余结构体定义、GUID 使用、Depex 机制完全一样。

## 整体架构

```
CmosDxe.h（共享头文件：GUID + 接口结构体）
     │
     ├── CmosDxe.c / CmosDxe.inf     ← 生产者：InstallProtocol
     │
     └── MyDxeDriver.c / MyDxeDriver.inf（修改已有文件）  ← 消费者：LocateProtocol → ReadCmos
```

## 文件 1：CmosDxe.h — 共享头文件

定义 Protocol 的 GUID 和接口结构体。生产者和消费者都 include 它，保证两边看到的 GUID 和函数签名完全一致。

```c
#ifndef __CMOS_PROTOCOL_H__
#define __CMOS_PROTOCOL_H__

#define CMOS_PROTOCOL_GUID \
  { \
    0xA1B2C3D4, 0x5E6F, 0x7890, \
    { 0xAB, 0xCD, 0xEF, 0x01, 0x23, 0x45, 0x67, 0x89 } \
  }

extern EFI_GUID  gCmosProtocolGuid;

#define CMOS_PROTOCOL_REVISION  0x00010000

typedef struct _CMOS_PROTOCOL {
  UINTN       Revision;
  EFI_STATUS  (EFIAPI *ReadCmos) (IN UINT8 Address, OUT UINT8 *Value);
  EFI_STATUS  (EFIAPI *WriteCmos)(IN UINT8 Address, IN  UINT8 Value);
} CMOS_PROTOCOL;

#endif
```

设计要点：
- GUID 用 macro 封装花括号列表（128 位常量标准做法）
- 结构体里 Revision 固定为第一个字段（Protocol 惯例）——以后加新函数指针时改版本号，调用方按版本号判断哪些函数可用
- GUID 变量 extern 声明放头文件，实际定义写在生产者 .c。定义在头文件里的话每个 include 它的 .c 都生成一份，链接报重复符号

## 文件 2：CmosDxe.c — 生产者实现

做三件事：定义 GUID 变量实例、实现 CMOS 读写函数、在入口点安装 Protocol。

```c
#include <Uefi.h>
#include <Library/UefiDriverEntryPoint.h>
#include <Library/DebugLib.h>
#include <Library/IoLib.h>
#include "CmosDxe.h"

EFI_GUID  gCmosProtocolGuid = CMOS_PROTOCOL_GUID;

EFI_STATUS
EFIAPI
CmosRead (
  IN  UINT8  Address,
  OUT UINT8  *Value
  )
{
  if (Value == NULL) {
    return EFI_INVALID_PARAMETER;
  }
  IoWrite8 (0x70, Address);
  *Value = IoRead8 (0x71);
  return EFI_SUCCESS;
}

EFI_STATUS
EFIAPI
CmosWrite (
  IN UINT8  Address,
  IN UINT8  Value
  )
{
  IoWrite8 (0x70, Address);
  IoWrite8 (0x71, Value);
  return EFI_SUCCESS;
}

CMOS_PROTOCOL  gCmosProtocol = {
  CMOS_PROTOCOL_REVISION,
  CmosRead,
  CmosWrite
};

EFI_STATUS
EFIAPI
CmosDxeEntryPoint (
  IN EFI_HANDLE        ImageHandle,
  IN EFI_SYSTEM_TABLE  *SystemTable
  )
{
  EFI_STATUS  Status;
  EFI_HANDLE  Handle;

  Handle = NULL;

  Status = SystemTable->BootServices->InstallMultipleProtocolInterfaces (
                                         &Handle,
                                         &gCmosProtocolGuid,
                                         &gCmosProtocol,
                                         NULL
                                         );

  DEBUG ((DEBUG_INFO, "[CmosDxe] InstallProtocol Status = %r\n", Status));

  return Status;
}
```

关键设计决定：
- CMOS 读写用 IoLib 的 IoWrite8/IoRead8 访问 IO 端口 0x70/0x71——和 PPI 生产者实现完全一样，只是包装接口从 PPI 换成 Protocol
- ReadCmos 先检查 Value 指针非空再赋值，防止空指针解引用
- Protocol 实例 gCmosProtocol 是全局结构体（版本号 + 两个函数指针），编译期确定，不分配堆内存
- 安装用 InstallMultipleProtocolInterfaces 而非 InstallProtocolInterface——可一次装多个 Protocol 到同一 Handle，最后一个参数固定 NULL 表示列表结束；Handle 传 NULL 让系统自动创建新 Handle
- 入口点签名 `(EFI_HANDLE, EFI_SYSTEM_TABLE*)` 与 PEIM 的 `(FileHandle, PeiServices)` 不同。SystemTable 是 DXE 阶段核心表，BootServices 是它的子表

## 文件 3：CmosDxe.inf — 生产者 build 描述

```inf
[Defines]
    INF_VERSION                    = 0x00010005
    BASE_NAME                      = CmosDxe
    FILE_GUID                      = 5E4D3C2B-1A09-8F7E-6D5C-4B3A2E1D0C9B
    MODULE_TYPE                    = DXE_DRIVER
    VERSION_STRING                 = 1.0
    ENTRY_POINT                    = CmosDxeEntryPoint

[Sources]
    CmosDxe.c
    CmosDxe.h

[Packages]
    MdePkg/MdePkg.dec
    OemJYTianPkg/OemJYTianPkg.dec

[LibraryClasses]
    UefiDriverEntryPoint
    DebugLib
    IoLib

[Protocols]
    gCmosProtocolGuid

[Depex]
    TRUE
```

字段解释：
- MODULE_TYPE 填 DXE_DRIVER——不需要 Runtime 存活、不需要绑定设备，开机执行一次装完 Protocol 就退出的服务提供者
- ENTRY_POINT 必须和 .c 里入口函数名完全一致，否则链接报 unresolved symbol
- [Sources] 同时列 .c 和 .h。头文件不是必须列，但列了 build 系统会在头文件变化时触发重新编译（依赖追踪）
- [Packages] 引用两个 .dec：MdePkg 提供 Uefi.h、IoLib、DebugLib；OemJYTianPkg 提供 CmosDxe.h 的 include 路径
- [LibraryClasses] 三个：UefiDriverEntryPoint（DXE 入口框架）、DebugLib、IoLib。Protocol 的安装/查找直接用 gBS，不需要额外库封装
- [Protocols] 段声明 gCmosProtocolGuid，build 去 .dec 的 [Protocols] 段查值——**不能写在 [Guids] 段，各段对应各段**
- [Depex] 填 TRUE：无运行时依赖，调度器启动后直接执行（生产者不依赖任何 Protocol）

## 文件 4：JYTianProtocolModuel.cif — 模块注册

```xml
<component>
    name = "JYTianProtocolModuel"
    category = ModulePart
    LocalRoot = "OemJYTianPkg/JYTianProtocolModuel/"
    RefName = "JYTianProtocolModuel"
[INF]
"CmosDxe.inf"
[files]
"JYTianProtocolModuel.sdl"
<endcomponent>
```

AMI 的 build 系统通过 .cif 发现模块目录。没有 .cif，SYSTEM 不知道这个目录下有 INF 要编译。name 和 RefName 保持一致，LocalRoot 指向模块目录相对路径。

## 文件 5：JYTianProtocolModuel.sdl — SDL 配置

```sdl
TOKEN
    Name  = "JYTianProtocolModuel_SUPPORT"
    Value  = "1"
    Help  = "Main switch to enable JYTianProtocolModuel support in Project"
    TokenType = Boolean
    TargetMAK = Yes
    Master = Yes
End

TOKEN
    Name  = "CmosDxe_INF_SUPPORT"
    Value  = "1"
    Help  = "Main switch to enable CmosDxe support in Project"
    TokenType = Boolean
End

INFComponent
    Name  = "CmosDxe"
    File  = "CmosDxe.inf"
    Package  = "OemJYTianPkg"
    ModuleTypes  = "DXE_DRIVER"
    Token = "CmosDxe_INF_SUPPORT" "=" "1"
End
```

三个关键字段不能漏：
- **Package 必填**，缺了报 `Mandatory object missing - Package`
- **ModuleTypes 决定模块放进哪个 FV**。DXE_DRIVER 放进 DXE FV，由 DXE 调度器加载。填错类型模块进错 FV、调度器不加载或加载时机不对
- **Token 是条件编译开关**，`CmosDxe_INF_SUPPORT = "1"` 表示无条件编译；改成 `"0"` 整个模块不编译

## 影响包级的 3 个改动

### 改动 1：OemJYTianPkg.cif — 注册子模块

在 parts 段加一行 `"JYTianProtocolModuel"`。不注册则 SDL 不加载该 .cif，模块不参与编译，FV 里没有 CmosDxe，消费者 Depex 永远等不到。

### 改动 2：OemJYTianPkg.dec — 暴露头文件和定义 GUID

- [Includes] 段加 `JYTianProtocolModuel`，让消费者能 `#include <CmosDxe.h>`
- [Protocols] 段新增 Protocol GUID 值定义：

```
[Protocols]
  gCmosProtocolGuid = { 0xA1B2C3D4, 0x5E6F, 0x7890, { 0xAB, 0xCD, 0xEF, 0x01, 0x23, 0x45, 0x67, 0x89 } }
```

> 必须放 [Protocols] 段而非 [Guids] 段：EDK II 查找规则按段名对应——INF 的 [Protocols] 段声明的 GUID，build 去 .dec 同名段查值。放 [Guids] 段报 `Value of Protocol [gCmosProtocolGuid] is not found under [Protocols] section`。

### 改动 3：消费者 MyDxeDriver（复用已有模块）

**MyDxeDriver.c 追加代码**：

```c
#include <CmosDxe.h>   // 新加的 include

// 在入口函数末尾，MyLibHello() 之后，return 之前插入：
{
  EFI_STATUS          Status;
  CMOS_PROTOCOL       *CmosProtocol;
  UINT8               CmosValue;

  Status = SystemTable->BootServices->LocateProtocol (
                                         &gCmosProtocolGuid,
                                         NULL,
                                         (VOID **)&CmosProtocol
                                         );
  if (!EFI_ERROR (Status)) {
    CmosProtocol->ReadCmos (0x0E, &CmosValue);
    DEBUG ((DEBUG_INFO, "[MyDxeDriver] via Protocol: CMOS[0x0E] = 0x%02x\n", CmosValue));
  } else {
    DEBUG ((DEBUG_INFO, "[MyDxeDriver] LocateProtocol FAILED = %r\n", Status));
  }
}
```

LocateProtocol 三参数：第一个是要找的 Protocol GUID，第二个 NULL（不需要 Registration），第三个输出参数，拿到接口指针强转成 CMOS_PROTOCOL 类型调用。

**MyDxeDriver.inf 两处改动**：

```diff
+[Protocols]
+    gCmosProtocolGuid

 [Depex]
-    TRUE
+    gCmosProtocolGuid
```

Depex 从 TRUE 改成 gCmosProtocolGuid 是关键：DXE 调度器在 CmosProtocol 安装之前不执行 MyDxeDriver。维持 TRUE 的话可能在 CmosDxe 之前执行，LocateProtocol 返回 NOT_FOUND。

## Depex 在 DXE 阶段的运行方式

与 PEI 逻辑一样：DXE 调度器每轮扫描检查每个未执行模块的 Depex 是否满足。Depex = TRUE 的最先执行；Depex = gCmosProtocolGuid 的被跳过，直到 CmosDxe 安装该 Protocol。调度器检测到新 Protocol 注册后重新扫描，发现依赖满足即执行。

## 常见报错

| 报错信息 | 原因 | 怎么修 |
|---|---|---|
| `Mandatory object missing - Package` | sdl 的 INFComponent 缺 Package | 补 `Package = "包名"` |
| `Value of Protocol [xxx] is not found under [Protocols]` | GUID 定义在 .dec 的 [Guids] 段 | 在 .dec 补 `[Protocols]` 段 |
| `File/directory not found: xxx.inf` | sdl INFComponent File 和实际文件名不一致 | 对齐三个名字：.inf 文件名、sdl File、cif INF 行 |
| 生产者没执行 | ModuleTypes 写错或没写 | sdl INFComponent 补 `ModuleTypes = "DXE_DRIVER"` |
| LocateProtocol 返回 NOT_FOUND | 消费者比生产者先执行 | 检查消费者 Depex 是否填了正确的 Protocol GUID |
