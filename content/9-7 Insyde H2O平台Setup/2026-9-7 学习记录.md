# Insyde H2O 平台 Setup 最小实践笔记（2026-9-7）

> 记录在 Insyde H2O 平台下，如何用 **5 个文件** 写一个最小可用的 BIOS Setup 页面。
> 

---


| 文件 | 类型 | 角色 | 编译产物 |
|------|------|------|---------|
| `JYTianSetupConfig.h` | 共享头文件 | 定义类型 / 各 ID / 两个 GUID | 被 `.c` 和 `.vfr` 都 include |
| `JYTianSetup.uni` | 字符串包 | 页面上所有**文字**（标题/提示/选项） | `JYTianSetupStrings[]`（字符串包） |
| `JYTianSetup.vfr` | 表单定义 | 页面**结构**（formset/varstore/form/question） | `JYTianSetupFormBin[]`（IFR 二进制） |
| `JYTianSetup.inf` | 模块定义 | 说明这是哪个模块、依赖什么 | 编译链接配置 |
| `JYTianSetup.c` | 驱动源码 | 真正的**逻辑**：读/写变量、注册页面 | 可执行驱动 |

> **图 1 · 五文件编译流水线**：从 5 个源文件到编译产物（字符串包 / IFR 表单包 / DXE 驱动），再到运行时注册进 HII 数据库。



### 数据流全景（先建立整体印象）

```
                    ┌────────────── NVRAM 变量 "JYTianSetupVar"（2 字节, 断电不丢）──────────────┐
                    │                                   ▲                                   │
                    │            GetVariable / SetVariable（读/写 NVRAM，按名字+GUID）         │
                    │                                   │                                   │
   UEFI Form Browser ── EFI_HII_CONFIG_ACCESS_PROTOCOL ──┴── ConfigRouting 协议（翻译器）      │
        (渲染+交互)         │  ExtractConfig(读) / RouteConfig(写)                              │
                    │                                   │                                   │
                    │            BlockToConfig(字节→字符串) / ConfigToBlock(字符串→字节)        │
                    │                                   │                                   │
                    └── 内存镜像 mJYTianSetupConfig（struct，2 字节） ←─────────────┘
                              EnableFlag / DemoMode

  前端(浏览器看到的字符串) ⇄ ConfigRouting ⇄ 后端(mJYTianSetupConfig 字节) ⇄ NVRAM(持久化)
```

## 1. 在理解代码时的一个疑问：

### <font color="#ff0000">既然 `ExtractConfig` 要把字节转成字符串，**为什么一开始不就把配置存成字符串？**</font>

个人理解：

 HII 配置字符串是"接口传输格式"，不是"存储格式"。感觉类似于互联网开发时的数据库与Json格式的关系。数据库里的数据往往先被序列化为JSON再传给后端。

```
GUID=5C8E7A19-2B3D-47F6-8E41-A9D063F27B55&NAME=JYTianSetupVar&PATH=<设备路径>&OFFSET=0&WIDTH=2&VALUE=0100
```

| 对比 | 存 struct（字节） | 存字符串 |
|------|------------------|---------|
| NVRAM 占用 | **2 字节** | 90+ 字节，其中 `VALUE=0100` 只占 4 字符，其余全是重复的标识元数据 |
| 代码读/写 | `mJYTianSetupConfig.EnableFlag = 1;` 直接操作一个字节 | 每次都要解析十六进制、按 Offset/Width 抠出来再转换 |
| 类型安全 | `UINT8 EnableFlag` 有类型、有约束 | 纯文本，无类型，极易损坏 |
| UEFI 变量 API | `GetVariable/SetVariable` 本身就收 `VOID*` 原始字节 | 得把字符串再转回字节才能用，多绕一圈 |
| 可派生性 | 字节是源头真相，字符串随时能生成 | 字符串是冗余、还可能和实际字节不一致 |

**结论**：内部存字节（struct），只在浏览器索要时才用 `BlockToConfig` 生成字符串。`ExtractConfig`/`RouteConfig` 就是这个"字节 ⇄ 字符串"的边界转换。这正如"数据库存结构化行数据，只在 API 响应时序列化成 JSON"。

## 2. `JYTianSetupConfig.h` —— 共享定义

三个角色：定类型、定 ID、定两个 GUID。

```c
#include <Uefi.h>

// 两个 GUID：一个是"页面表单集"，一个是"变量命名空间"，必须不同
#define JY_TIAN_SETUP_FORMSET_GUID \
  { 0x6A2D5C31, 0x9F48, 0x4B7E, { 0xA5, 0x2D, 0x3E, 0x8B, 0x7C, 0x91, 0x40, 0x6F } }
#define JY_TIAN_SETUP_VARSTORE_GUID \
  { 0x5C8E7A19, 0x2B3D, 0x47F6, { 0x8E, 0x41, 0xA9, 0xD0, 0x63, 0xF2, 0x7B, 0x55 } }

// question ID（和 .vfr 保持一致）
#define JY_TIAN_ENABLE_QUESTION_ID  0x0001
#define JY_TIAN_MODE_QUESTION_ID    0x0002

// ★ varstore 结构 = 变量的内存布局 = 页面数据区，三者严格对应（2 字节）
#pragma pack(1)
typedef struct {
  UINT8  EnableFlag;   // 偏移 0
  UINT8  DemoMode;     // 偏移 1
} JY_TIAN_SETUP_CONFIGURATION;
#pragma pack()
```

### 关键点

- **两个 GUID 分开用**：
  - `FORMSET_GUID` → 标识"这个页面本身"，用于 `HiiAddPackages`、设备路径。
  - `VARSTORE_GUID` → 标识"这段配置存到哪个变量"，用于 `GetVariable/SetVariable/HiiConstructConfigHdr`。
  - 首页面 formset 和变量存储是两个独立概念，分开标识。
- **`#pragma pack(1)` 强制紧缩**：保证结构体就是紧凑 2 字节，和 NVRAM 变量、IFR 里的 varstore 字节布局完全一致。三者（变量 / IFR / struct）对得上才不出错。
- 这份头文件被 `.c` 和 `.vfr` **共同 include**，所以"类型 + GUID + ID"两边天然同步。头文件注释专门提醒：`keep in sync with the VFR`——这类对应关系没有编译器兜底，改一边必须改另一边。

## 3. `JYTianSetup.uni` —— 字符串包

纯文字，无逻辑。每个 `#string` 由一个 `STRING_TOKEN` 名字 + 一种语言的内容组成：

```
#langdef en-US "English"

#string STR_JY_TIAN_SETUP_TITLE   #language en-US "JYTian Setup Demo"
#string STR_JY_TIAN_SETUP_HELP    #language en-US "Minimal self-built setup page for HII practice"
#string STR_JY_TIAN_FORM_TITLE    #language en-US "JYTian Demo Settings"
#string STR_JY_TIAN_ENABLE_PROMPT #language en-US "Enable Demo Feature"
#string STR_JY_TIAN_ENABLE_HELP   #language en-US "Enable/Disable the JYTian demo feature"
#string STR_JY_TIAN_MODE_PROMPT   #language en-US "Demo Mode"
#string STR_JY_TIAN_MODE_HELP     #language en-US "Select the demo mode"
#string STR_JY_TIAN_MODE_A        #language en-US "Mode A"
#string STR_JY_TIAN_MODE_B        #language en-US "Mode B"
```

编译成 `JYTianSetupStrings[]` 字节数组（字符串包）。

**为什么 .vfr 用 token 而不是直接写字？**
**.vfr 里通过 `STRING_TOKEN(STR_JY_TIAN_ENABLE_PROMPT)` 引用，.uni 里把 token 翻译成对应语言。** 这样图文分离、支持多语言（同一页面换 `#langdef` 即可出不同语言），这正是"文字"和"页面结构"分离设计的原因。

## 4. `JYTianSetup.vfr` —— 表单定义（页面结构）

```vfr
#include "JYTianSetupConfig.h"

formset
  guid      = JY_TIAN_SETUP_FORMSET_GUID,
  title     = STRING_TOKEN(STR_JY_TIAN_SETUP_TITLE),
  help      = STRING_TOKEN(STR_JY_TIAN_SETUP_HELP),
  classguid = {0x9f85453e, 0x2f03, 0x4989, {0xad, 0x3b, 0x4a, 0x84, 0x07, 0x91, 0xaf, 0x3a}},
  class     = 0x0001,
  subclass  = 0,

  efivarstore JY_TIAN_SETUP_CONFIGURATION,   // 类型 = 结构体
    attribute = 0x00000007,                  // 变量属性 = NON_VOLATILE|BOOTSERVICE|RUNTIME
    name      = JYTianSetupVar,              // 变量名
    guid      = JY_TIAN_SETUP_VARSTORE_GUID; // 变量 GUID

  form formid = 0x0001, title = STRING_TOKEN(STR_JY_TIAN_FORM_TITLE);

    checkbox varid = JYTianSetupVar.EnableFlag,
      questionid = JY_TIAN_ENABLE_QUESTION_ID,
      prompt     = STRING_TOKEN(STR_JY_TIAN_ENABLE_PROMPT),
      help       = STRING_TOKEN(STR_JY_TIAN_ENABLE_HELP),
      flags      = RESET_REQUIRED;
    endcheckbox;

    oneof varid = JYTianSetupVar.DemoMode,
      questionid = JY_TIAN_MODE_QUESTION_ID,
      prompt     = STRING_TOKEN(STR_JY_TIAN_MODE_PROMPT),
      help       = STRING_TOKEN(STR_JY_TIAN_MODE_HELP),
      option text = STRING_TOKEN(STR_JY_TIAN_MODE_A), value = 0, flags = DEFAULT | RESET_REQUIRED;
      option text = STRING_TOKEN(STR_JY_TIAN_MODE_B), value = 1, flags = RESET_REQUIRED;
    endoneof;

  endform;
endformset;
```

### 4.1 `classguid / class / subclass` —— 决定页面出现在哪


- **概念上**：表单申报"我是这一类"，前端（H2O form browser）手里有一张"标签 → 菜单位置"的映射表，扫描 HII 数据库里所有 formset，按标签匹配归位。
- **这里**：`classguid = {0x9f85453e...}` = `SETUP_UTILITY_FORMSET_CLASS_GUID`（见 Config.h 注释，来自 `InsydeModulePkg Include/Guid/H2OSetup.h`），表示"这是 **Setup 工具里的配置页面（SC page）**"。因此 H2O form browser 会把它当成一个正常 setup 页面收编，而不是野生表单忽略。
- **注意**：它落到 Main 还是 Advanced，**取决于平台源码里的映射表**，`.vfr` 只负责"申报类别"，`.vfr` 本身给不出具体 Tab。
- **类比**：菜单大类 = 会议室（Main/Advanced），class = 你填的"会议类型回执"；前台（setup 前端）按"类型→房间"排班表把你安排进对应房间。回执决定进哪个房间，但它不是房间。

![[fig5-classguid-menu-mapping.svg|700]]

> **图 5 · classguid / class / subclass 归类机制**：.vfr 只负责申报类别，落到 Main 还是 Advanced 取决于平台源码的“标签→菜单位置”映射表。

### 4.2 `efivarstore` —— 声明数据存哪个变量

```vfr
efivarstore JY_TIAN_SETUP_CONFIGURATION,
  attribute = 0x00000007,   // = EFI_VARIABLE_NON_VOLATILE(1) | BOOTSERVICE(2) | RUNTIME(4)
  name      = JYTianSetupVar,
  guid      = JY_TIAN_SETUP_VARSTORE_GUID;
```

这里把"**页面用的数据类型**"和"**真实 UEFI 变量**"绑在一起。`attribute = 7` 的含义：

| 位 | 标志 | 含义 |
|----|------|------|
| 0x01 | NON_VOLATILE | 存非易失 Flash，断电不丢（配置必须） |
| 0x02 | BOOTSERVICE_ACCESS | 开机阶段（Boot Services）固件可读写 |
| 0x04 | RUNTIME_ACCESS | OS 接管后（Runtime）仍可读写 |

![[fig6-variable-identity-varstore.svg|700]]

> **图 6 · UEFI 变量身份 / varstore / attribute**：变量完整身份 = 名字（UTF-16）+ GUID；attribute=0x7 由非易失|开机读写|运行期读写三个位组成。

### 4.3 `formid` / `checkbox` / `oneof`

- `form formid = 0x0001` —— 表单页，页面里的一组 question。
- `checkbox varid = JYTianSetupVar.EnableFlag` —— 一个勾选框，绑定结构体字段 `EnableFlag`（偏移 0，1 字节）。`varid` 直接引用结构体成员，就是"把这个控件连到变量的哪一块"。
- `oneof varid = JYTianSetupVar.DemoMode` —— 一个下拉/单选，绑定 `DemoMode`（偏移 1）。两个 option，值 0 → Mode A（默认）、值 1 → Mode B。

![[fig4-ifr-formset-question-tree.svg|700]]

> **图 4 · IFR 结构树**：浏览器读 IFR opcode 解析成 formset → form → question(checkbox/oneof) 树，varstore / NVRAM 变量 / struct 三者字节布局严格对应（2 字节）。

## 5. `JYTianSetup.inf` —— 模块定义

```ini
[Defines]
    INF_VERSION   = 0x00010005
    BASE_NAME     = JYTianSetup
    FILE_GUID     = 1D4E8F26-93C7-4A5B-8E2D-6F09B3C74A81
    MODULE_TYPE   = DXE_DRIVER          # ← 关键：这是 DXE 驱动
    ENTRY_POINT   = JYTianSetupEntryPoint

[Sources]
    JYTianSetup.c
    JYTianSetup.vfr      # .vfr/.uni 在这里被编译成 HII 包
    JYTianSetup.uni
    JYTianSetupConfig.h

[Packages]
    MdePkg/MdePkg.dec
    MdeModulePkg/MdeModulePkg.dec
    Oem/OemJYTianPkg/OemJYTianPkg.dec

[LibraryClasses]
    UefiDriverEntryPoint
    UefiBootServicesTableLib
    UefiRuntimeServicesTableLib
    BaseLib
    BaseMemoryLib
    MemoryAllocationLib
    DebugLib
    PrintLib
    HiiLib

[Protocols]
    gEfiHiiConfigAccessProtocolGuid
    gEfiHiiConfigRoutingProtocolGuid
    gEfiDevicePathProtocolGuid

[Depex]
    TRUE
```

### 关键点

- **`MODULE_TYPE = DXE_DRIVER`** —— 证据表明它是 DXE 驱动的权威来源。它在 **DXE 阶段**加载，装协议、注册页面；它注册的页面则在**后面 BDS 阶段**由浏览器渲染交互。
- **`ENTRY_POINT = JYTianSetupEntryPoint`** —— 入口函数名。
- `[Sources]` 里把 `.vfr`/`.uni` 列进来，编译工具会据此生成 `JYTianSetupFormBin[]` 和 `JYTianSetupStrings[]`。
- `[LibraryClasses]` 里 `HiiLib` 提供 `HiiAddPackages`/`HiiConstructConfigHdr` 等；`UefiBootServicesTableLib`/`UefiRuntimeServicesTableLib` 提供 `gBS`/`gRT`。
- `[Depex] TRUE` —— 无依赖条件，进 DXE 即可加载（这个驱动只依赖 HII 和一些基础库）。

## 6. `JYTianSetup.c` —— 驱动实现（核心）

### 6.1 头部：宏 + 外部符号 + GUID

```c
#define JY_TIAN_SETUP_VAR_NAME        L"JYTianSetupVar"
#define JY_TIAN_SETUP_VAR_ATTRIBUTES  (EFI_VARIABLE_NON_VOLATILE | EFI_VARIABLE_BOOTSERVICE_ACCESS | EFI_VARIABLE_RUNTIME_ACCESS)

extern UINT8  JYTianSetupStrings[];   // 由 .uni 生成 → 字符串包
extern UINT8  JYTianSetupFormBin[];   // 由 .vfr 生成 → IFR 表单包

EFI_GUID  gJYTianSetupFormsetGuid  = JY_TIAN_SETUP_FORMSET_GUID;
EFI_GUID  gJYTianSetupVarstoreGuid = JY_TIAN_SETUP_VARSTORE_GUID;

STATIC JY_TIAN_SETUP_CONFIGURATION  mJYTianSetupConfig;
STATIC EFI_HANDLE  mDriverHandle;
```

- **`JY_TIAN_SETUP_VAR_NAME`** —— `L` 前缀宽字符串（UTF-16）。UEFI 变量名/字符串 API 都用这种宽字符串。变量完整身份 = **名字 + GUID**。
- **`JY_TIAN_SETUP_VAR_ATTRIBUTES`** —— 三个属性位按位或，声明"存非易失 + 开机读写 + 运行期读写"，是 `SetVariable` 告诉固件"怎么存储、谁能访问"。
- **`extern JYTianSetupStrings[] / FormBin[]`** —— 外部 symbol，不是本文件定义，而是编译工具生成的字节数组；`extern` 只是声明类型。供 `HiiAddPackages` 发布。
- **`GLOBAL_REMOVE_IF_UNREFERENCED`** —— EDK2 宏，表示"如果没人引用该全局变量，链接时去掉它"，省 Flash。这里两个 GUID 用 `EFI_GUID 变量 = 宏` 存成全局，是为了能取地址 `&xxx` 传给那些要 `EFI_GUID*` 的 API（`GetVariable` 等）。
- **`mJYTianSetupConfig`** —— 变量的**内存镜像**（非易失变量在内存里的缓存），`STATIC` 文件私有 + 零初始化。
- **`mDriverHandle`** —— 驱动在 UEFI 协议数据库里的身份 handle，多个函数共享。

### 6.2 设备路径类型

```c
typedef struct {
  VENDOR_DEVICE_PATH          VendorDevicePath;   // 厂商自定义路径节点（头 + 一个 GUID）
  EFI_DEVICE_PATH_PROTOCOL    End;                // 结束节点
} HII_VENDOR_DEVICE_PATH;

STATIC HII_VENDOR_DEVICE_PATH  mVendorDevicePathTemplate = {
  { { HARDWARE_DEVICE_PATH, HW_VENDOR_DP, {...} },
    JY_TIAN_SETUP_FORMSET_GUID },                      // 关键：只塞一个 GUID
  { END_DEVICE_PATH_TYPE, END_ENTIRE_DEVICE_PATH_TYPE, {...} }
};
```

### 6.3 `LoadConfigFromVariable` —— 读变量到内存

```c
Size = sizeof (mJYTianSetupConfig);
Status = gRT->GetVariable (
                JY_TIAN_SETUP_VAR_NAME, &gJYTianSetupVarstoreGuid, NULL, &Size, &mJYTianSetupConfig);
```

把 NVRAM 变量里的值搬到 `mJYTianSetupConfig`。注意 UEFI 变量靠 **名字 + GUID** 两个要素定位。

### 6.4 `ExtractConfig` —— 读方向（字节 → 字符串）

```c
// ① 校验 Progress/Results 非空
// ② *Progress = Request   （出错时浏览器知道处理到哪）
// ③ 若 Request 非空且头部不匹配本 varstore（GUID+名字）→ EFI_NOT_FOUND
// ④ LoadConfigFromVariable()  刷新内存，保证是新值
// ⑤ 若 Request 为 NULL 或不含 "OFFSET" → 构造全量请求:
//      HiiConstructConfigHdr()  生成 "GUID&NAME&PATH=" 前段
//      拼接 "&OFFSET=0&WIDTH=<sizeof>"  (这里 WIDTH=2)
//    若有 OFFSET → ConfigRequest = Request 原样
// ⑥ LocateProtocol(&gEfiHiiConfigRoutingProtocolGuid) 拿 ConfigRouting
// ⑦ return ConfigRouting->BlockToConfig(ConfigRequest, &mJYTianSetupConfig, size, Results, Progress);
```

浏览器想显示当前值时调用它：把 `mJYTianSetupConfig` 的字节按请求的 OFFSET/WIDTH 翻译成配置字符串（如 `...&VALUE=0100`）返回。

### 6.5 `RouteConfig` —— 写方向（字符串 → 字节 → 存变量）

```c
// ① 校验 Progress 非空
// ② *Progress = Configuration
// ③ 若 Configuration 非空且头部不匹配 → EFI_NOT_FOUND
// ④ LocateProtocol 拿 ConfigRouting
// ⑤ BufferSize = sizeof(mJYTianSetupConfig)
//    ConfigRouting->ConfigToBlock(Configuration, &mJYTianSetupConfig, &BufferSize, Progress)
//    解析 "VALUE=..." 填回结构体
// ⑥ gRT->SetVariable(JY_TIAN_SETUP_VAR_NAME, &gJYTianSetupVarstoreGuid,
//                    JY_TIAN_SETUP_VAR_ATTRIBUTES, size, &mJYTianSetupConfig)  // 真正持久化
```

浏览器保存用户改动时调用：把配置字符串解析回字节、更新 `mJYTianSetupConfig`，再 `SetVariable` 写进 NVRAM 变量。**注意**：`ConfigToBlock` 的 `BufferSize` 是入/出参数（入=容量 2，出=实际解析字节数）。

![[fig7-read-write-sequence.svg|700]]

> **图 7 · 读写时序**：读（ExtractConfig）先 LoadConfig 刷内存再 BlockToConfig；写（RouteConfig）先 ConfigToBlock 填内存再 SetVariable 落盘。

### 6.6 `Callback` —— 交互回调

```c
return EFI_UNSUPPORTED;
```
当前没有需要交互的 question（实时刷新/联动/弹窗），直接返回让浏览器走默认的 Extract/Route 流程。

### 6.7 `InstallMultipleProtocolInterfaces` —— 注册身份和能力

```c
Status = gBS->InstallMultipleProtocolInterfaces (
                &mDriverHandle,                       // 传出：新 handle
                &gEfiDevicePathProtocolGuid,          // 协议 GUID：设备路径
                DevicePath,                            // 它的接口 = 设备路径数据
                &gEfiHiiConfigAccessProtocolGuid,      // 协议 GUID：配置访问
                &mConfigAccess,                        // 它的接口 = 三个回调
                NULL                                   // 结束标记
                );
```

- 变参：`(handle, GUID, interface, GUID, interface, ..., NULL)`。GUID 是"装哪个协议"（键），interface 是"装的内容"（值）。光有 GUID 无接口没意义。
- 一次**原子地装两个**：设备路径（身份）+ ConfigAccess（能力），保证成对不脱节。装完系统才能发现并调用你的设置结果。
- 这步是"注册"；`ExtractConfig` 里用它 `LocateProtocol`（找 ConfigRouting）是"查询"，方向相反。

### 6.8 `HiiAddPackages` —— 发布页面外观

```c
Status = HiiAddPackages (
           &gJYTianSetupFormsetGuid,   // 包列表 GUID（= formset GUID）
           mDriverHandle,              // 归属的 handle（带 ConfigAccess 那个）
           JYTianSetupStrings,         // 字符串包（文字）
           JYTianSetupFormBin,         // IFR 表单包（结构）
           NULL                        // 结束
           );
```

把 `.uni/.vfr` 编译成的**文字包 + 表单包**发布进 HII 数据库，登记在这个 formset GUID 下并归属到 handle。

> **关键**：两步必须都做。
> - `InstallMultipleProtocolInterfaces` 装**逻辑**（回调）——能取值存值；
> - `HiiAddPackages` 装**外观**（文字+结构）——浏览器能找到并渲染。
> 两者缺一不可。IFR 里的 `STRING_TOKEN` 要靠字符串包翻译成实际文字，所以两个包必须一起打包。

### "浏览器"到底是什么？

- **组件层面**：一个装了 `EFI_FORM_BROWSER2_PROTOCOL`（核心 `SendForm`）的 **DXE 驱动**（EDK2 是 `MdeModulePkg/Universal/SetupBrowserDxe/`）。它渲染、处理按键、和 ConfigAccess 协议交互。（Insyde/AMI 可能用自己的实现替换，职责相同。）
- **数据层面**：它从 HII 数据库读出 `.vfr/.uni` 编译成的 **IFR opcode 字节流**，解析成一棵 **formset → form → question(statement)** 的树，每个 question 节点记录 `QuestionId`、文字 token、**它对应哪个 varstore（GUID+偏移+宽度）和当前值**。
- **和代码的连接**：浏览器要显示值时，顺着 varstore GUID 找到装 ConfigAccess 协议的 handle，调用 `ExtractConfig`（读）/ `RouteConfig`（写）。
