# SMBIOS：硬件信息表的结构、定位与 BIOS 实现

SMBIOS（System Management BIOS，DSP0134）是 DMTF 制定的标准，规定固件如何以统一格式把主板、系统、CPU、内存等硬件信息报告给 OS。PC 不需要像 MCU 那样逐个寄存器探测硬件——就像 STM32 有 Unique ID 和 Flash 里的产品信息区，PC 的"系统身份证"就是这张 SMBIOS Table：BIOS 在 POST 阶段把它构建好放进内存，OS 和管理工具（wmic、dmidecode、设备管理器）按固定入口定位并解析。本篇覆盖 Entry Point 定位、Structure 布局与 String-Set 机制、常用 Type、EFI_SMBIOS_PROTOCOL 四个接口的完整用法。

## 一、概述：为什么需要 SMBIOS

SMBIOS 解决的核心问题：**消除硬件探测风险**。OS 若不借助 SMBIOS，就得自己枚举总线、读 PCI 配置空间、访问 SMBus 猜测硬件，慢且容易出错。SMBIOS 让固件在启动早期把关键硬件信息整理成标准结构表，OS 直接读取。

| 项目 | 说明 |
| --- | --- |
| 标准 | DMTF DSP0134 |
| 当前版本 | 3.1.1（2017 年） |
| 支持架构 | IA-32、x64、Itanium、ARM32、ARM64 |
| 数据提供方 | BIOS 固件（DXE 阶段构建） |
| 消费方 | OS、资产管理系统（SCCM/MDT/WMI）、硬件检测工具 |

版本历史要点：2.0 引入 Table 方法；2.1 Table 成为必须实现；2.3 定义必需结构集（Type 0/1/2/3/4/7）；3.0 新增 64-bit Entry Point（`_SM3_`）。

> SMBIOS 是**静态快照**：信息在 POST 时构建，运行期间不更新。这与 ACPI 的动态枚举机制形成对比——ACPI 描述"系统如何工作"（电源、中断、资源），SMBIOS 描述"系统是什么"（型号、序列号、插槽）。

## 二、数据流：从 POST 到 OS

1. **构建**：SMBIOS Table 在 **DXE 阶段**由 `SmbiosDxe` 驱动统一管理，各模块驱动（BasicDxe、CpuSmbios、MemSmbios、MiscSmbios）通过 `EFI_SMBIOS_PROTOCOL` 把自己的 Structure 注册进去
2. **存放**：Table 分配在 **`EfiRuntimeServicesData`** 类型内存。OS 运行期仍要读 SMBIOS（wmic 等随时可查），这段内存不能在 ExitBootServices 后被回收
3. **入口**：`SmbiosDxe` 在 ReadyToBoot 前后把 Entry Point / Table 指针安装进 **EFI Configuration Table**（两个 GUID）
4. **消费**：Windows 走 wmic/msinfo32/WMI；Linux 走 dmidecode//sys/firmware/dmi/；AMI 平台用 AMIDEEFI

> MCU 类比：SMBIOS Table 相当于 MCU 烧录在 Flash 用户区、由启动代码组装的"设备信息结构体"；UEFI 的 Configuration Table 就是"系统表里的注册表入口"，OS 通过固定 GUID 拿指针。`EfiRuntimeServicesData` 与 Runtime Services 的 Runtime 内存段是同一套机制。

## 三、Entry Point Structure（EPS）：入口结构

EPS 是定位整张 SMBIOS Table 的"门牌"。存在两代格式，可同时存在于系统中。

### 3.1 32-bit EPS（SMBIOS 2.1+，总长 1Fh）

| Offset | 名称 | 长度 | 说明 |
| --- | --- | --- | --- |
| 00h | Anchor String | 4B | `_SM_` |
| 04h | Entry Point Checksum | 1B | 整个 EPS 按字节求和，低 8 位应为 0 |
| 05h | Entry Point Length | 1B | 当前 1Fh |
| 06h/07h | Major/Minor Version | 1B×2 | SMBIOS 主/次版本 |
| 08h | Max Structure Size | 2B | 最大结构体（格式化区+字符串集） |
| 0Ah | Entry Point Revision | 1B | EPS 修订 |
| 10h | Intermediate Anchor String | 5B | `_DMI_`（旧 DMI 浏览器兼容） |
| 16h | Table Length | 2B | Structure Table 总字节数 |
| 18h | Table Address | 4B | Table 的 32-bit 物理地址 |
| 1Ch | Number of Structures | 2B | 结构体数量 |

### 3.2 64-bit EPS（SMBIOS 3.0+，总长 18h）

| Offset | 名称 | 长度 | 说明 |
| --- | --- | --- | --- |
| 00h | Anchor String | 5B | `_SM3_` |
| 0Ch | Table Maximum Size | 4B | Table 最大尺寸 |
| 10h | Table Address | 8B | 64-bit 物理地址，Table 可放任意位置 |

64-bit EPS 优势：Table 可放 4GB 以上、结构更紧凑（18h 对 1Fh）、可与 32-bit EPS 并存。

### 3.3 定位方式：Legacy 搜索 vs UEFI Configuration Table

| 环境 | 定位方法 |
| --- | --- |
| 非 UEFI（Legacy BIOS） | 在物理内存 `0xF0000–0xFFFFF` 段按 16 字节对齐扫描 `_SM_`/`_SM3_` 锚点 |
| UEFI | 在 EFI Configuration Table 中查 `SMBIOS_TABLE_GUID`（2.x 表）或 `SMBIOS3_TABLE_GUID`（3.x 表） |

```c
// MdePkg/Include/Guid/SmBios.h —— 两个 GUID
#define SMBIOS_TABLE_GUID \
  { 0xeb9d2d31, 0x2d88, 0x11d3, {0x9a, 0x16, 0x00, 0x90, 0x27, 0x3f, 0xc1, 0x4d } }

#define SMBIOS3_TABLE_GUID \
  { 0xf2fd1544, 0x9794, 0x4a2c, {0x99, 0x2e, 0xe5, 0xbb, 0xcf, 0x20, 0xe3, 0x94 } }
```

> [!warning]
> EDK2 头文件注释明确：**UEFI 系统下只允许通过 Configuration Table 定位 SMBIOS，禁止再扫描 0xF0000 段**。UEFI 下 Table 可能不在 F0000 段附近，甚至可能超过 4GB。

双表共存：符合 3.0+ 的固件通常同时安装 2.1 版 Table（`_SM_`，兼容老 OS）和 3.x 版 Table（`_SM3_`），两个 GUID 都在。

## 四、Structure 布局与 String-Set 机制

每个 SMBIOS Structure 的内存布局：**4 字节 Header + 格式化区域（Formatted Area）+ 字符串集（String-Set）**。

### 4.1 Header（4 字节）

| Offset | 名称 | 长度 | 说明 |
| --- | --- | --- | --- |
| 00h | Type | 1B | 0–127 标准结构；128–255 OEM 自定义 |
| 01h | Length | 1B | **格式化区域**长度（不含字符串集） |
| 02h | Handle | 2B | 唯一 16-bit 标识符，跨结构引用用 |

Handle 规则：2.1+ 合法范围 0–0xFEFF；`0xFFFE`（`EFI_SMBIOS_INVALID_HANDLE`）表示"由 SmbiosDxe 自动分配"。

```c
typedef struct {
  EFI_SMBIOS_TYPE   Type;
  UINT8             Length;   // 格式化区域长度
  EFI_SMBIOS_HANDLE Handle;
} EFI_SMBIOS_TABLE_HEADER;
```

### 4.2 String-Set 规则

1. 每个字符串以 `00h` 结束
2. 整个字符串集以 `00h 00h` 双空结束
3. 格式化区域中的字符串字段是**索引**（从 1 开始，0 = 空字符串）
4. 字符串按顺序排列，按索引取第 N 个

内存示例（Type 1 System Information）：

```
Offset 内容
------+------------------------------------------
 00h  | Type=01  Length=1Bh  Handle=0x0001   ← Header 4B
 04h  | Mfr=1 Prod=2 Ver=3 SN=4 ...           ← Formatted 23B
      | "CVTE\0"                              ← String 1
      | "D35TE\0"                             ← String 2
      | "V1.0\0"                              ← String 3
      | "SN12345\0"                           ← String 4
      | \0                                    ← 字符串集结束
```

读取字符串：从 `Record + Length` 处开始，逐个跳过 `AsciiStrSize()` 长度的字符串，按索引计数。

```c
CHAR8 *
GetSmbiosString (
  IN EFI_SMBIOS_TABLE_HEADER *Record,
  IN UINT8                    StringNum
  )
{
  CHAR8 *Str = (CHAR8 *)Record + Record->Length;   // 跳过格式化区域
  if (StringNum < 1) {
    return "";                                     // 索引 0 = 空字符串
  }
  while (--StringNum > 0) {
    Str += AsciiStrSize (Str);                     // 跳过前 N-1 个字符串
  }
  return Str;
}
```

> 遍历 Table 还有隐含哨兵：**Type 127（End-of-Table）** 是最后一条结构，`Type 126` 表示 Inactive 空位。遍历靠 Type 127 判断结束，不依赖"数量"字段。

### 4.3 Structure 演化准则

- 新字段只能**追加到格式化区域末尾**，同时把 Length 加长
- 解析程序必须**用 Length 字段**判断格式化区大小，不得硬编码
- 每条结构以双空 `0000h` 结尾

这套"向后兼容"规则与 MCU 固件协议升级时"只追加字段、旧程序按长度解析"的做法一致。

## 五、常用 Type 详解

### 5.1 Type 0/1/2：BIOS / System / Baseboard（必需结构）

Type 0/1/2 是合规实现的最小必需集，产线写入的 SN/UUID 主要落在 Type 1/2。

**Type 0 — BIOS Information**：Vendor、BIOS Version、BIOS Starting Address、BIOS Release Date、BIOS ROM Size、BIOS Characteristics（QWORD 位图）、System BIOS Major/Minor、EC FW Major/Minor。

**Type 1 — System Information**：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| Manufacturer | STRING | 制造商 |
| Product Name | STRING | 产品名 |
| Serial Number | STRING | **系统 SN（产线写入 ★）** |
| UUID | 16 BYTEs | **系统 UUID（产线写入 ★）** |
| Wake-up Type | BYTE | 唤醒方式 |
| SKU Number | STRING | SKU |

**Type 2 — Baseboard Information**：Manufacturer、Product、Version、Serial Number（**主板 SN，AMIDEEFI `/BS` 写入 ★**）、Asset Tag、Feature Flags、Location in Chassis、Chassis Handle、Board Type。

> [!warning]
> UUID 是产线常见踩坑点：Type 1 的 16 字节 UUID 中，前 3 个字段（time_low/time_mid/time_hi）是 **little-endian** 存储，其余按原序。Windows（按规范字节序转字符串）和 Linux dmidecode（有的按 raw 字节打印）显示的 UUID 可能"前后颠倒"，不是数据错，是字节序解释差异。

### 5.2 Type 3/4/7：Chassis / Processor / Cache

**Type 3 — Chassis（机箱）**：Manufacturer、Chassis Type（Desktop=3、Tower=7、Laptop=9）、Version/Serial/Asset、Boot-Up/Power/Thermal State、Security Status。

**Type 4 — Processor**：Socket、Processor Type、Family、Manufacturer、**Processor ID（8 字节）**、Version、**Max Speed / Current Speed（MHz ★）**、Core Count / Thread Count。

```c
// Processor ID 字段编码：等于 CPUID 指令 01h 的 EAX（低 4 字节）+ EDX（高 4 字节）
// EAX[3:0]  = Stepping
// EAX[11:8] = Family
// EAX[19:16]= Model
// EDX       = Feature Flags（MMX/SSE/... 位图）
```

**Type 7 — Cache**：Socket、Cache Config（Level/Location/Mode 位图）、Max Size、Installed Size、SRAM Type、Cache Speed、Error Correction、Cache Type、Associativity。

### 5.3 Type 16/17：内存（Handle 关联示例）

Type 16 描述**物理内存阵列**（一个内存控制器下的所有插槽），Type 17 描述**单个内存条**。Type 17 的 `Memory Array Handle` 指向 Type 16 的 Handle：

```
Type 16 (Physical Memory Array)  Handle: 0x0030   Max: 64GB, Devices: 2
   ├── Type 17 #1 (Slot A)  Array Handle: 0x0030  Size: 16GB  DDR5 4800
   └── Type 17 #2 (Slot B)  Array Handle: 0x0030  Size: 16GB  DDR5 4800
```

**Type 16**：Location（System Board=3）、Use（System Memory=3）、Error Correction、Maximum Capacity、Number of Devices、Extended Max Capacity。

**Type 17**：Memory Array Handle（→ Type 16）、Size（0=未安装、0xFFFF=用 Extended Size）、Form Factor（DIMM=9、SODIMM=13）、Device Locator、Memory Type（DDR4=26、DDR5=34）、Speed（MT/s ★）、Manufacturer/SerialNumber/PartNumber。

> 内存容量常用字段：`Type17->Size` 以 MB 为单位（容量超 32GB 时用 Extended Size 字段，按 KB 计）。这也是 Shell `smbiosview` 能直接列出内存条信息的原因。

### 5.4 完整 Type 速查

| Type | 名称 | Type | 名称 |
| --- | --- | --- | --- |
| 0 | BIOS Info | 16 | Phys Mem Array |
| 1 | System Info | 17 | Memory Device |
| 2 | Baseboard | 19 | Mem Mapped Addr |
| 3 | Chassis | 32 | Boot Info |
| 4 | Processor | 43 | TPM Device |
| 7 | Cache | 126 | Inactive |
| 8 | Port Conn | 127 | End-of-Table |
| 9 | System Slot | 128+ | OEM Custom |

## 七、BIOS 中的 SMBIOS 实现架构

### 驱动分工

```
                    ┌────────────────────────────┐
                    │  SmbiosDxe（生产者）        │
                    │  安装 EFI_SMBIOS_PROTOCOL   │
                    │  维护 Structure 链表        │
                    │  ReadyToBoot 时组表并安装    │
                    └────────────┬───────────────┘
                                 │ Add()/GetNext()/UpdateString()/Remove()
        ┌───────────────┬────────┴───────┬───────────────┬──────────────┐
        ▼               ▼                ▼               ▼              ▼
  BasicDxe        CpuSmbios        MemSmbios        MiscSmbios      OEM 驱动
  Type 0/1/2/3    Type 4/7         Type 16/17       Type 9/11/13    Type 128+
```

- `SmbiosDxe`（MdeModulePkg/Universal/SmbiosDxe）是**生产者**：安装 Protocol、把各驱动注册的 Structure 组成 Table、在 ReadyToBoot/ExitBootServices 附近把 Table 指针安装进 Configuration Table
- 各模块驱动是**消费者兼填充者**：通过 Protocol 的 Add() 注册自己负责的 Type

### EDK II 源码位置

| 内容 | 路径 |
| --- | --- |
| 全部标准结构体定义 | `MdePkg/Include/IndustryStandard/SmBios.h` |
| Entry Point 结构 | `MdePkg/Include/IndustryStandard/SmBios.h` |
| EFI_SMBIOS_PROTOCOL 接口 | `MdePkg/Include/Protocol/Smbios.h` |
| 两个定位 GUID | `MdePkg/Include/Guid/SmBios.h` |
| SmbiosDxe 驱动实现 | `MdeModulePkg/Universal/SmbiosDxe/SmbiosDxe.c` |


工程内真实用法在 `AmiModulePkg/InfoReport/PostReport.c`（POST 界面显示 CPU 信息）：

```c
// 1. 定位 Protocol
Status = gBS->LocateProtocol (&gEfiSmbiosProtocolGuid, NULL, (VOID **)&Smbios);

// 2. 从头开始遍历 Type 4（初始 Handle 用保留值 0xFFFE）
SmbiosHandle = SMBIOS_HANDLE_PI_RESERVED;    // 0xFFFE
SmbiosType   = EFI_SMBIOS_TYPE_PROCESSOR_INFORMATION;   // Type 4
Status = Smbios->GetNext (Smbios, &SmbiosHandle, &SmbiosType, &SmbiosRecord, NULL);

// 3. 取格式化区字段
SmbiosType4Record = (SMBIOS_TABLE_TYPE4 *)SmbiosRecord;
// 4. 取字符串：ProcessorVersion 是字符串索引
StringIndex = SmbiosType4Record->ProcessorVersion;
Status = SmbiosGetOptionalStringByIndex (
           (CHAR8 *)((UINT8 *)SmbiosType4Record + SmbiosType4Record->Hdr.Length),
           StringIndex, &ProcessorVersionString);
// 5. 直接读数值字段
UnicodeSPrint (CpuCurrentSpeedString, ..., L"%s: %dMHz", L"Processor Speed",
               SmbiosType4Record->CurrentSpeed);
```

这段代码与第四节 `GetSmbiosString` 思路完全一致：`Record + Length` 跳过格式化区 → 按索引数字符串。`SMBIOS_HANDLE_PI_RESERVED 0xFFFE` 就是 `EFI_SMBIOS_INVALID_HANDLE` 的别名。

## 八、EFI_SMBIOS_PROTOCOL 四接口

```c
typedef struct _EFI_SMBIOS_PROTOCOL {
  EFI_SMBIOS_ADD            Add;            // 添加 Structure
  EFI_SMBIOS_UPDATE_STRING  UpdateString;   // 更新字符串
  EFI_SMBIOS_REMOVE         Remove;         // 删除 Structure
  EFI_SMBIOS_GET_NEXT       GetNext;        // 遍历 Structure
} EFI_SMBIOS_PROTOCOL;
```

> [!warning]
> 调用约束：**只能在不高于 `TPL_NOTIFY` 的优先级调用**（PI 1.2 Volume 5）。中断处理函数或高 TPL 回调里不能直接调 SMBIOS Protocol。

### 8.1 Add()：添加 Structure

`Add` 把一条 Structure（Header + 格式化区 + 字符串集）复制进 Table。`SmbiosHandle` 传 `EFI_SMBIOS_INVALID_HANDLE` 时由 SmbiosDxe 自动分配新 Handle 并回填。

```c
EFI_STATUS
EFIAPI
MySmbiosDxeEntryPoint (
  IN EFI_HANDLE        ImageHandle,
  IN EFI_SYSTEM_TABLE  *SystemTable
  )
{
  EFI_STATUS              Status;
  EFI_SMBIOS_PROTOCOL     *Smbios;
  EFI_SMBIOS_HANDLE       Handle;

  // 1. 定位 SMBIOS Protocol
  Status = gBS->LocateProtocol (&gEfiSmbiosProtocolGuid, NULL, (VOID **)&Smbios);
  if (EFI_ERROR (Status)) {
    return Status;
  }

  // 2. INVALID → SmbiosDxe 自动分配 Handle
  Handle = EFI_SMBIOS_INVALID_HANDLE;

  // 3. 注册 Structure（mType2Data = Header + 格式化区 + 字符串集，连续内存）
  Status = Smbios->Add (
             Smbios,
             ImageHandle,                            // ProducerHandle
             &Handle,                                // 返回分配的 Handle
             (EFI_SMBIOS_TABLE_HEADER *)&mType2Data // Record 指针
             );

  DEBUG ((DEBUG_INFO, "Type 2 added, Handle=0x%04x\n", Handle));
  return Status;
}
```

Type 2 数据定义（`#pragma pack(1)`，字符串集紧跟格式化区）：

```c
#pragma pack(1)
typedef struct {
  SMBIOS_TABLE_TYPE2  Header;    // 格式化区域（含 4 字节 Header 头）
  CHAR8               Strings;   // String-Set 起点：全部字符串 + 结束双空
} SMBIOS_TYPE2_DATA;
#pragma pack()

SMBIOS_TYPE2_DATA mType2Data = {
  {
    { 2, sizeof (SMBIOS_TABLE_TYPE2), 0 },   // Type=2, Length, Handle(0=自动)
    1,    // Manufacturer     = String 1
    2,    // Product          = String 2
    3,    // Version          = String 3
    4,    // SerialNumber     = String 4
    5,    // AssetTag         = String 5
    0x09, // FeatureFlags
    6,    // LocationInChassis = String 6
    0,    // ChassisHandle
    0x0A, // BoardType = Motherboard
    0,    // NumberOfContainedObjectHandles
  },
  // 下面 String-Set（顺序与索引一一对应）：
  // "CVTE\0"  ← String 1
  // "D35TE\0" ← String 2
  // "V1.0\0"  ← String 3
  // "SN001\0" ← String 4
  // "AT001\0" ← String 5
  // "Board\0" ← String 6
  // \0         ← String-Set 结束
};
```

### 8.2 GetNext()：遍历

`GetNext` 按 Type 过滤遍历。`Handle` 是输入/输出参数：输入 0 从头开始，输出下一个匹配的 Handle；返回 `EFI_NOT_FOUND` 表示遍历结束。`Type` 传 NULL 则不过滤。

```c
EFI_STATUS
DumpAllMemoryDevices (
  IN EFI_SMBIOS_PROTOCOL *Smbios
  )
{
  EFI_STATUS              Status;
  EFI_SMBIOS_HANDLE       Handle = 0;     // 从头开始
  EFI_SMBIOS_TYPE         Type   = 17;    // 只查 Type 17
  EFI_SMBIOS_TABLE_HEADER *Record;
  SMBIOS_TABLE_TYPE17     *Type17;

  while (TRUE) {
    Status = Smbios->GetNext (Smbios, &Handle, &Type, &Record, NULL);
    if (EFI_ERROR (Status)) {
      break;                              // EFI_NOT_FOUND = 遍历结束
    }
    Type17 = (SMBIOS_TABLE_TYPE17 *)Record;
    DEBUG ((DEBUG_INFO, "Handle=0x%04x Size=%dMB Speed=%d\n",
            Type17->Hdr.Handle, Type17->Size, Type17->Speed));
  }
  return EFI_SUCCESS;
}
```

### 8.3 UpdateString()：更新字符串

`UpdateString` 修改已有 Structure 的**字符串**（String-Set 中的一条），**不能改格式化区域**。新字符串长度可以不同，SmbiosDxe 自动调整 Table 大小。产线写 SN 的核心接口。

```c
EFI_STATUS
UpdateSystemSerialNumber (
  IN EFI_SMBIOS_PROTOCOL *Smbios,
  IN CHAR8               *NewSN
  )
{
  EFI_STATUS              Status;
  EFI_SMBIOS_HANDLE       Handle = 0;
  EFI_SMBIOS_TYPE         Type   = 1;
  EFI_SMBIOS_TABLE_HEADER *Record;
  SMBIOS_TABLE_TYPE1      *Type1;

  // 1. 找到 Type 1
  Status = Smbios->GetNext (Smbios, &Handle, &Type, &Record, NULL);
  if (EFI_ERROR (Status)) {
    return Status;
  }
  Type1 = (SMBIOS_TABLE_TYPE1 *)Record;

  // 2. 更新 String 4（SerialNumber 字段的值就是索引 4）
  Status = Smbios->UpdateString (
             Smbios,
             &Handle,                // Type 1 的 Handle
             &Type1->SerialNumber,   // 指向字符串索引字段（=4）
             NewSN                   // 新字符串
             );
  return Status;
}
```

产线常见用法对照：

| 目标 | 调用方式 |
| --- | --- |
| 系统 SN（Type 1） | `&Type1->SerialNumber`（String 4） |
| 主板 SN（Type 2） | `&Type2->SerialNumber`（String 4） |
| UUID（Type 1） | **不能用 UpdateString**（UUID 是格式化区 16 字节字段），需 Remove() + Add() 整体替换 |
| 字符串任意长度 | 可以，SmbiosDxe 自动重建 Table |

## 九、AMIDEEFI：AMI DMI Editor

AMIDEEFI 是 AMI Aptio 平台的 DMI 读写工具（EFI Shell 下运行），产线写 SN/UUID 的官方通道。常用参数：

| 命令 | 功能 | Type |
| --- | --- | --- |
| `/SM` / `/SP` / `/SV` / `/SS` | 读写 System Manufacturer/Product/Version/SN | 1 |
| `/SU` | 读写 System UUID（16 字节）/ `AUTO` 自动生成 | 1 |
| `/SK` / `/SF` | 读写 SKU / Family | 1 |
| `/BM` / `/BP` / `/BV` / `/BS` | 读写 Baseboard 各字段 | 2 |
| `/BT` | 读写 Asset Tag | 2 |
| `/CM` / `/CT` / `/CS` | 读写 Chassis 各字段 | 3 |
| `/OS` | 读写 OEM String（Type 11） | 11 |
| `/IV` / `/ID` | 读写 BIOS Version / Release Date（Type 0） | 0 |
| `/ALL` / `/DUMP` | 导出全部 SMBIOS 数据 | — |

```bash
# 读：不带参数
AMIDEEFIx64.efi /SS
# 写：带参数（含空格用双引号）
AMIDEEFIx64.efi /SS "AACA2051013"
AMIDEEFIx64.efi /SP "CVTE-D35TE"
AMIDEEFIx64.efi /SU AUTO
```

### 为什么重启后 SN 还在？

AMIDEEFI 写入的字符串**不是**只改内存里的 Runtime Table，而是持久化到 **SPI Flash 的 NVRAM/DMI 数据区**。启动流程：

```
开机 → BIOS 从 SPI Flash 读取 DMI/NVRAM 数据 → 组装 SMBIOS Structure（含 SN/UUID）
     → SmbiosDxe 生成 Table → 安装进 Configuration Table → OS 读取
```

"重启后 SN 还在"是因为源头在 Flash 里，每次启动只是**重建**而非重新生成。这与 Runtime Services 笔记里"NV 变量持久化于 SPI Flash NVRAM"是同一机制。

> MCU 类比：相当于把"设备序列号"烧进 MCU 的 Flash 用户数据区（而非 RAM），每次上电从 Flash 读出填进设备信息结构体。AMIDEEFI 就是"产线烧录工具"，`/SU AUTO` 相当于"按芯片 UID 生成唯一序列号"。

## 十、作业思路：Type 140 与 Setup 显示

1. **创建 SMBIOS Type 140（OEM 类型）**：自定义结构体，Type=140（128+ 属于 OEM 区），定义好格式化区字段（如 BIOSVersion、ECVersion + 字符串），按第八节 Add() 流程注册，可在 DXE 驱动入口完成
2. **在 Setup 上显示**：Setup 界面是 AMI TSE 框架，显示自定义数据走 Setup 页面配置/Hook 机制，或在 POST 界面（InfoReport 风格）打印；更直接的做法是 DXE 驱动把 Type 140 字段读出来（GetNext + 字符串读取）交给显示层
3. **AMIDEEFI 读写 SN**：见第九节命令表

> OEM Type（128–255）的格式化区格式由厂商自定，**不注册到 SMBIOS 规范**，但结构仍遵循"Header + 格式化区 + String-Set + 双空结束"的通用布局，OS 侧工具（dmidecode 未知类型）会跳过或原样显示。

## 术语表

| 术语 | 含义 |
| --- | --- |
| SMBIOS | System Management BIOS，DMTF DSP0134 标准，硬件信息表 |
| DMI | Desktop Management Interface，SMBIOS 的前身/别名 |
| EPS | Entry Point Structure，定位 Structure Table 的入口结构（`_SM_`/`_SM3_`） |
| Structure | 一条硬件信息记录，Type/Length/Handle + 格式化区 + 字符串集 |
| Handle | 结构的 16-bit 唯一标识，跨结构引用用（如 Type 17 → Type 16） |
| String-Set | 格式化区后的字符串集合，索引从 1 开始，双空结尾 |
| Formatted Area | 结构体定长字段区，长度由 Header 的 Length 给出 |
| Type 127 | End-of-Table，Table 的最后一条哨兵结构 |
| EFI_SMBIOS_PROTOCOL | UEFI 下添加/遍历/修改 SMBIOS 记录的服务接口 |
| Configuration Table | UEFI 系统表（gST）中的配置表，SMBIOS 通过其中 GUID 定位 |
| AMIDEEFI | AMI 的 DMI Editor 工具，EFI Shell 下读写 SMBIOS 字符串 |
