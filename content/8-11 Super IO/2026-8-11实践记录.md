# GPIO40 输出拉高实践记录（IT8786E-I）


## GP40 的寄存器链路

| 功能 | 寄存器 | 位 | 写后实测值 |
| --- | --- | --- | --- |
| 复用选择 | 0x28 | bit0=1 | 01 |
| Simple I/O 使能 | 0xC3 | bit0=1 | 41（默认 40h + bit0） |
| 方向 Output | 0xCB | bit0=1 | 01 |
| 拉高 | 0xA03（数据口） | bit0=1 | FB |

## 工程实现（MyGPIO）

新建了 `OemJYTianPkg\JYTianPeiIo` 子模块，MyGPIO.c 用表驱动（仿 IT8786PeiIoTable 的 SIO_DEVICE_INIT_DATA 三元组）+ 自己写遍历。**没引 AMI 的 SIO 库**，因为引了会陷入依赖泥潭（见排错）。LPC decode 兜底也自己写了：直接操作 LPC 桥（BDF 0:31:0）的 Generic Decode Range 寄存器（0x84 起 4 个），照抄 SbCspIoDecodeLib 的实现。

```
解锁(2E←87 01 55 55) → LDN=07 → 0x28 bit0 → 0xC3 bit0 → 0xCB bit0 → 锁回(02/02) → 0xA03 bit0
```

## 构建排错

工程有个隐性状态：`AlderLakeFspSource.sdl` 把 `AmiChipsetModulePkg_SB_SUPPORT` 覆盖成 0（FSP 方案裁掉 AMI 的南桥链）。这导致 AMI 的 SIO 库（AmiSioPeiLib 等）全部没进 Platform.dsc，按序踩了这些：

1. **error 4000（AmiSioPeiLib 找不到）**：GenericSio/IT8786 链被禁用 → 库映射不生成。在自己包的 sdl 里补 LibraryMapping
2. **SDL 报 "INFComponent ... not defined"**：LibraryMapping 引用的 INFComponent 必须在已加载链里定义，被禁用链里的不算。要连 INFComponent 一起补
3. **error 000E 路径错**：INFComponent 的 File 是相对 sdl 文件目录的，跨包要用 `../../` 上溯
4. **LNK2001（SbLibSetLpcGenericDecoding）**：AmiIoDecodeLib 这个库类工程里**本来就有实例**（Sb.sdl 映射到 SbCspIoDecodeLib），我又补了一个不同实现，dsc 同段后者覆盖前者，把 SbPei 的链接搞坏了。教训：补库映射前先 grep dsc 里该类有没有
5. **AmiChipsetIoLib 找不到**：SbCspIoDecodeLib 又依赖它，还在被裁剪链里——连锁无底洞
6. **最终放弃 AMI 库，自包含**：decode 照抄 SbCspIoDecodeLib（PciCf8Lib 操作 LPC 桥），依赖只剩 AmiPeiLib + PciCf8Lib，两个 dsc 里都有映射

核心经验一句话：**FSP 方案工程里，涉及 SIO 的自建模块别引 AMI 库链，自己实现最干净**。

## RW 验证（又一个坑）

RW 里两个视图容易混：

- **Super I/O 视图**（标题 Winbond Super I/O 2E/2F）：显示的是 SIO 配置寄存器空间（0x00~0xFF），Chip ID 在 0x20 行可见（87 86）。**这里没有数据口**
- **IO Space 视图**（Access → I/O Ports）：系统 IO 端口空间，0xA03 在这里

我一开始把 Super I/O 视图的 0xA0 行当成端口空间，误判"拉高没生效"。切到 IO Space 看 0xA03 = **FB**，bit0 是 1，拉高其实早生效了。判断视图：Super I/O 视图 0x20 行能读到 Chip ID，IO Space 从 0x0000 排端口。

实测确认：0x28=01、0xC3=41、0xCB=01、0xA03=FB（bit0=1）、0xA00 段 decode 已开（非 FF）。

## 结论

GP40 配置任务完成：复用已切、方向已设输出、数据口 bit0 已置 1。GP40 正好是工程电源 LED 引脚（OemSmi.c 的 S3BreathLed/S4S5PowerLed 在操作它），所以拉高对应 LED 亮。硬件层面（万用表量引脚 76）留待上板确认。
