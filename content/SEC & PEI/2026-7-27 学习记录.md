# SEC & PEI

## 一、概述

BIOS 启动大致分几个阶段：SEC → PEI → DXE → BDS → …。SEC 和 PEI 是"最早期"的阶段，那时内存还没初始化好，资源匮乏。

## 二、SEC 阶段

### SEC 是什么

SEC = Security Phase，系统一上电就跑的第一段代码。这里"Security"不是说一定做加密验证（有些实现会做），更强调它是"最可信、最先执行"的那一段。资源少得可怜，基本只能用汇编。

### SEC 实际要做的事

1. **特殊寄存器初始化**：内存还没初始化，C 语言跑不了，只能用汇编配 MTRR、CRx 等特殊寄存器
2. **临时内存建立（Cache-as-RAM，CAR）**：C 语言要栈和堆才能跑，SEC 把 CPU 的 Cache 临时当内存用，得到一小块临时栈和堆空间，C 代码才跑得起来
3. **模式切换**：从实模式切到保护模式（x86 上电默认实模式 16 位寻址，SEC 切到 32 位保护模式）
4. **移交给 PEI**：构造 `EFI_SEC_PEI_HAND_OFF` 结构体（交接清单），调用 `SecStartup()` 进入 C 代码，最后跳到 PEI Foundation 入口

### SEC 在 ROM 里的位置

CPU 上电后第一条指令地址固定：`0xFFFFFFF0`，即 Reset Vector（复位向量）。ROM 里该位置通常放一条 `JMP` 跳到 SEC 入口，所以 SEC 代码要放在 Flash 最顶端附近。

> [!info] 复位向量
> `0xFFFFFFF0` 是 4GB 顶端的 16 字节处。整块 BIOS 固件烧在 Flash 里，但地址映射被刻意安排成"顶端是复位入口"。跟 MCU 的复位向量表一个意思，只是地址空间大得多。

**SEC 代码流程**：汇编入口 → 配寄存器 → 开 CAR → 切保护模式 → 准备 Hand-off → 跳 PEI。

## 三、PEI 阶段

### PEI 为什么存在

PEI = Pre-EFI Initialization，在 SEC 之后、DXE 之前。那时：内存没初始化、芯片组没初始化、代码还在 ROM 里跑（没搬内存、没解压）、CPU 缓存还不能用（被 CAR 占着）。DXE 是"重量级"阶段，需要内存和芯片组基本就绪。PEI 就是干"临门一脚"的活：把内存找出来、把芯片组配好，给 DXE 铺路。

### PEI 主要做什么

- 芯片组基本初始化
- 内存检测与初始化（Memory Sizing）
- 把栈从 CAR 切到真正的物理内存（Switch Stack to Memory）
- 关掉 CAR（Disable CAR）
- 启用 CPU 缓存（Enable Cache）
- 创建 HOBs（握手数据块，各阶段之间传数据的载体）
- 调 DXE IPL PPI，进 DXE

> [!note] 个人理解
> "Switch Stack to Memory"和"Disable CAR"这两步是连着的：先用真内存把栈搬过去，才能放心地把 Cache 还给 CPU 当缓存用。顺序不能乱，不然栈没了程序就崩了。

PEI 是最小代码层，复杂算法都推到 DXE 做。PEI 代码要尽量小（得塞进"容错固件块"，BIOS Recovery 时还能用）；S3 睡眠恢复路径要求最快，所以 PEI 代码路径要最短。

### 几条特殊启动路径

- **Normal Boot**：正常启动，完整硬件初始化
- **BIOS Recovery**：固件恢复，PEI 驻留在容错块里，坏固件也能救
- **ACPI S3 Resume**：从睡眠唤醒，要求速度最快，只做最少的事

### PEI 的跨平台性

PEI Foundation（PEI 核心）跨平台可移植——同一 ISA 下，一份二进制能跑在所有处理器微架构上。PEIM 用 C 写，可跨微架构编译。这点跟 SEC 的纯汇编不一样，PEI 已经能享受 C 的可移植性。

## 四、PEI 阶段的服务

**PEI Foundation（PEI Core）提供的服务：**
- PPI Services（Install/Locate/Notify）—— 模块间通信（重点）
- Boot Mode（Get/Set）—— 启动模式
- HOB Services（Create/Get）—— 创建/读取握手块
- FV Services（FindNextVolume/File/Section）—— 在固件卷里找文件
- Memory Services（Install/Allocate）—— 内存相关
- StatusCode / Reset / CpuIo / PciCfg —— 杂项服务

**PEI Dispatcher（调度器）：**
- 评估每个 PEIM 的依赖表达式（DEPEX）
- 按依赖顺序调度 PEIM
- 维护 PPI 数据库
- 一轮轮扫，直到没有可调度为止

**PEIMs（PEI 模块）**：CPU 初始化、芯片组初始化、MRC（内存初始化）、平台特定。

**DXE IPL PPI**：PEI 最后调的 PPI，负责加载 DXE Foundation 并传 HOB List。

**Firmware Volumes**：BFV（含 PEI Core）、多个 FV 存 PEIM。

> [!note] 个人理解
> 可以把 PEI Foundation 想成"操作系统内核"，PEIM 想成"驱动模块"，Dispatcher 是"驱动加载器"，PPI 就是"驱动之间互相调用的 API 表"。

## 五、PPI 机制（重点）

### PPI 是什么

PPI = PEIM-to-PEIM Interface，PEI 阶段模块之间通信的核心机制。每个 PPI 用 GUID 唯一标识。

### PPI 描述符结构

```c
typedef struct {
  UINTN      Flags;   // 标志位
  EFI_GUID   *Guid;   // PPI 的 GUID
  VOID       *Ppi;    // 指向 PPI 接口
} EFI_PEI_PPI_DESCRIPTOR;

#define EFI_PEI_PPI_DESCRIPTOR_PPI             0x10
#define EFI_PEI_PPI_DESCRIPTOR_NOTIFY_CALLBACK 0x20
#define EFI_PEI_PPI_DESCRIPTOR_NOTIFY_DISPATCH 0x40
#define EFI_PEI_PPI_DESCRIPTOR_TERMINATE_LIST  0x01
```

三个字段：`Flags`（类型）、`Guid`（唯一 ID）、`Ppi`（实际接口，函数指针集合，可能为 NULL）。

### 三大操作

- **InstallPpi（生产）**：生产者把 PPI 注册进数据库，相当于"发布接口"
- **LocatePpi（消费）**：消费者按 GUID 找 PPI，相当于"查找并使用接口"
- **NotifyPpi（监听）**：注册回调，指定 PPI 一装好就触发，相当于"等通知"

### InstallPpi 详解

`InstallPpi` 是 PEIM 把接口注册到 PPI 数据库的服务。装完之后别的 PEIM 才能通过 `LocatePpi` 发现它。

```c
static EFI_PEI_PPI_DESCRIPTOR Ps2KeyboardInputPpiList = {
    (EFI_PEI_PPI_DESCRIPTOR_PPI | EFI_PEI_PPI_DESCRIPTOR_TERMINATE_LIST),
    &gPeiAmikeycodeInputPpiGuid,
    NULL
};
Ps2KeyboardInputPpiList.Ppi = &gPeiKbd.AmiKeyCodePpi;
Status = (**PeiServices).InstallPpi(PeiServices, &Ps2KeyboardInputPpiList);
```

**两种 PPI 类型（重点区分）：**
- **信号型 PPI（Ppi = NULL）**：不提供函数，只是个"事件信号"。如 `gEfiPeiCpuIoPpiInstalledGuid`（CpuIo 已就绪）、`gEfiPeiMemoryDiscoveredPpiGuid`（内存已发现）、`gEfiPeiMasterBootModePpiGuid`（启动模式已确定）
- **服务型 PPI（Ppi ≠ NULL）**：提供真正函数。如 `gEfiPeiStallPpiGuid`（提供 Stall()）、`gEfiPeiReset2PpiGuid`（提供 ResetSystem()）、`gEfiPeiReadOnlyVariable2PpiGuid`（提供 GetVariable()）

### 完整创建一个 PPI（Stall 示例）

1. **定义接口（.h）**：定义 GUID，声明函数类型，定义接口结构体（函数指针集合）
2. **实现函数（.c）**：写函数体，造 PPI 实例填函数地址，造描述符把实例和 GUID 绑一起
3. **入口安装**：在 Entry Point 调 `PeiServicesInstallPpi(&mPpiDesc)`

```c
EFI_PEI_STALL_PPI mStallPpi = {
  1,      // Resolution = 1 微秒精度
  Stall   // 指向实现函数
};

EFI_PEI_PPI_DESCRIPTOR mPpiDesc = {
  (EFI_PEI_PPI_DESCRIPTOR_PPI | EFI_PEI_PPI_DESCRIPTOR_TERMINATE_LIST),
  &gEfiPeiStallPpiGuid,
  &mStallPpi
};

EFI_STATUS EFIAPI
StallServiceEntryPoint (IN EFI_PEI_FILE_HANDLE FileHandle,
                        IN CONST EFI_PEI_SERVICES **PeiServices)
{
  return PeiServicesInstallPpi (&mPpiDesc);
}
```

### InstallPpi 内部流程

PEI Core 收到 `InstallPpi` 调用后：验证参数 → 遍历 PpiList 直到 TERMINATE_LIST → 描述符加进 PPI 数据库（在临时 RAM 里）→ 扫已注册的 Notify 回调，GUID 匹配的立刻回调 → 触发 Dispatch（新 PPI 可能让之前依赖为 FALSE 的 PEIM 变 TRUE，Dispatcher 重新扫）。

> [!note] 个人理解
> 第 4、5 步是精髓——装一个 PPI，可能立刻"唤醒"一堆等在后面的 PEIM。这就是 PPI 解耦的关键：生产者装完就不管了，谁依赖谁自己被调度。

### LocatePpi 详解

消费者按 GUID 和 Instance 号去查 PPI。

```c
EFI_STATUS PeiServicesLocatePpi (
  IN CONST EFI_GUID *Guid,
  IN UINTN Instance,
  IN OUT EFI_PEI_PPI_DESCRIPTOR **PpiDescriptor,
  IN OUT VOID **Ppi)
```

调用示例（消费者）：

```c
EFI_PEI_STALL_PPI *StallPpi;
Status = PeiServicesLocatePpi (&gEfiPeiStallPpiGuid, 0, NULL, (VOID **)&StallPpi);
if (EFI_ERROR (Status)) {
  return Status;   // 没找到
}
StallPpi->Stall (PeiServices, StallPpi, 1000);  // 延时 1000 微秒
```

消费者的 `.inf` 要写 `[Depex]` 声明依赖，不然 Dispatcher 不会在 PPI 装好前调度它：

```ini
[Depex]
  gEfiPeiStallPpiGuid
```

> [!tip] Instance 参数
> 同一个 GUID 可以有多个实例（0、1、2…），`Instance` 用来选第几个。一般用 0 号就够。

### NotifyPpi 详解

`NotifyPpi` 注册一个回调，指定的 PPI 一装好就自动触发，适合"等某某就绪后我再做点事"。

```c
typedef struct {
  UINTN       Flags;
  EFI_GUID    *Guid;
  EFI_PEIM_NOTIFY_ENTRY_POINT Notify;
} EFI_PEI_NOTIFY_DESCRIPTOR;
```

两种 Flags：
- `NOTIFY_CALLBACK (0x20)`：回调里记日志、收集数据、更新状态，不装新 PPI
- `NOTIFY_DISPATCH (0x40)`：回调里会装新 PPI，可能让别的 PEIM 依赖满足，需要 Dispatcher 重新扫

流程：PEIM A 先注册 Notify 监听 GUID_X → PEIM B 装了 GUID_X → PEI Core 检测到，触发 A 的回调，把 PPI 指针交给 A。

> [!note] 个人理解
> Notify 和 Locate 的区别：Locate 是"我现在就要用，你有没有？"；Notify 是"你以后装好了叫我一声"。前者同步拿接口，后者异步等通知。

## 六、PEIM 调度

### DEPEX 与 TRUE 类型

每个 PEIM 的依赖写在 `.inf` 的 `[Depex]` 段，编译后生成 `.depex` 嵌进 FFS，Dispatcher 据此排顺序。

`TRUE` 表示"无依赖"，第一轮就被调度。一般是基础模块：StatusCode、SIO、NVRAM 这些，它们装好的 PPI 会被后面的 PEIM 依赖。

```ini
// NvramPei.inf
[Depex]
  TRUE
```

调度链条：TRUE PEIM 先跑 → 装上 PPI → Dispatcher 重新评估 → 满足依赖的 PEIM 被调度 → 循环。

### 调度顺序怎么定

关键一句：**PEIM 调度顺序不是你手写的，是 `[Depex]` 里的 PPI 依赖自动决定的**。Dispatcher 每轮扫所有 PEIM，把依赖满足的调度执行，直到没得可调。

调试技巧：
1. 看 `Build/` 下各 PEIM 的 `.depex` 文件
2. 串口 Debug 日志跟调度顺序
3. 某 PEIM 没被调度？查它依赖的 PPI 到底装没装

### APRIORI 文件机制

除了 DEPEX，还有"强制插队"机制：APRIORI 文件，定义在 FDF 的 `APRIORI PEI {}` 里。

| 对比项 | APRIORI 文件 | DEPEX 依赖 |
|--------|--------------|------------|
| 控制方式 | 按列表顺序强制执行 | 看 PPI 满不满足自动调度 |
| 定义位置 | FDF 的 `APRIORI PEI {}` | INF 的 `[Depex]` |
| 优先级 | 最高（先于 DEPEX） | 次之 |
| 适用场景 | 严格时序要求 | 松耦合依赖 |
| 灵活性 | 固定顺序 | 动态调度 |

Dispatcher 流程：扫描 FV 看有没有 APRIORI → 有就按列表强制调度 → 然后才进 DEPEX 循环 → 没得调了就进 DXE IPL。

APRIORI 里的 PEIM 跳过 DEPEX 评估，直接按顺序跑。所以哪怕某 PEIM 的 `[Depex]` 写 TRUE，只要它在 APRIORI 里，就按 APRIORI 的顺序来。

```fdf
APRIORI PEI {
  INF Module1.inf
  INF Module2.inf
  INF Module3.inf
}
```

> [!warning] 注意
> 项目里 `CpuIoPei` 排 APRIORI 第 6 位，它装的 CpuIo PPI 被后面 NbPei/SbPei/CpuPei 依赖。把它移出 APRIORI 可能调度就乱了——这种严格时序的就得靠 APRIORI 卡住。

### 项目实例（Platform.fdf）

**FV_BB1（启动块）APRIORI**：StatusCodePei（最先，建立状态码输出）→ PcdPei（建 PCD 库）→ ResetSystemPei（复位服务）→ FvBb1Pei（找其他 FV）→ RomLayoutPei（ROM 布局解析）

**FV_MAIN（主 FV）APRIORI**：IT8625PeiInit（SIO 串口/GPIO）→ RomDataMigration → NvramPei → SecMigrationPei → EnhancePeiVariable → CpuIoPei（CPU I/O 服务，被 NbPei/SbPei 依赖）→ TpvPei → CmosManagerPei

> [!note] 个人理解
> 看这些顺序能体会出先打好地基的思路：先有状态码输出（出错了能打印）、先有 PCD（配置数据库）、先有复位（崩了能重启），最后才是具体的芯片初始化。跟 MCU 初始化（先时钟、先 GPIO、再外设）是一个道理。
