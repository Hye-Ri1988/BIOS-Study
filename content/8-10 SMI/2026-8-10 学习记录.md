# SMI 与 SMM（System Management Mode）

SMI（System Management Interrupt）是 x86 上特权级最高的中断信号，CPU 收到后进入 SMM（System Management Mode）——一个对操作系统完全透明的执行模式，所有 SMM 处理代码运行在 SMRAM（System Management RAM）里。Flash 读写、Legacy USB、KBC 仿真、ACPI 电源切换、硬件错误记录，底层几乎都挂在 SMI Handler 上。


## 一、SMI / SMM / SMRAM 基本概念

| 概念 | 含义 |
| --- | --- |
| SMI | 不可屏蔽的中断信号，进入 SMM 的唯一途径；经 `SMI#` pin 或 APIC SMI Message 触发 |
| SMM | CPU 执行模式（386SL 引入），只能经 SMI 进入、只能经 RSM 指令退出；对 OS 完全透明，常称 "Ring -2" |
| SMRAM | 内存中的专用区域，SMM 处理程序全部在其中运行；非 SMM 模式下不可访问 |

关键链路：`SMI 信号 → CPU 进入 SMM → 在 SMRAM 执行处理程序 → RSM 退出`

SMM 处理程序由 BIOS 实现，OS 无法感知。这就是"Ring -2"的含义——比 Ring 0（OS 内核）还高一层，Hypervisor 也看不到。

## 二、SMI 的作用：为什么需要 SMM

| 用途 | 典型内容 |
| --- | --- |
| 处理系统事件 | Memory/Chipset 错误记录、System Event Error 触发 SMI |
| 控制硬件 | 特殊功能/虚拟硬件、硬件 Bug 规避、Flash ROM 读写 |
| 电源管理 | ACPI 电源功能实现、系统休眠/唤醒、Thermal 事件（PROCHOT#） |
| USB 驱动 | Legacy USB 支持、USB Mass Storage、KBC 仿真 |

> 为什么这些事必须放进 SMM？因为它们需要"在 OS 运行时、以 OS 看不见的方式"操作硬件。最典型的是 Flash 写保护：OS 层拿不到也碰不了 SPI 控制器和锁寄存器，固件更新要先把 Flash 解锁再写，这个"解锁-写-再上锁"的敏感动作放在 SMM 里，OS 全程无法干预也无法窃取。

## 三、SMI 的触发方式

### Hardware Trigger（硬件触发）

- **System Event Error**：硬件错误产生时触发
- **RTC Alarm**：实时时钟闹钟
- **GPIO Trigger**：GPIO 引脚
- **IO Trap**：读写特定 IO 端口时产生
- **SMI# Pin**：低有效、电平触发，最少保持 1 个 RTC Clock

### Software SMI（软件触发）

往 APM 控制端口写值：

```c
// Software SMI Trigger Example
// Write to APM Control Port (0xB2)
IoWrite8 (0xB2, SwSmiValue);

// PCH Register: SMI_EN (ABASE + 0x30)
// Bit 0: GBL_SMI_EN (Global SMI Enable)
// Bit 5: BIOS_EN   (BIOS SMI Enable)
```

`0xB2`（APM_CNT）是 Intel 定义的软件 SMI 触发口，写入的 8 位值就是软件 SMI 号；返回值从 `0xB3`（APM_STS）读。DXE 驱动通常不直接写 `0xB2`，而是走 `EFI_SMM_CONTROL2_PROTOCOL` 的 `Trigger()`——它内部做的就是写这两个端口。

触发 SMI 前要保证 PCH 的 `SMI_EN`（ABASE+0x30）里 `GBL_SMI_EN` 和 `BIOS_EN` 已置位，否则写 `0xB2` 不会产生 SMI。

## 四、SMM 进入与退出（CPU 视角）

### 进入流程

1. SMI 信号产生（硬件或软件）
2. CPU 自动保存上下文到 **Save State Area**（SMBASE + 0xFE00 ~ 0xFFFF）
3. CPU 跳转到 **SMI Handler 入口**（SMBASE + 0x8000）
4. Handler 执行
5. RSM 指令恢复上下文，原程序继续执行

与普通中断的差别：普通中断由 OS 软件保存现场（压栈 + IRET 恢复），SMM 由 CPU **硬件自动保存**到 SMRAM，用 **RSM**（Opcode `0x0F 0xAA`）退出。

### 两个特殊 Restart 机制

- **Auto HALT Restart**：SMI 在 HLT 指令执行时产生，Save State 记录该标志；RSM 后 CPU 回到 HLT 状态继续等待
- **I/O Restart**：SMI Handler 可修改 Save State 中的 I/O Restart 标志，使 RSM 后**重新执行**被中断的 I/O 指令。这是 IO Trap 类 SMI 的惯用技巧（如仿真原本不存在的端口读写）

## 五、SMM 状态特点

- **中断全部屏蔽**：SMM 下所有中断被屏蔽，SMI 自身也被屏蔽——SMI Handler **不可重入**。Pending 的 SMI 被锁存，RSM 后才处理
- **优先级最高**：SMI > NMI > IRQ
- **模式无关**：无论 CPU 当前是实模式、保护模式还是虚拟 8086，SMI 一律进入 SMM；RSM 后回到进入前模式

## 六、SMRAM 架构与保护

### 布局

- **TSEG**（Top of DRAM，通常 1/2/8 MB）：现代平台 SMM 主体所在，位于 DRAM 顶端
- **Compatible SMRAM**（A0000h–BFFFFh，128KB）：legacy 兼容区
- 其余为 Normal DRAM（OS 可访问）

### SMBASE 重定位

- 所有 x86 处理器 SMBASE 默认值都是 **0x30000**——多个核都用默认值的话，第一次 SMI 时互相覆盖对方的 Save State
- POST 中把每个核的 SMBASE 重定位到 TSEG 内不同地址，写入 Save State 偏移 **0x7EF8**
- 入口 SMBASE + 0x8000，Save State SMBASE + 0xFE00

> 传统做法（EDK II `PiSmmCpuDxeSmm` 的 `SmmRelocateBases()`）：默认 SMBASE 相同，AP 必须先触发第一次 SMI、在 SMM 里改好自己 Save State 里的 SMBASE 再退出，下一个 AP 才能开始——必须**串行**执行，还要用 SemaphoreHook 钩住 RSM 返回地址做同步。2023 年起引入 **SMM_BASE_HOB** 方案：PEI 阶段提前用二进制模块把每个核的 SMBASE 写进 HOB（`SmBase[Index]`），PiSmmCpuDxeSmm 直接消费 HOB，首次 SMI 可并行、省开机时间、省掉 Semaphore 逻辑。

### 保护机制

| 保护 | 说明 | 配置方式 |
| --- | --- | --- |
| TSEG Lock | 锁定 TSEG 区域，防止非 SMM 访问 | ESMRAMC 寄存器 |
| SMRAMC D_LCK | SMRAM 锁定位，防止运行时修改配置 | SMRAMC Bit 4 |
| SMRR | 防止 Cache 攻击（如缓存侧信道），非 SMM 读返回 0xFF | MSR 0x1F2 / 0x1F3 |
| SMM Code Check | 限制 SMM 仅执行 SMRAM 内代码，防代码注入 | MSR 0x4E0 |

## 七、SMM Save State Area

进入 SMM 时 CPU 把寄存器状态自动存入 SMBASE+0xFE00~0xFFFF（512 字节）。Intel 32 位与 64 位偏移不同（关键偏移）：

| 寄存器 | 32-bit 偏移 | 64-bit 偏移 |
| --- | --- | --- |
| CR0 | 7FFCh | 7FF8h |
| CR3 | 7FF8h | 7FF0h |
| EFLAGS/RFLAGS | 7FF4h | 7FE8h |
| EIP/RIP | 7FF0h | 7FD8h |
| SMBASE | 7EF8h | 7EF8h |
| EAX/RAX | 7FD0h | 7F5Ch |
| ESP/RSP | 7FE0h | 7F7Ch |
| R8–R15 | — | 7F1Ch–7F54h |

> AMD 架构偏移不同（SMBASE 在 FEF8h），见 AMD APM Vol.2 Section 10.4。EDK II 里偏移定义在 `MdePkg/Include/Register/Intel/SmramSaveStateMap.h`——写 SMM 驱动要读写寄存器现场时直接查头文件，不要自己记偏移。

## 八、SMI 处理程序执行流程与分发

```
1 SMI 信号产生 → 2 CPU 切 SMM、保存上下文 → 3 跳 SMBASE+0x8000
  → 4 Handler 判断来源、分发 → 5 RSM 退出
```

### 分发机制（BIOS 侧）

BIOS 在 SMRAM 里实现 SMI Handler 总入口：
1. 读 **SMI_STS**（ABASE+0x34）判断 SMI 来源
2. 按来源分发到子处理函数（USB、Thermal、Power、Flash…）
3. 处理完清除 SMI 状态，发送 **EOS**（End of SMI）信号
4. RSM

### EDK II 侧

- **PiSmmCore**（`MdeModulePkg/Core/PiSmmCore`）是 SMM 里的"DXE Core"，管理 SMRAM 里的驱动加载、协议注册、事件。SMM 驱动通过 `gSmst` 使用服务
- **SMM 驱动类型**：`SMM_CORE`（核心）、`SMM_DRIVER`（普通）、`DXE_SMM_DRIVER`（DXE 驱动 + 内嵌 SMM 镜像）
- **SmiHandlerRegister / SmiManage**：SMM 驱动注册自己的 Handler，`SmiManage()` 按 GUID 分发
- **SmmSwDispatch2Protocol**：`Register()` 指定 `SwSmiInputValue`，把软件 SMI 号绑定到 Handler
- **SmmControl2Protocol.Trigger()**：DXE 侧触发软件 SMI 的标准入口，内部就是 `IoWrite8(0xB2, ...)`

### SMM Communication（DXE ↔ SMM 的 IPC）

`EFI_SMM_COMMUNICATION_PROTOCOL.Communicate()` 是 Ring 0（DXE/OS）到 Ring -2（SMM）的唯一标准 IPC 通道：

1. 调用方在普通内存分配 **CommBuffer**，开头放 `EFI_SMM_COMMUNICATE_HEADER`（`HeaderGuid` 标识目标 Handler + `MessageLength`），后面跟数据载荷
2. `Communicate()` 把缓冲指针填进 `gSmmCorePrivate` 共享结构，然后调 `SmmControl2.Trigger()` 写 `0xB2` 触发 SMI
3. SMM 侧 `PiSmmCommunicationHandler` 校验缓冲后调 `SmiManage(&HeaderGuid, ...)` 分发到注册了该 GUID 的 Handler
4. Handler 处理完把返回状态写回 CommBuffer，RSM 退出，调用方读回状态

> [!warning]
> 安全性关键：SMM Handler 收到 CommBuffer 后**必须先校验**（`SmmIsBufferOutsideSmmValid()` 检查缓冲不在 SMRAM、大小合法、GUID 匹配），再处理数据。恶意构造的 CommBuffer 指针可以诱导 SMM 往 SMRAM 写——历史上大量 SMM 漏洞（CVE）源于 Handler 信任了普通世界的输入。

> 这个模型你其实已经见过：Runtime Services 笔记里变量服务的 `VariableSmmRuntimeDxe`（DXE 侧）+ `VariableSmm`（SMM 侧）就是标准 SMM Communication 用例——DXE 侧把 GetVariable/SetVariable 请求打包进 CommBuffer，触发 SMI，SMM 侧真正操作 NVRAM Flash。这解释了为什么运行时变量访问"必须经过 SMM"：NVRAM 在 Flash 里，而 Flash 写只在 SMM 里被信任执行。

## 九、SMM 编程特点

- **寻址空间**：0~4GB 平坦寻址；进入时 Paging 禁用（CR0.PG=0）、Protected Mode 禁用（CR0.PE=0）
- **无特权级别**：类似 Big Real Mode，可以执行所有指令（含 I/O 读写），可访问 0~4G 物理地址做数据读写
- **代码执行限制**：指令只能在 SMRAM 内执行（SMM Code Access Prevention 收紧代码获取），数据访问放开到整个 4GB
- **寄存器状态**：通用寄存器（GPR）进入时不保证；段寄存器初始化为特定值（ES=DS=SS=FS=GS = SMBASE Selector）

> 为什么 SMM 里"可以访问 4GB 物理内存但代码只能在 SMRAM"？因为设计意图：SMM 需要读任意物理地址（备份/修改 OS 内存数据、读系统事件），但绝不允许把攻击者代码引入执行。SMRR + SMM Code Check 双保险。

## 十、BIOS 中的 SMI 应用（实际场景）

- **Flash Operation**：SPI Flash 读写/擦除、UEFI Variable 存储、BIOS 更新——全部经 SMM 实现
- **SMBIOS**：Get/Set SMBIOS Information
- **USB Driver**：Legacy USB、USB Mass Storage、KBC（PS/2）仿真
- **Power & Thermal**：Timer 功能、Error Logging、TCO Watchdog Timer、Thermal Management（PROCHOT#）

**场景 1：POST 中按下 Power Button**：用户按电源键 → EC 产生 SMI → SMM Handler 处理关机流程 → 执行 ACPI 关机序列。

**场景 2：硬件断电前的寄存器设置（S0/S3/S4/S5 切换）**：OS 发 SCI → 固件产生 SMI 进入 SMM → SMI Handler 访问寄存器按需求配置 → 唤醒时键盘/鼠标/网卡信号触发 SMI，SMM 初始化硬件再交还 OS。

> 这里接上 ACPI 笔记的 **SCI vs SMI**：SCI 是 OS 可见的系统控制中断（OS 的 ACPI 驱动处理），SMI 是 OS 不可见的管理中断。电源状态切换的"最后一公里"（写 PM 寄存器、断电时序）由固件经 SMI 完成——OS 只发 SCI 请求，实际动手的是 SMM。

## 十一、SMI vs NMI vs IRQ 对比

| 特性 | SMI | NMI | IRQ（可屏蔽中断） |
| --- | --- | --- | --- |
| 优先级 | 最高（1） | 次高（2） | 最低（3） |
| 可屏蔽性 | 不可屏蔽 | 不可屏蔽 | 可屏蔽（IF 标志） |
| 触发方式 | SMI# Pin / APIC Msg / SW | NMI Pin / ICR | INTR Pin / IOAPIC |
| 处理入口 | SMBASE + 0x8000 | IDT Vector 2 | IDT 对应 Vector |
| 执行模式 | SMM（Big Real Mode） | 保护模式/长模式 | 保护模式/长模式 |
| 状态保存 | CPU 自动存到 SMRAM | 软件保存（IRET 恢复） | 软件保存（IRET 恢复） |
| 退出方式 | RSM 指令 | IRET 指令 | IRET 指令 |
| 对 OS 可见 | 不可见（透明） | 可见 | 可见 |

## 十二、SMM 与安全：Ring -2 的攻击面

SMI 是 x86 特权级最高的中断，运行在 "Ring -2"，OS 和 Hypervisor 都无法感知——这让 SMM 成为固件安全的关键攻击面：

- **CommBuffer 校验**：Handler 必须验证普通世界传入的缓冲（位置、大小、GUID），否则可被诱导向 SMRAM 写数据（SMM 写原语攻击）
- **SMM Lock / TSEG Lock**：POST 后期锁定 SMRAM 配置，防止运行时被篡改（D_LCK、TSEG_LOCK、SMRR）
- **Cache 攻击**：SMRR 防止缓存侧信道把 SMRAM 内容带出来
- **STM（SMI Transfer Monitor）**：Intel 提供的一种让 SMM 本身也受监控的机制，限制 SMI Handler 行为，实际启用率不高
- **SMM 漏洞面**：BIOS 更新（Capsule）、变量服务、Legacy USB 等 SMM 代码都是历史 CVE 高发区——攻破 SMM 就拿到比内核还高的权限，且 OS 侧完全看不见

## 十三、实战：OemSmi.c 源码逐段解析

> 对 AMI 实训项目 `OemPkg\Function\OemSmi` 驱动的完整分析（`C:\TEST\ib.iw68.xa03\OemPkg\Function\OemSmi`）。这个驱动干的事：系统进入 S3/S4/S5 睡眠或按下电源键的瞬间，设置电源 LED 状态、配置 Wake-on-LAN、处理 AC 掉电恢复策略。

### 13.1 文件组成

| 文件 | 作用 |
| ------------ | ------------------------------------------------ |
| `OemSmi.c` | 源码：DXE 入口 + SMM Handler |
| `OemSmi.inf` | EDK II 模块描述：`MODULE_TYPE = DXE_SMM_DRIVER` |
| `OemSmi.sdl` | AMI 声明层：`OemSmi_SUPPORT` 开关 + `INFComponent` 注册 |
| `OemSmi.cif` | AMI 组件描述（category = ModulePart），构建系统按它找到 sdl/inf |

### 13.2 INF 关键点：DXE_SMM_DRIVER 与 Depex

```inf
[Defines]
  MODULE_TYPE = DXE_SMM_DRIVER          ; 双半身：DXE 半身 + SMM 半身
  ENTRY_POINT = OemSmiEntry

[Protocols]
  gEfiSmmSxDispatch2ProtocolGuid        ; 睡眠状态 (Sx) 分发器
  gEfiSmmPowerButtonDispatch2ProtocolGuid ; 电源键分发器
  gEfiSmmSwDispatch2ProtocolGuid        ; 软件 SMI 分发器
  gEfiSmmAccess2ProtocolGuid

[Depex.common.DXE_SMM_DRIVER]
  gEfiSmmSxDispatch2ProtocolGuid AND
  gEfiSmmPowerButtonDispatch2ProtocolGuid AND
  gEfiSmmSwDispatch2ProtocolGuid AND
  gEfiSmmAccess2ProtocolGuid
```

Depex 的作用：**等三个分发协议全部就绪才加载本驱动**，否则 `InSmmFunction` 里 `SmmLocateProtocol` 会失败。

### 13.3 双半身架构（核心理解）

`DXE_SMM_DRIVER` 的 .efi 里包含两个半身，执行在两个不同世界：

```
POST 时（DXE 环境）：OemSmiEntry
  → InitAmiLib + 读 Setup 变量
  → InitSmmHandler(...)          ← AMI 封装：把 SMM 半身装入 SMRAM
        ↓ 进入 SMM 环境
SMRAM 内：InSmmFunction
  → Locate 分发协议 → Register 四个 Handler
        ↓ 之后每次 S3/S4/S5/电源键 SMI 到来
  → 对应 Handler 在 SMM 里操作 IT8786 / PM1 寄存器
```

### 13.4 入口函数：OemSmiEntry（DXE 半身）

```c
EFI_STATUS OemSmiEntry(...)
{
    InitAmiLib(ImageHandle, SystemTable);      // AMI 库初始化，拿 pRS/pSmst 等
    DataSize = sizeof(SETUP_DATA);
    Status = pRS->GetVariable(L"Setup", &gEfiSetupGuid, NULL, &DataSize, &SetupData);
    return InitSmmHandler(ImageHandle, SystemTable, InSmmFunction, NULL);
}
```

三个要点：
- `SETUP_DATA SetupData` 是**文件级全局变量**，DXE 侧从 NVRAM 读好，之后 SMM 侧直接使用。这是 SMM 驱动读 Setup 配置的标准做法——SMM 里没有变量服务，先在 DXE 侧读好、拷进 SMRAM
- `pRS->GetVariable(L"Setup", ...)` 读 AMI 的 Setup 变量（`AC_Support`、`WakeOnLan` 都在里面）
- `InitSmmHandler` 是 AMI 封装：加载 SMM 镜像并在 SMM 环境回调 `InSmmFunction`。**执行到这一步，代码已经换到 SMRAM 里运行了**

### 13.5 注册函数：InSmmFunction（SMM 半身）

跑在 SMRAM 里，任务只有一个：**把本驱动的处理函数挂到系统 SMI 分发器上**。

```c
// 1. 找到三个分发协议
pSmst->SmmLocateProtocol(&gEfiSmmSxDispatch2ProtocolGuid, ...);       // 睡眠分发器
pSmst->SmmLocateProtocol(&gEfiSmmSwDispatch2ProtocolGuid, ...);       // 软件 SMI 分发器
pSmst->SmmLocateProtocol(&gEfiSmmPowerButtonDispatch2ProtocolGuid, ...); // 电源键分发器

// 2. 注册 S3/S4/S5 三个睡眠 Handler（Sx 分发器）
AMI_SMM_SX_DISPATCH_CONTEXT S3DispatchContext = {SxS3, SxEntry};   // Type=S3, Phase=Entry
SxDispatch->Register(SxDispatch, S3SleepSmiOccurred, &S3DispatchContext, &hS3Smi);
// S4、S5 同理

// 3. 注册电源键 Handler
pPowerButton->Register(pPowerButton, PowerButtonActivated, &PowerButtonContext, &Handle);
```

对应第 8 节的分发机制：**SMM 驱动不自己写"中断向量表"，而是向系统分发器注册回调**。注册上下文 `{SxS3, SxEntry}` 的含义是"我在系统进入 S3 睡眠的那一刻被调用"（Type=睡眠类型、Phase=Entry 进入 / Exit 唤醒）。

> `AMI_SMM_SX_DISPATCH_PROTOCOL` 是个 `#define` 宏（行 43），没有结构体定义——它只是 `EFI_SMM_SX_DISPATCH2_PROTOCOL` 的别名；后者又是 `EFI_MM_SX_DISPATCH_PROTOCOL` 的 typedef。真实结构体在 `MdePkg/Include/Protocol/MmSxDispatch.h`。查这类"找不到定义"的协议，沿 `#define → typedef → struct` 一路追到 `Mm*Dispatch.h`。

### 13.6 四个 Handler：真正干活的地方

S3 / S4 / S5 / 电源键四个 Handler 结构几乎一样，做三件事：AC 策略 + LED + WOL。

```c
EFI_STATUS S5SleepSmiOccurred(...)   // S5（软关机）进入瞬间被调
{
    AfterG3();                    // AC 掉电恢复策略（写 IT8786）
    S4S5PowerLed();               // 电源 LED 设为 S4/S5 常亮状态
    if (SetupData.WakeOnLan == 1) {
        LanWakeEnable();          // 按 Setup 开关配置网络唤醒
    } else {
        LanWakeDisable();
    }
    return EFI_SUCCESS;
}
```

区别只在 LED 函数：S3 用 `S3BreathLed()`（呼吸灯），S4/S5/电源键用 `S4S5PowerLed()`。四个函数签名都是标准的 SMM Handler 形态（`DispatchHandle / DispatchContext / CommBuffer / CommBufferSize`）——即使不用 CommBuffer，签名也要保持，这是 SMM 回调的统一接口。

### 13.7 硬件操作：IT8786 Super I/O（LED 与 AC 策略）

`S3BreathLed` / `S4S5PowerLed` / `AfterG3` 都在操作 **IT8786 Super I/O 芯片**，通过索引/数据两个 IO 端口访问内部寄存器。宏定义在 `AmiModulePkg/IO/IT8786/IT8786.sdl`（`TargetH = Yes`，构建期生成到 .h）：

```
IT8786_CONFIG_INDEX = 0x2E   ; 索引端口（选寄存器号）
IT8786_CONFIG_DATA  = 0x2F   ; 数据端口（读/写该寄存器值）
IT8786_LDN_SEL_REGISTER = 0x07
IT8786_LDN_GPIO      = 0x07  ; GPIO 逻辑设备号
```

操作套路固定为三步（以 `S4S5PowerLed` 为例）：

```c
// ① 进配置模式（解锁序列，IT87xx 固定）
IoWrite8(0x2E, 0x87); IoWrite8(0x2E, 0x01); IoWrite8(0x2E, 0x55);
#if (IT8786_CONFIG_INDEX == 0x2E)
    IoWrite8(0x2E, 0x55);   // 0x2E 口用 0x55 结尾
#else
    IoWrite8(0x2E, 0xAA);   // 0x4E 口用 0xAA
#endif

// ② 选择逻辑设备 LDN=0x07（GPIO），配置其寄存器
IoWrite8(0x2E, 0x07);       // LDN 选择寄存器
IoWrite8(0x2F, 0x07);       // 选 GPIO 逻辑设备
IoWrite8(0x2E, 0xF8);       // GPIO 配置寄存器（GP LED 功能选择）
IoWrite8(0x2F, 0x00);

// ③ 退出配置模式
IoWrite8(0x2E, 0x02); IoWrite8(0x2F, 0x02);
```

`S3BreathLed` 多了 GP40 的配置：读改写 0xC3 清 BIT0（GP40 输出电平）、0xF8=0x20（GP40 功能）、0xF9=0x02（**GP LED 闪烁频率 1Hz、blinking 输出低有效**）——这就是"呼吸灯"的来源。`AfterG3` 在 `SetupData.AC_Support == 2`（AC 掉电后自动开机）时清 0xF4 的 BIT5。

> MCU 类比：Super I/O 是"用 IO 端口访问内部寄存器"的芯片，改寄存器要先解锁（进配置模式）、改完锁回（出配置模式），和给 MCU Flash 写之前开写保护是同一思路。`0x87 0x01 0x55` 是 IT87xx 系列的固定解锁口令。

### 13.8 Wake-on-LAN：操作 PCH 的 PM1 寄存器

```c
VOID LanWakeEnable() {
    // 清 BIT30 = 允许 Wake# 引脚唤醒
    IoWrite32(ACPI_BASE_ADDRESS + R_ACPI_IO_PM1_STS,
        IoRead32(ACPI_BASE_ADDRESS + R_ACPI_IO_PM1_STS) & ~BIT30);
    // BIT14 写 1 清除（唤醒状态位）
    IoWrite32(ACPI_BASE_ADDRESS + R_ACPI_IO_PM1_STS,
        IoRead32(ACPI_BASE_ADDRESS + R_ACPI_IO_PM1_STS) | BIT14);
}
```

`R_ACPI_IO_PM1_STS = 0x00`（定义在 `Intel/ClientOneSiliconPkg/Include/Register/PmcRegs.h`），即 PCH 的 **PM1 Status 寄存器**——正是 ACPI 笔记里 FADT 的 `PM1a_EVT_BLK` 指向的那块寄存器。逻辑：允许 WOL 就清 BIT30，禁止就置 BIT30；BIT14 写 1 清唤醒状态（PCH 寄存器写 1 清除的约定）。

> 这也串起一条线：**OS 通过 ACPI 表知道 PM1 在哪，固件在 SMM 里直接写同一组寄存器——两边操作的是同一个物理东西。**

### 13.9 SDL：构建系统如何收编这个驱动

```sdl
TOKEN
    Name  = "OemSmi_SUPPORT"
    Value  = "1"
    Master = Yes
    Token  = "AMI_FSP_BIN_SUPPORT" "=" "0"    ; FSP 方案下关闭
End

INFComponent
    Name  = "OemSmi"
    File  = "OemSmi.inf"
    Package  = "OemPkg"
    ModuleTypes  = "DXE_SMM_DRIVER"
End
```

呼应 Library Mapping 笔记：SDL 是声明层，`OemSmi_SUPPORT` token 决定是否编入，`INFComponent` 声明模块，构建时 AMISDL 生成 DSC/FDF 条目。`IT8786_CONFIG_INDEX` 等宏也是 SDL Token（`TargetH=Yes` 生成头文件）——**在 .c 里找不到它们的 `#define`，因为它们由构建工具生成**。

### 13.10 运行流程总览（一句话串起全驱动）

```
用户睡眠/关机（S3/S4/S5）或按电源键
  → 芯片组产生 SMI → CPU 进 SMM（保存现场到 SMRAM）
  → Sx/PowerButton 分发器调 OemSmi 注册的 Handler
  → Handler 在 SMRAM 里操作 IT8786 GPIO（LED、AC 策略）和 PM1（WOL）
  → RSM 退出，睡眠流程继续
```

**为什么要放 SMM 而不是普通 DXE 驱动？** 睡眠/关机瞬间 OS 已进入不可信甚至冻结状态，普通驱动代码没有可靠运行机会；SMI 是最高优先级、无论 OS 什么状态都被 CPU 强制接管。电源 LED 在睡眠后还要保持显示、WOL 要保证睡眠期间网卡能唤醒——这些"睡后仍生效"的硬件配置，只能由 OS 看不见的 SMM 完成。

## 术语表

- **SMI**：System Management Interrupt，不可屏蔽、优先级最高的中断，进入 SMM 的唯一途径
- **SMM**：System Management Mode，386SL 引入的 CPU 执行模式，对 OS 透明，称 "Ring -2"
- **SMRAM**：System Management RAM，SMM 处理程序的专用内存区，非 SMM 模式不可访问
- **RSM**：Resume from SMM 指令（0F AA），退出 SMM 的唯一途径
- **SMBASE**：SMM 基地址（默认 0x30000），入口在 SMBASE+0x8000，Save State 在 SMBASE+0xFE00
- **TSEG**：Top of DRAM 的 SMRAM 区域（1/2/8MB），现代平台 SMM 主体所在
- **Save State Area**：CPU 进入 SMM 时自动保存寄存器现场的区域
- **EOS**：End of SMI，Handler 处理完清除 SMI 状态后发送的信号
- **SMRR**：SMM Range Register（MSR 0x1F2/0x1F3），防止缓存攻击、非 SMM 读返回 0xFF
- **APM_CNT（0xB2）/ APM_STS（0xB3）**：软件 SMI 触发/状态端口
- **EFI_SMM_COMMUNICATION_PROTOCOL**：DXE/OS ↔ SMM 的标准通信协议，基于共享 CommBuffer + 软件 SMI
- **PiSmmCore**：EDK II 的 SMM 核心，SMRAM 里的 "DXE Core"
- **STM**：SMI Transfer Monitor，Intel 用于监控/约束 SMI Handler 的机制
- **PROCHOT#**：处理器过热信号，可触发 SMI 做 Thermal 处理
