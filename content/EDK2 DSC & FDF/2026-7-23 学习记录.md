# EDK2 DSC & FDF

## 什么是 EDK II?

EDK II 是 UEFI 固件的**开源参考实现与开发环境**，提供符合 UEFI 和 PI 规范的固件基础代码（启动服务、运行时服务、协议等）。

## 核心组件

- **DSC（平台描述文件）**：定义要构建的模块和配置
- **FDF（Flash 描述文件）**：定义固件镜像内容和布局
- **INF（模块信息文件）**：描述模块源码和构建规则
- **DEC（包声明文件）**：声明包的公共元素
- **BaseTools**：构建工具链，从源码生成 FV 和最终固件镜像（FD）

> DSC 与 FDF 必须配合使用才能生成可引导镜像。

## DSC 文件规范

### DSC 的作用

- **定义平台组成**：指定平台包含哪些模块（PEI/DXE/UEFI 应用），各模块的 INF 文件
- **库类映射**：决定模块链接哪个库实例
- **PCD 设置**：覆写和固定平台配置值（内存大小、串口基址、安全启动等）
- **编译与构建选项**：编译器标志、优化级别、构建目标（调试/发布）

### 典型结构

- **`[Defines]`**：平台名称、GUID、版本、输出目录、支持的架构（IA32/X64/AARCH64）、SKU
- **`[LibraryClasses]`**：库类名 → 库实例 INF 映射，可按模块阶段细分（`common.PEIM`、`common.DXE_DRIVER`）
- **`[Components]`**：要编译的所有模块（`.inf`），平台的"菜单"
- **`[PcdsFeatureFlag]`、`[PcdsFixedAtBuild]`、`[PcdsDynamic]` 等**：PCD 赋值
- **`[BuildOptions]`**：额外的编译/链接参数

### 语法规则

- 每个条目必须写在同一行内
- 路径与文件名**区分大小写**，禁止 `/../`、`/./`
- 多值用**竖线 `|`** 分隔而非逗号（`IA32|X64|AARCH64`、`DEBUG|RELEASE`）
- `DSC_SPECIFICATION` 用十六进制标识规范版本

### `[Defines]` 节

| 字段 | 含义 | 必需 |
| --- | --- | --- |
| `PLATFORM_NAME` | 平台名称 | 是 |
| `PLATFORM_GUID` | 平台唯一标识符 | 是 |
| `PLATFORM_VERSION` | 平台版本号 | 常用 |
| `DSC_SPECIFICATION` | 规范版本号（Hex） | 是 |
| `OUTPUT_DIRECTORY` | 构建产物输出目录 | 可选 |
| `SUPPORTED_ARCHITECTURES` | 支持的 CPU 架构（`IA32X64`） | 是 |
| `BUILD_TARGETS` | 构建目标（`DEBUG\|RELEASE`） | 是 |
| `SKUID_IDENTIFIER` | 默认 SKU 标识 | 可选 |

> [!warning] 易踩的坑
> `SUPPORTED_ARCHITECTURES` 和 `BUILD_TARGETS` 用 `|` 分隔，不是逗号。

### 处理顺序与预处理

构建工具按固定流程解析（非文件顺序）：`[Defines]` → `[BuildOptions]` → `[SkuIds]` → `[LibraryClasses]` → PCD 各节 → `[Components]` → `[UserExtensions]`

DSC 支持预处理：`DEFINE` 宏、`!if/!else/!endif` 条件编译、`!include` 引入其他文件、C 风格表达式（可引用 PCD）。

### `[LibraryClasses]` 节

- **库类（Library Class）= 接口**：只在头文件（.h）声明函数原型，不编译成代码
- **库实例（Library Instance）= 实现**：有自己的 C 文件和 INF，本身也是一个模块
- DSC 的 `[LibraryClasses]` 干一件事：把库类名绑定到某个库实例的 `.inf`

举例：`DebugLib` 至少有两种实例——`BaseDebugLibNull`（空实现，Release 用）和 `BaseDebugLibSerial`（打串口，Debug 用）。

映射粒度与优先级（越具体越先生效）：通用 `[LibraryClasses]` < 阶段级 `[LibraryClasses.common.DXE_DRIVER]` < 组件级（`[Components]` 内 `<LibraryClasses>`）。即**组件级 > 阶段级 > 通用级**。

> 这体现了 EDK II 的设计哲学：同一套接口，不同执行阶段挂不同实现。

### PCD 节

PCD（Platform Configuration Database）是"可配置的平台参数仓库"，让固件行为通过改配置而不是改代码来调整。

| 类型 | 值何时确定 | 能不能改 |
| --- | --- | --- |
| `FeatureFlag` | 构建时 | 不可改（`#ifdef` 编译开关） |
| `FixedAtBuild` | 构建时烧进二进制 | 不可改（`const`/`#define`） |
| `PatchableInModule` | 构建时定，留在模块固定位置 | 可用工具补丁改，不用重编但需重烧 |
| `Dynamic`/`DynamicEx` | 运行时数据库 | 运行时可读写 |

> [!warning] 常见误解
> "PCD 不重编就能改功能"只适用于 **Dynamic** 和 **PatchableInModule**；FeatureFlag/FixedAtBuild 本质是构建时定死。

示例：
```ini
[PcdsFeatureFlag]
  gEfiMdePkgTokenSpaceGuid.PcdDebugPropertyMask|TRUE
[PcdsFixedAtBuild]
  gEfiMdePkgTokenSpaceGuid.PcdMaxVariableSize|0x10000
[PcdsPatchableInModule]
  gEfiMdePkgTokenSpaceGuid.PcdDebugPrintErrorLevel|0x80000000
[PcdsDynamicDefault]
  gEfiMdePkgTokenSpaceGuid.PcdPlatformBootTimeOut|L"5"
```

## FDF 文件规范

### 作用

回答"镜像怎么摆、放在 Flash 哪个位置"。在 DSC 选定模块之后，把编译产物组织成可烧录的固件镜像（FD）。

### 章节结构

- `[Defines]`：FDF 自身定义信息
- `[FD]`：Flash 设备物理布局——地址、大小、分区
- `[FV]`：固件卷内容组织——包含哪些模块/文件
- `[Capsule]`：固件更新包定义
- `[Rule]`：模块如何被打包进 FV 的规则
- `[OptionRom]`：PCI Option ROM 定义

### `[FD]` 节：物理 Flash 布局

关键字段：`BaseAddress`、`Size`、`BlockSize`/`NumBlocks`、`ErasePolarity`。

FD 内部按 `偏移量|大小` 划分区域（Region），每个区域映射到某个 FV，或存放 `DATA`/`FILE`/`CAPSULE`：

```ini
[FD.MyPlatform]
  BaseAddress   = 0xFF000000
  Size          = 0x01000000   # 16MB
  ErasePolarity = 1
  BlockSize     = 0x10000      # 64KB
  NumBlocks     = 0x100        # 256 块
  0x00000000|0x00100000        # 1MB 区域 -> FVMAIN
  FV = FVMAIN
  0x00100000|0x00080000        # 512KB 区域 -> NVRAM
  DATA = { 0x00, 0x00, 0x00, 0x00 }
```

### `[FV]` 节：逻辑固件卷

- 用 `INF` 语句引用 DSC 中构建出的模块
- 支持**嵌套 FV** 与 **COMPRESS** 压缩
- 可指定对齐方式（FvAlignment）、用 GUID 命名
- 内容类型：`INF`（模块）、`FILE`（原始文件）、`FV`（嵌套卷）、`APRIORI`（优先加载列表）等

```ini
[FV.FVMAIN]
  BlockSize      = 0x10000
  NumBlocks      = 0x10
  FvAlignment    = 16
  INF MdeModulePkg/Core/Dxe/DxeMain.inf
  INF MdeModulePkg/Universal/Variable/RuntimeDxe/VariableRuntimeDxe.inf
```

### `[Capsule]` 与 `[Rule]` 节

- **Capsule**：描述可更新的固件包，配合 FMP（固件管理协议）实现 UEFI Capsule Update
- **Rule**：定义模块打包方式——文件类型（PE32/TE/UI）、依赖项（PEI_DEPEX/DXE_DEPEX）、压缩方式（PI_STD），可按模块类型分别定义

## DSC 与 FDF 的关系 & 构建流程

- **DSC = What & How**：构建哪些模块、用哪个库实例、PCD 取什么值
- **FDF = Where & Layout**：模块摆进 Flash 哪个分区、如何组织成 FV、是否压缩

> 单独有 DSC 只能编译出模块，单独有 FDF 没有模块可装；两者结合 + BaseTools 才能产出可引导的固件镜像（FD）。

**完整构建流程**：解析 DSC → 编译模块（按 INF + BuildOptions + PCD）→ 解析 FDF → 生成 FV（按 Rule 打包）→ 生成 FD 镜像（按偏移放置）。

## 术语表

| 术语 | 英文 | 说明 |
| --- | --- | --- |
| DSC | Platform Description | 平台构建内容与配置 |
| FDF | Flash Description | 固件镜像布局与结构 |
| FD | Flash Device | 物理 Flash 设备定义 |
| FV | Firmware Volume | 逻辑固件卷，装载模块 |
| PCD | Platform Config Database | 平台配置数据库 |

| Capsule | Update Capsule | 固件更新包 |

## 最佳实践

- DSC 与 FDF 放在同一目录
- 为平台指定有意义、唯一的 GUID
- 合理组织 FV 结构（PEI、DXE、NVRAM 各成区域）
- 用 `[Rule]` 统一管理打包规则
- 注意路径大小写与 `|` 分隔符等格式细节

## 从 MCU/Keil 视角理解 EDK II 机制

### 1. BUILD_TARGETS（DEBUG|RELEASE）与 Keil 优化等级（O0–O3）

- **`DEBUG|RELEASE` 不是优化等级，是"构建配置"的名字**。它决定一整套行为：优化等级、调试符号、断言/DebugLib、链接哪个库实例
- 真正的 `-O0`/`-O2` 写在 `tools_def.txt` 和 DSC `[BuildOptions]` 里。惯例是 RELEASE 套 `-O2`、DEBUG 套 `-O0 -g`
- **Keil 类比**：O0–O3 只是优化开关；Keil 没有内建 Debug/Release 切换，需手动配置。EDK II 相当于把"配置 + 优化旋钮"打包成一层开关
- `BUILD_TARGETS` 名字只是标签可自定义；优化等级由 `[BuildOptions]` 绑定

### 2. INF 文件的三层定位

- **INF = 单个模块的配方**：是什么、用什么源码、要哪些接口
- **DSC = 平台级清单**：构建哪些模块、库类用哪个实例、PCD 取什么值
- **FDF = 镜像级布局**：构建好的模块摆进 Flash 哪个 FV

> 同一个 INF 被两头用：DSC 决定"怎么构建"，FDF 决定"产物放哪里"。

**Keil 类比**：相当于把 Keil 工程里"某个 Group 的 .c 属于哪个 Target、include 路径、链接哪些库"这些元数据单独做成一份文件。区别是 Keil 信息散落在 `.uvprojx` 里跟着工程走，而 EDK II 让每个模块自带 INF，可被不同平台、不同 DSC 复用。

### 3. 库类映射的本质

- 库类 = 接口（.h 声明函数原型）；库实例 = 实现（.c + .inf）
- DSC `[LibraryClasses]` 把库类名绑定到库实例 INF → **接口不变、实现可换**（依赖注入/策略模式）

**MCU 对比**：MCU 常用"结构体函数指针"（`typedef struct { void (*Init)(void); ... } DebugDriver;`，填 `gNullDriver`/`gSerialDriver` 两份实现）。EDK II 库类是那个"接口形状"，库实例是两份实现，DSC 映射是"选一个"。

**关键差异**：EDK II 在**链接时**把 `DebugPrint` 符号直接绑到选中的实现上，零运行时开销；MCU 写法通常是运行时拿着函数指针去调。更直接的对应：EDK II 的 **Protocol** 在 DXE 阶段就是运行时结构体函数指针（如 `EFI_SIMPLE_TEXT_OUTPUT_PROTOCOL`）。

### 4. PCD 深入

**一句话**：PCD 是"平台的一个设置项"，有名字、有值；代码按名字 `PcdGetXxx(名字)` 读取，值写在 DSC 里，不在 `.c` 里。

**例（串口波特率）**：不用 PCD → `#define BAUD 115200` 写死，换板子要改 `.c` 重编；用 PCD → `Baud = PcdGet32(PcdSerialBaudRate);`，值写在 DSC 的 `[PcdsFixedAtBuild]`，换板子只改 DSC 一行。

**三个文件分工**：DEC 登记（默认值和类型）→ DSC 赋值 → 代码 `PcdGetXxx()` 读取 → FDF 把动态 PCD 默认值放进 VPD 区域。

**Keil 类比**：PCD 是 EDK II 对 MCU 里 `#define` + `#ifdef` + 常量表那套做法正式化、系统化的替代——类型安全、集中管理、构建工具自动生成访问宏。

### 5. 综合实例：DebugLib + PCD 端到端链路

```c
// 库类头文件（接口，只声明）
// Library/DebugLib.h
VOID DebugPrint (UINTN Level, CONST CHAR8 *Format, ...);
```

```c
// 两个库实例（实现，各带 .inf）
// BaseDebugLibNull.c —— 空实现（Release 用）
#include <Library/DebugLib.h>
VOID DebugPrint (UINTN Level, CONST CHAR8 *Format, ...) { /* 什么都不做 */ }

// BaseDebugLibSerial.c —— 串口实现（Debug 用），内部读 PCD
#include <Library/DebugLib.h>
#include <Library/PcdLib.h>
VOID DebugPrint (UINTN Level, CONST CHAR8 *Format, ...) {
  if (!PcdGetBool (PcdDebugPropertyMask)) return;
  SerialOutput (Format);
}
```

```ini
# DSC 把接口指向实现，并给 PCD 赋值
[LibraryClasses]
  DebugLib|MdePkg/Library/BaseDebugLibSerial/BaseDebugLibSerial.inf
[PcdsFeatureFlag]
  gEfiMdePkgTokenSpaceGuid.PcdDebugPropertyMask|TRUE
```

**构建后发生的事**：链接器把 `DebugPrint` 符号直接绑到 `BaseDebugLibSerial`（静态链接，零运行时开销）；`PcdGetBool()` 因是 FeatureFlag 被直接替换成常量，`if(FALSE)` 整段被优化掉；想改行为只动 DSC。

> 库类管"行为"（调哪个函数实现），PCD 管"数据"（用哪个配置值）。两者都让模块源码保持干净、平台配置集中可控。
