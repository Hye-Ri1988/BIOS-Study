# UEFI Shell 调试命令与 APP 开发

UEFI Shell 是预启动阶段（ExitBootServices 之前）的交互式命令行环境，本质是一个 `UEFI_APPLICATION`（通常是 `Shell.efi`）。它在 DXE/BDS 阶段加载，安装 `EFI_SHELL_PROTOCOL` 和 `EFI_SHELL_PARAMETERS_PROTOCOL`，提供文件浏览、驱动加载、设备枚举、内存查看、脚本执行等能力。BIOS 调试里绝大多数"看一眼硬件状态"的需求，在 Shell 里敲几条命令就能完成，不必重新编译固件。

理解 Shell 的关键：它和 Boot Services 的 Handle/Protocol 模型是同一套东西。Shell 里的 `devices`、`dh`、`drivers`、`connect` 全是围绕 Handle 数据库和 Protocol 在转。

## Shell 的架构：命令从哪来

Shell 本身是一个应用，认识的命令分三类：

- **内置命令（Built-in）**：链接进 `Shell.efi` 的库，由 `ShellCommandLib` 在库构造期注册到内部链表
- **外部命令（External）**：独立的 `.efi` 文件，敲路径或文件名执行（如 `fs0:\EFI\TOOLS\RU.efi`）。`load` 加载驱动类外部命令，直接跑 `.efi` 是应用类
- **NSH 脚本**：`.nsh` 文本文件，由 Shell 解释执行

### 命令分级（ShellPkg 构建期控制）

EDK II 的 ShellPkg 把命令按"能力层级"和"功能分组"切分，构建时由 PCD 决定哪些编进镜像。有些平台 Shell 没有 `pci`/`mm` 不是命令丢了，是构建时没启用。

| 层级 | 名称 | 包含的命令 | 用途 |
| --- | --- | --- | --- |
| 0 | Minimal | 无交互命令，仅 Shell 协议 | 极简环境 |
| 1 | Scripting | `for` `if` `goto` `shift` `stall` `exit` | 脚本控制流 |
| 2 | Basic | `ls` `cd` `cp` `mv` `rm` `map` `mkdir` `set` `load` `reset` `date` `time` | 文件与设备管理 |
| 3 | Interactive | `alias` `cls` `echo` `help` `pause` `type` `ver` | 完整交互 |

还有 Profile 组（独立开关）：
- **Drivers1**：`connect` `devices` `devtree` `dh` `disconnect` `drivers` `drvcfg` `openinfo` `reconnect` `unload`
- **Debug1**：`comp` `dblk` `dmem` `dmpstore` `edit` `hexedit` `memmap` `mm` `mode` `pci` `sermode` `setvar` `smbiosview`
- **Network1/2**：`ifconfig` `ping` `ifconfig6` `ping6`

> 量产固件常只编 Level 2 + 部分 Profile。`mm`、`dmpstore` 敲了报"未找到命令"，基本就是构建时把 Debug1 组关掉了。

### 进入 Shell 的方式

BIOS Setup → Boot → UEFI Shell；启动菜单（F12）→ UEFI Shell；写 `startup.nsh` 自动执行；部分主板编进固件（Built-in Shell）。

## 文件系统与设备映射

Shell 自动把存储设备映射成盘符，`map` 列出全部映射。

| 前缀 | 含义 |
| ------- | ---------------------------- |
| `fs0:` | 第一个 FAT 分区（通常是 EFI 系统分区 ESP） |
| `fs1:` | 第二个 FAT 分区 |
| `blk0:` | 块设备（原始磁盘/分区） |
| `hd0:` | 硬盘 |
| `cd0:` | 光盘 |
| `nx0:` | 网络接口 |

路径用 DOS 风格：`fs0:\EFI\BOOT`，冒号后反斜杠表示根。`map -r` 重新枚举设备，`map -b` 分页。

## 文件系统与导航命令

| 命令 | 功能 | 示例 |
| --- | --- | --- |
| `ls` | 列目录，支持 `*.efi` 通配符 | `ls fs0:\EFI\BOOT` |
| `cd` | 切换目录 | `cd fs0:\EFI` |
| `cp` | 复制，可跨文件系统 | `cp fs0:\a.efi fs1:\` |
| `mv` | 移动/重命名（同文件系统内） | `mv old.efi new.efi` |
| `rm` | 删除，不可恢复 | `rm fs0:\temp.efi` |
| `mkdir` | 建目录 | `mkdir fs0:\TEST` |
| `type` | 查看文本文件 | `type startup.nsh` |
| `edit` | 内置全屏文本编辑器 | `edit startup.nsh` |
| `comp` | 二进制比较 | `comp a.efi b.efi` |

实用技巧：`Tab` 自动补全；任何命令加 `-?` 看帮助、`-b` 分页；输出重定向 `pci > pci_log.txt`；FAT32 单文件 4GB 上限。

## 硬件与设备调试命令

### pci — PCI/PCIe 设备枚举

```
Shell> pci                      # 列出所有 PCI 设备
Shell> pci -b 0 -d 2 -f 0 -v   # 查特定设备详情（含 BAR）
Shell> pci -b                  # 输出所有设备的 BAR 信息
```

输出字段：`Seg`、`Bus`（0~255）、`Dev`（0~31）、`Func`（0~7）、`Vendor`/`Device`（VID/DID）、`Class Code`。`-b` 显示 BAR 基地址，`-s` 显示桥设备的 Subordinate Bus。

> `VID=FFFF` 表示设备没响应——没焊、没上电或配置空间访问失败。对比 pci 输出和 PCH EDS 设备列表，能快速确认某个控制器是否正常枚举。

### memmap — 物理内存映射（E820）

`memmap` 显示系统物理内存布局，对应固件传给 OS 的 E820 表。

| 内存类型 | E820 Type | 说明 |
| --- | --- | --- |
| Available | 1 | OS 可用 |
| Reserved | 2 | 硬件/固件占用（含 Boot/DXE/Runtime 代码区） |
| ACPI Reclaimable | 3 | ACPI 表数据，OS 可取用后释放 |
| ACPI NVS | 4 | S3 睡眠恢复数据，不可回收 |

调试要点：`TOLUD` 位置是否与 MMIO 冲突、4GB 以上内存是否映射、UMA 共享显存是否保留。`memmap`、`RU.efi`（Alt+F2）、`RW.exe` 三者看 E820 应一致，可交叉验证。

> `Runtime Services Code/Data` 在 memmap 里显示为 Reserved/Type 2——带 `EFI_MEMORY_RUNTIME` 属性，OS 建页表时必须保留映射。

### mm / dmem / mem — 内存与寄存器查看修改

`mm`（Memory Modify）是 Shell 里最接近硬件调试器的命令，能直接读写 MEM、MMIO、IO、PCI、PCIe 地址空间：

```
Mm <address> [<value>] [-w 1|2|4|8] [-MEM|-MMIO|-IO|-PCI|-PCIE] [-n]
```

- 不指定 `-n` 进入交互模式；`-n` 非交互直接写
- `-MMIO` 访问设备内存，`-IO` 访问 IO 端口（如 RTC 的 0x70/0x71），`-PCI` 访问 PCI 配置空间

`dmem`（Dump Memory）只读转储：`Dmem [-b] [<address>] [<size>] [-MMIO]`。不带参数直接转储 EFI System Table。

> [!warning]
> `mm` 写寄存器是"随心所欲"的，写错可能直接挂死平台或破坏硬件状态。和 RU 工具一样属于危险操作，动之前确认地址和宽度。

### devices / drivers / dh

三者是排查"设备—驱动—协议"关系的核心组合：

- `devices`：列出所有 EFI Handle（Controller / Device 两类），带 Device Path
- `drivers`：列出已加载驱动、名称、版本、绑定的 Controller
- `dh`（Dump Handle）：看指定 Handle 上安装的所有 Protocol，最细粒度

```
Shell> dh            # 所有 Handle 简要
Shell> dh 52         # 看 Handle 52
Shell> dh -p <Guid>  # 按 Protocol 过滤
```

常见协议：`TextInput`、`TextOutput`、`FileSystem`、`BlockIO`、`DevPath`、`LoadedImage`、`DiskIO`、`SerialIO`、`UsbIO`、`PciIO`。

> `devices` 看"设备 Handle 树"，`drivers` 看"驱动镜像列表"。一个驱动可绑定多个设备（如 XHCI 驱动绑到多个 USB 控制器）。`dh` 看到的就是 Handle 数据库里每个 Handle 上挂的 Protocol 集合。

### devtree — 设备树

树形展示 Parent-Child 拓扑，从 `PciRoot(0x0)` 往下展开桥、VGA、XHCI、LPC 等。配合 `map` 用：`devtree` 看层级位置，`map` 看文件系统映射。

### connect / disconnect / load / unload

```
Shell> load fs0:\EFI\TOOLS\MyDriver.efi   # 加载驱动（不自动执行）
Shell> connect -all                        # 连接所有设备（重枚举常用）
Shell> connect 52                          # 连接特定 Handle
Shell> disconnect 52                       # 断开，用于重新初始化
Shell> unload <Handle>                     # 卸载驱动
```

驱动调试标准流程：`load` → `drivers` 确认加载 → `connect -all` → `devices` 看绑定 → `dh` 验证 Protocol。

## 变量与启动项命令（衔接 Runtime Services）

| 命令 | 功能 | 对应接口 |
| --- | --- | --- |
| `dmpstore` | 列出/转储所有 NVRAM 变量 | `GetNextVariableName` + `GetVariable` |
| `setvar` | 创建/修改/删除变量 | `SetVariable` |
| `bcfg` | 管理启动项（Boot####/BootOrder） | 变量服务 + LoadFile |

```
dmpstore                          # 列出全部变量
dmpstore -guid 8BE4DF61-...       # 按 GUID 过滤（EFI_GLOBAL_VARIABLE）
setvar MyVar -guid <GUID> -nv -bs -rt =0x12345678
bcfg boot dump                    # 查看启动项
bcfg boot add 0 fs0:\EFI\BOOT\bootx64.efi "My OS"
```

`bcfg` 操作的 `Boot####`/`BootOrder` 就是 Runtime Services 里全局变量表里的启动项——Shell 改它们本质就是写 `EFI_GLOBAL_VARIABLE` 命名空间下的变量。

```
Shell> smbiosview -t 0   # Type 0: BIOS Information
Shell> smbiosview -t 1   # Type 1: System Information
Shell> smbiosview -t 2   # Type 2: Base Board
```

`smbiosview` 读 SMBIOS 表，和 Aptio 工具链的 `DMIEDIT` 是同一份数据的两种入口。

| 命令 | 功能 | 常用参数 |
| --- | --- | --- |
| `ver` | Shell/固件版本 | — |
| `reset` | 系统复位 | `-w` 冷 / `-h` 热（不同 Shell 版本参数名可能不同） |
| `exit` | 退出 Shell | — |
| `cls` | 清屏 | — |

| `if`/`else`/`endif` | 条件 | `if exist file.efi` |

通用选项：`-b` 分页、`-v` 详细、`-sfo` 标准格式输出、`-?` 帮助。**Shell 命令数值默认十六进制**，且不区分大小写。

## NSH 脚本与 startup.nsh

NSH 是 Shell 的脚本语言，支持变量、条件、循环、跳转、重定向、参数传递。

`startup.nsh` 是自动启动脚本，放 ESP 根目录，Shell 启动后自动查找并执行。典型用途：延时、批量导出调试信息、自动拉起 RU 等工具。

```nsh
@echo -off
echo "========================="
echo "  BIOS Debug Auto Script  "
echo "========================="
stall 3000000              # 延时 3 秒
pci -b > fs0:\pci_info.txt
dh > fs0:\devices.txt
fs0:\EFI\TOOLS\RU.efi
```

语法速查：`@echo -off` 关回显、`>` 和 `>>` 重定向、`#` 注释、`%1`~`%9` 脚本参数、文件用 UTF-8 或 ASCII 编码。

自动烧录脚本示例：

```nsh
@echo -off
if exist fs0:\BIOS\newbios.cap then
  fs0:\EFI\TOOLS\AFU.efi fs0:\BIOS\newbios.cap /P /B /N /R
  echo "Flash complete!"
else
  echo "ERROR: BIOS image not found!"
endif
reset -w
```

## UEFI APP 开发

### EDK II 开发环境

EDK II 提供完整 UEFI 应用/驱动开发能力。典型包结构：MdePkg（基础协议与库）、MdeModulePkg（标准模块）、ShellPkg（Shell 源码与库）、MyPackage（自建包）。

工具链：编译器（GCC/MSVC）、汇编器 NASM、Python 构建脚本、`edksetup.bat` 配环境、`build` 命令构建。流程：搭环境 → 建模块（.inf + .c）→ 配 .dsc/.fdf → `build` → 拿 `.efi` → Shell 里跑。

### 两种应用入口

**写法 A：普通应用（无 Shell 参数）**

```ini
[Defines]
  BASE_NAME   = MyApp
  MODULE_TYPE = UEFI_APPLICATION
  ENTRY_POINT = UefiMain
[LibraryClasses]
  UefiApplicationEntryPoint
  UefiLib
  UefiBootServicesTableLib
```

```c
EFI_STATUS EFIAPI
UefiMain (IN EFI_HANDLE ImageHandle, IN EFI_SYSTEM_TABLE *SystemTable)
{
  Print (L"Hello, UEFI World!\n");
  return EFI_SUCCESS;
}
```

**写法 B：Shell 应用（带 Argc/Argv）**

```ini
[Defines]
  BASE_NAME   = MyTool
  MODULE_TYPE = UEFI_APPLICATION
  ENTRY_POINT = ShellCEntryLib     # 固定，不可改
[Packages]
  MdePkg/MdePkg.dec
  ShellPkg/ShellPkg.dec
[LibraryClasses]
  ShellCEntryLib
  ShellLib
  UefiLib
```

```c
INTN EFIAPI
ShellAppMain (IN UINTN Argc, IN CHAR16 **Argv)
{
  Print (L"arg0=%s\n", Argv[0]);   // Argv[0] 是 efi 自身路径
  return 0;
}
```

`ShellCEntryLib` 先进入，通过 Shell 协议取参数，再调用 `ShellAppMain`——类似 C 的 `main(argc, argv)`。需要解析 `-x` 风格选项时用 `ShellCommandLib` 的 `ShellCommandLineParse`。

> 选哪种取决于要不要读命令行参数。Hello World 用写法 A，带参数的实践（如指定延时秒数）用写法 B。

### 加入 DSC/FDF

应用要编进固件或单独出 `.efi`，都在 DSC 的 `[Components]` 挂 INF；要把 `.efi` 烧进 FV 让 Shell 直接找到，还要在 FDF 对应 `[FV]` 段放 INF。

### 注册为自定义 Shell 命令（进阶）

用 `ShellDynamicCommand`：在应用里 `LocateProtocol` 拿到 `EFI_SHELL_PROTOCOL`，调 `RegisterShellCommand` 注册命令名、处理函数、帮助串。动态加载、不修改固件；要开机即可用则把 `.efi` 编进 FV 或配启动项。

## AMI Aptio 工具链

### AFU — AMI Firmware Update

跨 DOS/EFI/Win/Linux 的固件烧录工具。核心开关：

| 开关 | 含义 | 风险 |
| --- | --- | --- |
| `/P` | 烧录 Main BIOS | 改主程序 |
| `/B` | 烧录 Boot Block | **最高风险**，Boot Block 写坏即变砖，需 Boot Block Recovery |
| `/N` | 烧录 NVRAM | 清掉所有 Setup 设置 |
| `/R` | 保留 SMBIOS 数据 | — |
| `/SP` | 保留 Setup 用户设置 | 不重置配置 |
| `/CAPSULE` | 走 Capsule 机制 | 配合 Runtime Services 的 Capsule 服务 |
| `/EC` | 更新 EC 固件 | — |

```
AFU64E.efi BIOS.cap /P /B /N          # 完整烧录（清设置）
AFU64E.efi BIOS.cap /P /B /N /SP      # 保留 Setup 设置
AFU64E.efi BIOS.cap /CAPSULE          # Capsule 方式
```

### AMISCE — Setup Control Environment

读取/修改 NVRAM 里的 Setup 变量，等于在 OS 或 Shell 下改 BIOS 设置，不必进 Setup 界面。量产和自动化测试必备。

```
AMISCEEFI /O > setup.txt          # 导出所有 Setup 变量
AMISCEEFI /S BootMode /V 1        # 设变量值
AMISCEEFI /B                      # 恢复默认
```

常见变量：`BootMode`（0/1）、`FastBoot`、`SecureBoot`、`ACPowLoss`（断电恢复策略）、`WakeOnLAN`、`VT-x` 等。本质是对 Setup 变量做 GetVariable/SetVariable。

### MMTool — 固件模块管理

打开/解析 `.ROM`/`.CAP` 镜像，树形浏览 FV，提取/插入/替换/删除 FFS 文件，管理微码和 Option ROM。常用于不重编整个 BIOS 就替换单个驱动或微码。修改后需重算 Checksum。

| FFS 类型 | 说明 |
| --- | --- |
| Driver | UEFI 驱动（USB、SATA 等） |
| Application | Shell、诊断工具 |
| Freeform | 微码、ACPI 表 |
| Raw | Option ROM、BMP Logo |
| PEI/DXE/SMM Module | 各阶段模块 |

### DMIEDIT / ChangeLogo

- **DMIEDIT**：改 SMBIOS 表字符串（System/Base Board/Chassis/OEM String），和 Shell 的 `smbiosview` 读的是同一份数据
- **ChangeLogo**：换 OEM Logo / PBA 图片（BMP），无需重编源码

### 开源 EDK II 对应物

| AMI 工具 | 开源/通用替代 |
| --- | --- |
| AFU | `CapsuleApp.efi`（EDK II，走 Capsule 更新） |
| AMISCE | `dmpstore` / `setvar`（Shell） |
| MMTool | `GenFfs`/`GenFv` 等 BaseTools |
| RU.efi | `mm`/`dmem`（Shell）或 `Chipsec`（安全审计） |

## 调试工作流（综合）

- **设备不识别**：`pci` → `devices` → `connect -all` → `dh`
- **内存问题**：`memmap` → `RU`/`mm` 看寄存器
- **启动问题**：`bcfg boot dump` → `map` → `devtree`
- **驱动问题**：`drivers` → `load` → `connect` → `dh`
- **改设置不进 Setup**：`AMISCE` 直接写变量
- **刷固件**：`AFU` 烧录 → `bcfg` 确认启动项 → 失败查 Boot Block

开发调试循环：`写 .c` → `配 .inf` → `build` → 出 `.efi` → 拷到 Shell 盘 → Shell 跑 → `Print()` 看输出 → `pci`/`dh`/`devices` 排查。

## 易错点

- **命令在不同固件上不一定齐全**：受 ShellPkg 层级/Profile 构建控制
- **Shell 命令数值默认十六进制**
- **`mm` 写寄存器危险**，动之前确认地址、宽度、当前值
- **`reset` 参数名随 Shell 版本变**，以 `reset -?` 为准
- **`/N` 会清 NVRAM 设置**，量产脚本确认是不是故意的
- **应用里阻塞轮询 `ReadKeyStroke` 没问题，常驻驱动里不行**——后者用 `RegisterKeyNotify`
- **`startup.nsh` 位置要对**，脚本编码用 ASCII/UTF-8
- **Shell 在 ExitBootServices 之前有效**，进 OS 后这些命令就不在了（OS 有自己的工具如 efivarfs、fwupdmgr）

## 术语表

- **EFI_SHELL_PROTOCOL**：Shell 安装的核心协议，外部命令通过它注册、取参数、操作文件
- **ShellCEntryLib**：提供 `ShellAppMain(Argc, Argv)` 入口的库
- **FV / FFS**：固件卷 / 固件文件系统，BIOS 镜像的容器和文件格式
- **NCB**：非关键块，可独立更新的固件区域
- **Boot Block**：固件最小引导块，含自救指令；写坏需 Boot Block Recovery
- **E820**：x86 启动阶段传递物理内存布局给 OS 的表
